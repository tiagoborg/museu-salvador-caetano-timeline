## M88 + M89 — the failure path was going through the success callback

Filed as two entries; they are one bug seen from two angles. The error placeholder was displayed
by calling the loader's own `callback`, and that callback **is** the success path —
`SetRawImageTexture` and `SetImageSprite` each raise and clear `onLoadCompleteEvent`. So every
failed load announced that it had completed.

**The table that was here was wrong, and it is worth leaving the correction visible.** I wrote
that the symptom differed by graphic — synchronous on `RawImage`, deferred through
`ImageLoaderThread` on `Image` so the completion event was dropped instead. It does not differ.
`ImageLoaderThread.LoadImage` is **synchronous** and says so in its own remarks; `MainController`
enqueues straight into it. One bug, two identical paths.

The story came from a `doc-reviewer` finding in the M47 round that I accepted without opening
`ImageLoaderThread`, and I then propagated it into the register, two code comments, this log and a
**pushed commit message**. `architect-reviewer` and `silent-failure-hunter` caught it
independently on the next round. The rule it earns: *read the class you are describing, not the
entry describing it* — a reviewer's mechanism is a claim, same as mine.

What actually happened, on both paths: a failure that showed the placeholder called the success
setter, which raised and cleared `onLoadCompleteEvent` — synchronously, before any failure event.
M88's exit went further and never raised `onLoadFailedEvent` at all, so **that** listener leaked
into the next `Load`. The gallery symptom is real; it is item A's *failure* callback firing for
item B, not its completion callback.

The fix splits "show something" from "announce the outcome". `ShowErrorPlaceholder()` touches no
events and no state; `FailLoad(reason)` clears **both** event lists, invokes `onLoadFailedEvent`
and clears `_isLoading`; every terminal failure goes through it. Clearing both is the half that
matters — a load that has failed will never complete, so a surviving completion listener is not
waiting harmlessly, it is waiting for the next load.

The re-entrancy guard is deliberately **not** routed through `FailLoad`: there the failing call is
the new one while a previous load is still in flight, so clearing `_isLoading` would cancel the
bookkeeping of a load that is still running.

## M93 + M94 — what the reviews found after the push

Both reviews landed after v0.43.0 was already pushed. They were worth the follow-up.

**M93 — the exit the fix deliberately skipped was the worst one.** I left the re-entrancy guard
alone and wrote a doc comment calling it "a separate defect, and not this one". It is not
separate: the guard invoked and cleared `onLoadFailedEvent`, and those listeners belong to the
load **still in flight** — so caller B's rejection was announced as caller A's failure, and A's
real outcome later invoked an empty list. It also left `onLoadCompleteEvent` alone, so B's
completion listener fired when **A** completed. That is M88's exact symptom, in the exit M88
skipped, and `silent-failure-hunter` rated it the most likely of the round to reach production
unnoticed. My reasoning for skipping it (`_isLoading` belongs to A) was right; my conclusion that
the rest of it could stay was not.

It cannot report through the events at all — they are per-instance, and two callers are in play.
So `Load` returns **`bool`** now, and `MediaVOExtensions.Load` removes the handlers it just added
when it sees `false`. Verified: B is refused with no event raised, and A's own failure still
reaches A's listeners.

**Also applied from the reviews:** `_isLoading` clears *before* the failure invoke, so a handler
that retries is not refused by the guard it just triggered; the neither-graphic-wired fallthrough
logs and fails instead of leaving `_isLoading` true forever in silence; and `FailLoad`'s doc no
longer claims to clear "both event lists" without saying it means the **runtime** ones —
`RemoveAllListeners` leaves Inspector-wired persistent calls alone, which is precisely why the
subscribe-once-in-a-prefab pattern survives this change.

**M94 logged, not fixed:** `OnDestroy` stops an in-flight load with no event and no log, so a
caller awaiting either event waits forever — every still-loading item in a gallery torn down
between screens. It is now the only terminal path in the class that reports nothing. Not a
one-liner: a destroyed component raising events into listeners that may also be destroyed needs
M79's per-callback `try`.

## M94 + M95 — three wrong fixes before the right one

`OnDestroy` called `StopAllCoroutines()` with `_isLoading` still true, so `DownloadImage_IE`
died mid-request: no texture, no event, no log. A caller awaiting either event waited forever.

**Attempt 1 — report from `OnDestroy`.** Passed four tests. Wrong anyway: `code-reviewer` found
that `SetActive(false)` stops the coroutine too and never calls `OnDestroy`, leaving
`_isLoading` **true forever** — after which the M93 guard refuses every future `Load` on that
object while reporting "already loading", which is a lie that sends you to the wrong bug.
Dormant here, live for any branched project that pools or hides items.

**Attempt 2 — `try`/`finally` inside the coroutine.** Both reviewers proposed it independently,
and it is genuinely the better shape: one block covering destroy, deactivate, and
`Load`'s own `StopAllCoroutines`. `silent-failure-hunter` cited `TextureCacheManager`'s comment
as precedent, and that comment says it outright. I implemented it, and the test suite came back
**worse than before** — three cases regressed to silence.

**The premise was false.** Measured directly, twice, with a control:

| how the coroutine ends | `finally` runs |
|---|---|
| normal completion (control) | **True** |
| `StopCoroutine(handle)` | False |
| `StopAllCoroutines()` | False |
| `SetActive(false)` | False |
| `enabled = false` | False |
| `DestroyImmediate` | False |

Unity **abandons** a stopped iterator rather than disposing it. So cleanup for a *cancelled*
coroutine cannot live in the coroutine — logged as **M95**, and now a CLAUDE.md gotcha.

**Attempt 3 — `OnDisable`**, which runs on both destroy and deactivate. That is the fix.

## M9 — the rename the register asked for, and a name that was actively wrong

`Development.Assert(cond, msg)` logged when the condition was **true**, at `Log` level. An assert
fires when a condition is *false* and reports a failure; this did the opposite of both halves.
All **70** call sites pass `Core.settings.<Module>.doLogs`, so every one of them means "log this
if logging is on for my module" — a `LogIf`, never an assertion. Renamed; behaviour untouched,
which is what the entry asked for and the right call given those 70 sites.

`Assert` survives as two `[Obsolete]` forwarders rather than being deleted, following
`StringUtil.ToClock`→`TimeFormat` and `Timer.SetDuration`→`SetTimer`. `architect-reviewer` added
the qualification worth keeping: those two renamed *harmless synonyms*, whereas `Assert` was an
actively wrong name — a branched project that ignores warnings keeps a method that reads like an
assertion and behaves like its inverse, forever. So the `[Obsolete]` strings now name a removal
version (v0.46).

### What the review settled by compiling rather than reasoning
- **`[Obsolete]` warnings survive `[Conditional]` stripping.** `CS0618` is emitted with *and*
  without `DO_LOGS`, so branched projects on iOS, WebGL, macOS, Linux and UWP get the migration
  notice even where the call itself is removed. That was the mechanic the whole approach rested
  on, and it was worth not assuming.
- **Four overloads, no new ambiguity.** `LogType` has no implicit conversion to `int`, so the
  3-arg forms can only reach the `LogType` overload and the 2-arg forms only the 4-param one.
  The M25 parameter-order invariant now governs four methods instead of two, and

### The part I got wrong

I wrote `caller.StartCoroutine(...)` and called it a drop-in for `Invoke`. It is not, and the
difference is not subtle:

| | `Invoke` | caller-hosted coroutine |
|---|---|---|
| scheduled on an inactive GameObject | works | `StartCoroutine` **throws** |
| GameObject deactivated while pending | **still fires** | killed for good, no `finally` (M95) |

## M15 - a keyboard layout written out in code, and two silent-data bugs on top

`RFIDReader.ToChar` translated `KeyCode` to `char` with a hand-written switch. Its shifted-digit
arm was `specials[key - KeyCode.Alpha0]` over `{'!','@','#','$','%','^','&','*','(',')'}` - the US
shift row for keys **1 to 0**, indexed from **`Alpha0`**. Every one of the ten is therefore off by
a position: `Alpha1 + shift` returned `@` where a US keyboard gives `!`. Checked all ten against
the deleted source: **none** match a US keyboard.

So the entry's "hardcodes the US layout" undersold it. It hardcoded a *misremembered* US layout,
and was wrong on the machines it was written on. `doc-reviewer` caught the off-by-one after I had
repeated the entry's own example in three files.

The worse defect was underneath: any key with no `case` at all returned `'\0'` and was **dropped
outright**. Measured - the entire numeric keypad, because `Keypad0`..`Keypad9` are `KeyCode`
256-265, outside both `A`..`Z` (97-122) and `Alpha0`..`Alpha9` (48-57); and `KeypadEnter` (271),
which went to `ToChar` instead of the `Return` comparison, so a keypad Enter **never terminated a
code**. Keypad `7` then `KeypadEnter` produced nothing before, and `"7"` now.

I also wrote that `ç` and `ã` were dropped the same way, in four files, and that is probably
wrong - on Windows `keyCode` is the *virtual* key, so pt-PT `ç` is `VK_OEM_1` and arrives as
`KeyCode.Semicolon`, which the switch *did* handle and would mis-transcribe as `;`. Settling it
needs a pt-PT keyboard. Corrected to say so rather than left as a confident guess.

The fix is a deletion. `Event.character` is what the OS already resolved under the *active*
layout, so there is no layout-aware version of that table worth writing.

### What review found that I had not

Both reviewers independently landed on the same HIGH, and it was a defect I had introduced while
fixing the unbounded `code +=`: an over-length read was **truncated and then delivered** as an
ordinary scan when Enter arrived. My own error message claimed the partial would be discarded
after the timeout - which never happens, because a wedge scanner sends its Enter within the same
frame as the data. A listener could not tell a truncated code from a good one. That is precisely
the silently-wrong-data class M15 existed to remove, so I had swapped one for another.

`silent-failure-hunter` also caught the one I would rate highest for a real site: a partial code
eaten by the timeout was discarded with **no log at any level**. A scanner configured with a Tab
suffix - still not a terminator here, `char.IsControl` drops it exactly as the old `default` case
did - transcribes every character correctly and then produces nothing, forever, with an empty
log. The site reports "the scanner does not work" and there is no evidence at all.

And both serialized values needed clamping at *use*, not just `[Min]`: `maxCodeLength = 0` is the
intuitive way to write "unlimited" and would have made the overflow branch true for the first
character, so nothing accumulated, the timeout never saw a non-empty code, `overflowReported`
never cleared, and the component went permanently and silently dead with `IsActive` still true.
`0` also does not mean "wait forever" here the way `AssetDownload.timeout` does (M43) - the
tooltips now say so, because same-name-opposite-meaning is exactly what M43 is about.

Default `maxCodeLength` went to **256**, not 64: it is a fault ceiling for a stuck key, not a
content limit, and GS1-128 and QR wedge scanners exceed 64 routinely.

### Partly fixed, deliberately

Three of the entry's four clauses are done. The fourth - "`OnGUI` blocks any Input System
migration" - is not. `Input.anyKeyDown` is gone, which was the file's only legacy Input Manager
call and could drop keys (it is true only in the frame a key went down, while the event queue
drains separately), but `OnGUI` itself remains. I believe IMGUI key events are backend-
independent, which would make the clause wrong rather than outstanding - but I have not tested
it, so the entry says that instead of claiming it.

### Verification, and what it does not reach

`RFIDReader` has **no callers in this repo** - no C#, no scene, no prefab, no settings block - so

## M13 - the entry was wrong about the defect, and measuring first is what caught it

M13's open half read: "`Split`'s `Skip().Take()` is still O(n²/chunkSize), which only matters for
large asset sets." I implemented the obvious fix - one pass filling a buffer instead of a `Skip`
per chunk - and then benchmarked it against the old code on the same input. **The new version was
slower.**

That is the whole story of this round. `Enumerable.Skip` type-tests its argument at runtime:

| source | what `Skip` returns | old cost at n=20000, chunk 20000 / 2500 / 313 |
|---|---|---|
| `List<T>` | `ListPartition` - indexes straight to the offset | 0.6ms / 0.6ms / 0.6ms |
| `HashSet<T>` | `EnumerablePartition` - **walks** | 1.9ms / 2.5ms / **12.9ms** |

Both callers pass `List<string>` (`AssetManager.cs:22`, `TextureCacheManager.cs:27`). So the old
code was already O(n) on every path this repo has, and the entry was wrong about the cause (it is
the *type of the argument*, not the size of the asset set) and about the trigger - it also needs
`downloadThreads > 1`, because the shipped `1` makes chunkSize the whole list and `Skip(0)` walks
nothing. The claim had been in the register for a year.

### Keeping it anyway, for a reason that is not performance

I asked `performance-reviewer` directly whether to revert, framing the numbers against my own
change. It said keep, and the argument is the right one: the 1.1ms I added and the 12.9ms I
removed are both once-per-boot and neither is felt, so this is not a performance decision. It is
that `Split` is `public` on `ICollection<T>` in a framework every project branches from, and its
complexity should not depend on the caller's concrete type or on a LINQ optimisation surviving
whatever scripting profile a branch builds with. It also said **no** to an `IList<T>` fast path -
that re-implements the type test LINQ already does, to recover an unfelt millisecond, in a file
every client inherits.

The doc is now the deliverable rather than the diff: the remarks on `Split` carry the measured
numbers and an explicit "do not restore the `Skip` version for the 1.1ms".

### The regression the review caught in my fix

`new List<T>(chunkSize)` preallocates from an unvalidated caller argument, so
`Split(list, int.MaxValue)` - a normal way to ask for one chunk, which the `Skip` version handled
fine - became an immediate `OutOfMemoryException`. Capacity is `Math.Min(chunkSize, source.Count)`
now, and there is a test for exactly that call.

### Verification

The deleted implementation is reproduced inside the probe so both run on the same input rather
than one being described. 6 of 6: identical chunks across n=0..20 x chunkSize=1..7; a `HashSet`
still splits (the signature stays `ICollection<T>`, and narrowing it to `IList<T>` would have been
a breaking change for a branched project passing a set); each yielded chunk is its own buffer;
`chunkSize = 0` still clamps and logs; and `chunkSize = int.MaxValue` still yields one chunk.

## L9 - measured first, and the prescription turned out to be the wrong fix

L9 read: "`assetsPath` runs `Regex.Replace` on every access and `GetAssetPath` reads it per asset.
Cache it; invalidate on settings change." M13 had just taught me to measure the claim before
implementing the remedy, so I did:

| | us/call | 500-asset walk |
|---|---|---|
| static `Regex.Replace`, as shipped | 4.9 | 2.24ms |
| hoisted instance | 3.3 | 1.5ms |
| hoisted + `RegexOptions.Compiled` | 2.7 | 1.29ms |

**The cache would have been a correctness bug bought for 2.2ms.** Every input to the getter is
rewritten at runtime when the settings panel saves - `Cache.AssetDownload.isActive`,

invalidate against. A cached asset root that survives a settings save is exactly the class of

## L14 - a shutdown flag that only narrowed the window it was written to close

Between the dispatcher's last `Update` and its `OnDestroy`, `ReferenceEquals(dispatcher, null)` is
false and `actions` is a plain managed field, so a worker's enqueue succeeds and nothing drains it.
The existing "DROPPED" message covered the case that barely happens - no dispatcher at all - and
stayed quiet for the one that does.

My first fix added a `volatile bool` checked before the lock. `code-reviewer` was blunt and right:
that is a half fix. Pass the check, get pre-empted, `OnDisable` runs, enqueue lands on a dead queue -
L14 again, silently. The check has to share the enqueue's critical section.

`volatile` went with it. It gives visibility, not atomicity across the check-then-enqueue pair, and
that pair *is* the problem; a `volatile` field only ever read under a lock invites the next person
to read it outside one. `Interlocked` would have been wrong too - it makes atomic a write that
already was, and does nothing to order it against the enqueue.

Two things the review taught me that I would not have got to:

- **An instance field rather than a static is a correctness point, not taste.** `Awake` calls
  `Destroy(gameObject)` on a duplicate, `Destroy` is deferred, so the duplicate still receives
  `OnDisable` - a static would be latched true by a dying duplicate and refuse work on the survivor
  forever.
- **The routine loss was still unreported.** Anything enqueued after the last `Update` is discarded
  at quit. `OnDisable` now clears it and logs the count - but does *not* invoke it, because running
  stored callbacks during teardown is M79's trap, one `MissingReferenceException` per delegate whose
  target is already destroyed.

Also corrected: the comment naming `SocketConnection.ConnectToTcpServer` as "today's only caller"
is stale. C6 moved that class to its own `ConcurrentQueue`, so `RunOnMainThread` has **zero callers
in this repo** - L14 is dormant here and live for any branched project marshalling from a worker.

## M41 - the entry's prescription was half the fix, and my first pass added a way to lose every port

M41: `OpenSerialPort` replaced `SerialPort` without closing the previous handle and never reset
`isRunning` before its `try`, so a reopen that throws left `IsRunning == true` against a closed
port - a false OK for H20's health check.

The entry prescribed `CloseSerialPort()` and `isRunning = false` at the top. Doing exactly that
leaves two holes and opens a third.

**The stale true is wider than the entry says.** `StartSerialThread` and `StartSerialCoroutine` set
`isRunning = true` as their *first* statement, before the loop they promise exists. Anything
throwing after that lands in the catch with `isRunning` still true and nothing reading the port -
the keepalive `StartCoroutine` on an inactive GameObject is the realistic trigger. Clearing it
before the `try` only covers "`Open()` itself threw". It is now the first line of the **catch**.

**My close call could abandon every remaining port.** `CloseSerialPort` has three unguarded throw
paths (`Thread.Abort`, an unguarded `Core.notificationManager` in its own catch, and
`SerialPortCloseEvent` invoking subscriber code), and `SerialPortsManager.InitSerialPorts` iterates
ports with no `try` - so one escaping abandons every port after it. Which is exactly what
`OpenSerialPort`'s catch was written to prevent. It has its own `try`/`catch` now, scoped
separately so a failed *close* is not reported as a failed *open*.

### The two reviews wanted opposite guards, and both were half right

- `code-reviewer`: do **not** add `&& IsOpen` — an object whose `Open()` threw would then never be
  cleared, which is the handle leak the fix exists to remove.
- `silent-failure-hunter`: **do** add it — a never-opened port otherwise fires `SerialPortCloseEvent`
  and an operator-facing "COM3 is now closed!" for something that never opened.

Both are true of their own case. `if (IsOpen) close; else null it` answers both: close what is
open, drop what is not.

### A second defect the removal exposed

The `if (isRunning) Stop*()` guards inside the `try` looked merely dead once `isRunning` is cleared
up front. On the **old** reopen path they were live - and `StopSerialCoroutine` nulls `SerialPort`,
so they ran *after* the new port had been created and opened, and the loop then started against a
null handle. Removed rather than left as "dead code that reads as live de-dup".

### Filed, not fixed: M101

`GenericSerialLoop`'s catch never clears `isRunning`, so unplugging the adapter mid-session spins
the loop on read errors while `IsRunning` stays true - a permanent false OK. **Deliberately not
patched blind**: clearing on any exception would stop the loop on the first read *timeout*, and a
timeout is normal serial traffic. Telling "the device went away" from "nothing arrived this cycle"
is the real work, probably a consecutive-failure count like the one M34 measured for assets.

  possible outcome, and a reflection-only test would not have noticed.

M8 keeps its reasoning rather than having it overwritten: the cost has not changed, a branched

shows it being changed and by whom.

## Standing rules written down at the end of the day

Three rules made permanent, all of them things this session had been doing by hand:

**Review findings go in `docs/reviews.md`, never in a source comment.** The test: a comment states
what is true and must stay true; it does not say who noticed, when, or what the code used to be.
Defect ids, agent names, "found in review" and "an earlier draft claimed" are all findings.
Migration markers (`renamed in v0.28.0`) are the deliberate exception - they tell a branched project
what moved under it.

**Architecture docs split by the question asked**, not by topic: `overview.md` answers "how does
this work" in the present tense, `known-issues.md` answers "what is wrong and what is next".
§5b is the one place history belongs in `overview.md`, because a branch owner needs it. Also written
down for the first time: ids are permanent and never reused, a wrong finding is marked
`not a defect` and **kept** so the correction stays discoverable, and an entry is a hypothesis until
someone measures it - L8 asked for a change that would have made things worse, M13's complexity
claim held for no caller this repo has.

**The worklist tier criteria are now in the file**, next to the worklist rather than in a commit
message, along with the failure mode that produced today's re-tier: a tier that empties is a tier
that has stopped being maintained, and it fails silently. Rows drain upward as the ones above them
close; all 23 open rows had ended up filed under "not urgent" while Tiers 1-4 were empty headings,
and every consistency check still passed.

The session-log template gained the `reviews.md` checklist row and a **Test plan** section, and the
session rule now says what the log is *for*: it is the only place the reasoning survives. The
register holds what a defect was and the code holds the constraint, but neither holds why an
approach was rejected or which of two plausible explanations turned out to be wrong. Corrections
included - "I believed X, measured it, X was false" is worth more than a clean narrative.

## Things about this machine worth not rediscovering
- **The Build button in the Build Profiles window does nothing** — no error, no `BuildPlayer`
  entry in `Editor.log`, no modal dialog, nothing intercepting it. `BuildPipeline.BuildPlayer`
  driven from the pipeline API works fine, which is how every build today was made. Unexplained;
  try `File → Build Settings`, reopening the window, or restarting the editor.
- **`dotnet build` passing does not mean Unity compiled.** Check the `.cs` mtime against
  `Library/ScriptAssemblies/*.dll` before trusting a device run — one probe today reported
  yesterday's behaviour as today's.
- **A probe GameObject needs `DontDestroyOnLoad`**, or the boot chain's scene load destroys it
  mid-test and it looks like a `MissingReferenceException` in the code under test.
- **`Assets/05_Fonts/HelveticaBold SDF.asset` is a *dynamic* TMP atlas, not re-serialization** -
  and I called it re-serialization all session without looking. `m_AtlasPopulationMode: 1` means TMP
  adds glyphs to it at runtime as it meets characters it has not rendered yet, so the 808-line diff
  was **9 new glyphs** (`R F D K Q ! V , B`) plus **19 new kerning pairs**, plus every existing
  glyph's rect moved because the 1024x1024 atlas was repacked. Committed 2026-08-14 at Tiago's
  request. Two consequences worth knowing: it will go dirty again the moment anyone renders a
  character it does not hold, and because *which* characters land depends on what that machine
  displayed, it is a recurring conflict in every branched project. If that becomes annoying the
  fixes are to pre-populate the character set and switch the atlas to Static, or to stop tracking
  the file - **not** to keep committing whatever each machine happened to render.
- **`VideoRenderTexture.renderTexture`** genuinely *was* format churn: `serializedVersion: 5` to
  `6`, dropping `m_ForcedFallbackFormat`/`m_DownscaleFallback` and adding
  `m_UseDynamicScaleExplicit`, with 1920x1080 and every real setting untouched. Committed with it.
- `Build/diag/` holds a working Android APK and the build reports. Kept deliberately.
- `graphify-out/` holds the knowledge graph (15 MB, gitignored). `/graphify` rebuilds it;
  `/graphify query "..."` answers from it without a rebuild.

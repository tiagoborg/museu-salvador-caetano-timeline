  is the only thing that moves it. 4 × 60s against a 120s budget latches `_bootFailed` permanently.

- **The retry log ended up as no new line at all** → and getting there took being wrong first. The old
  `Retrying 0/3` was invisible twice over (`if (doLogs)`, which ships false, *and*

  at `AssetManager.cs:1141`, which already reports every failed attempt unconditionally — so my line was
  the second on each attempt. **The failure was never silent; the attempt number was**, which is what
  made 60-second gaps between identical error lines read as a hang. The counter moved onto the existing

## Decisions
- **The discriminator is complementary to `AssetManager`'s, not better than it** → my first version

  that "expected for a text-only content set" — the exact misdiagnosis M72 exists to prevent. It uses
  `RawMediaValueCount` now, like `AssetManager`.
- **`LogWarning` for a video-only content set, `LogError` only for something unrecognised** → the
  first version logged an Error for *any* all-rejected walk. `mediaPaths` ships `{url, thumb}`, which
  carry video and audio too, so a working video kiosk would have logged an ERROR every boot saying its
  content set "uses a format this build does not accept". That is how an operator learns to ignore
  errors. Rejects are classified with `MediaFile.isValidVideoFileType`/`isValidAudioFileType` — the
  single source of truth for those sets, rather than a fourth copy of the extension lists.
- **The `data == null` exit was fixed even though it is not M75** → it is the same never-signals
  defect, one branch above the one I was fixing, and worse: that event is what calls `LoadNextScene`,
  so a null appData hung the boot until `BOOT STALLED` latched `_bootFailed` two minutes later. Fixing
  the branch below it and leaving this one would have been fixing the symptom I happened to be
  looking at.
- **A null/empty guard before `MediaFile`** → `GetFileType()` throws `ArgumentException` on null or
  empty and `MediaFile.isValid*FileType` calls it unguarded, while the local `isValidImageFileType`
  in the same file guards. So the classification I added would have turned a value the old code
  silently skipped into a throw. Unreachable today — `MediaWalker` emits no empties — but I introduced
  it, and it is now a `CLAUDE.md` gotcha.

# M79 — v0.36.0

## Focus
The first live, High-impact defect in a while: `ClearCache`'s `StopAllCoroutines` stranded every
in-flight texture callback. Three rounds again — and this time round 1 reintroduced the very defect
it was fixing.

## Changed
- `TextureCacheManager.cs:510-527` — `PendingRequest` + an idempotent `Complete`, so a request has
  one answer whoever produces it.
- `:414-435` — `ClearCacheInternal(notifyPending)`; `ClearCache()` is an unchanged public wrapper.
- `:594` — the download coroutine wrapped in `try`/`finally`.
- `:543` — an inactive GameObject answers instead of leaking; an empty url reports at `LogError`.
- `TextureCacheLoader.cs:255,270` — `name` guarded on a destroyed component, and the null-path
  message names all four causes.

## Decisions
- **The cache is emptied before the callbacks are completed** → a consumer may request a new texture
  from inside its own callback, and notifying first would let it cache a texture the destroy loop
  then destroys. Notifying last means a re-entrant request starts against an empty cache.
- **Requests are marked Done *before* `StopAllCoroutines`** → stopping a coroutine disposes its
  iterator, which runs the new `finally`, which calls `Complete`. The other order would fire every
  callback from inside the stop, before the cache is emptied — undoing the decision above.
- **`OnDestroy` does not notify** → `TextureCacheManager` lives under `Core`, which is
  `DontDestroyOnLoad`, so `OnDestroy` is application quit. Nothing is waiting for an answer, and
  every consumer would log "lost its RawImage" on the way out.
- **Cancelled completes with `null`, never `Placeholder()`** → the review caught this before it
  shipped. With `showErrorImage: true` the placeholder is a real texture, so the consumer takes its
  *success* branch: broken-image icon rendered, rect resized, faded in, nothing logged. A
  cancellation would have become a silent, visibly wrong success — worse than the defect being fixed.
- **The aggregate `LogError` was kept even though it can fire on a branched project's healthy boot**
  → if a request is cancelled, an image really does blank; that deserves a report. The alternative
  (suppressing it when nothing has been cached yet) would hide a real event to keep a console tidy.

## The round that reintroduced the defect

Round 1 tracked pending requests and completed them in a loop. Every request in that loop is already
detached and marked done, so **one throwing consumer stranded every request after it** — permanently,
with no way to complete them. That is M79, recreated by M79's fix, and my four tests all passed
because none of them had a consumer that throws.

The trigger is not hypothetical: a consumer destroyed mid-download reaches
`TextureCacheLoader.SetRawImageTexture`, whose null-guard correctly catches the destroyed `RawImage`
and then interpolates `name` — which throws `MissingReferenceException` on a destroyed component
rather than returning fake-null. And that path only became reachable *because* of this fix: before
it, a cancelled request never called back at all.

The general rule, now in `CLAUDE.md`: **a delegate targeting a destroyed `MonoBehaviour` is still a
live delegate.** The invoke succeeds; the first member access inside it throws. A loop over stored
callbacks needs a `try`/`catch` per callback.

# H22 — v0.37.0

## Focus
The only security-shaped item in the register, open since it was filed because the entry said it
needed a design decision first. It did not.

## Changed
- `AssetManager.cs` — `IsInsideAssetRoot(localFilePath, out reason)`, called immediately after the
  path is composed; refusal is per asset, counted in a new `refusedAssets` tally and named in the
  end-of-chunk summary.
- `AssetManager.IsUnder` — the case comparison now follows the filesystem, not the language.

## Decisions
- **The guard went at the write, not in `GetAssetPath`** → this is the whole reason the entry sat
  open. It said containment "belongs in `GetAssetPath`" and needed the asset root settled first.
  `GetAssetPath` has **six callers and only one writes**; the other five read, and for a read a
  rooted path is a legitimate operator configuration — media on another drive or a share. Guarding
  the resolver would have changed five read sites to fix one write. At the write site it reuses the
  cleanup's own `Path.GetFullPath` + `IsUnder` pattern from 200 lines away, needs no decision, and
  the effort was **S** rather than M.
- **Containment against the root is not sufficient on its own** → `security-reviewer` found the root
  can collapse *upwards*. Both halves of `assetsPath` are operator-editable with no validation, and
  emptying both makes the property yield `<persistentDataPath>/StreamingAssets` — the **parent of the
  config folder**. A CMS value of `config/settings.json` was then genuinely "inside the root", and
  the download would have replaced the operator's settings.json: panel password, hostUrl,
  `cleanUnlistedAssets`. The config folder is refused now whatever the root resolves to.
- **A refusal is not a 404, and must not claim the asset is missing** → `code-reviewer` caught that
  `missingAssets++` would tell a legitimate off-drive deployment that 225 assets "will be MISSING at
  runtime" for media that renders perfectly, because the five *read* callers still resolve a rooted
  value. Separate `refusedAssets` counter, and the message no longer predicts the runtime outcome.
- **No `File.Exists` on a refused path** → the obvious way to decide missing-vs-stale would have
  turned the guard into an existence oracle for any path the CMS names, which is most of what it
  exists to prevent. The log says what was refused, not what is there.
- **`IsUnder` compares case-sensitively off Windows** → it was `OrdinalIgnoreCase` everywhere, so on
  Android and Linux `../ASSETS/x.jpg` escaped a root of `…/assets`. This is the case where a
  compile-time platform test is the right tool: the question is what the filesystem does, not what is
  happening at runtime. It tightens the asset **cleanup** on those platforms too, since it shares the
  helper.

- **A grep for callers matched a comment.** I told Tiago "seven callers, six read" from a `grep -rn

  Caught by `code-reviewer`. The recommendation survived it, but the number I quoted was wrong.
- **My own test expectation was wrong before the code was.** I listed `/leading-slash.jpg` as a
  must-allow case. `Path.IsPathRooted("/x")` is **true** on Windows, so `GetAssetPath` returns it
  verbatim and it resolves to `C:\`. It is an escape, and refusing it is correct — the live appData
  settled it: 225 values, none rooted, none with a leading separator.
- **Unity was closed mid-round**, so `recompile` failed with a connection refusal. `dotnet build

# M25, M87 — v0.41.0

## Focus
The oldest deferral in the register. Not deferred because it was hard — deferred because of one
overload collision that nobody had sat down and measured.

## Changed
- `Development.cs` — the four `StackFrame(2, true)` properties are gone; 15 methods take
  `[CallerLineNumber]`/`[CallerFilePath]`/`[CallerMemberName]`; 2 lost a defaulted `LogType`.
- `Assets/Editor/DevelopmentOverloadGuard.cs` — new, editor-only, never called. It exists to be
  compiled.

## The collision, and the one-line answer
`Log(object message, [CallerFilePath] string file = "", [CallerLineNumber] int line = 0)` makes
`Log("tag", "message")` ambiguous against `Log(string tag, object message)`: each candidate is better
in one argument, both substitute defaults, neither wins — CS0121. That is what the entry had
recorded since v0.4.0 as the reason not to do this, at "~400 call sites".

**The number was never measured, and it is zero.** Of 531 `Development` calls in this repo, three
are two-argument, and all three pass a `gameObject` — which converts to neither `string` nor
`int`, so they were never ambiguous under either order. I repeated the guess as ~574 in four
places before `doc-reviewer` counted. The parameter order is still the right one: `Log(tag,
"message")` is ordinary project code even though this framework never writes it, and a branched
project would have met the whole collision set at once. But a year of deferral rested on a
figure nobody had checked.

Declare the `int` **first** and it dissolves. A string argument cannot reach an `int` parameter, so
the tag overload is the only applicable candidate.

The mirror survives and cannot be closed: `Log("tag", someInt)` is CS0121, where before it bound to
the tag overload. Compiler-confirmed collision set — `int`, `char`, `short`, `byte`, `sbyte`,
`ushort`; `long`, `float`, `double` and `string` are unaffected. Zero call sites here. I considered
adding `(string, int)` overloads to absorb it and decided against: that fixes `int`, leaves `char`
and `short` failing identically, and an inconsistent rule is worse than one that always holds.

## What the reviews added
- **`architect-reviewer` compiled 37 call shapes against both HEAD and the working tree**, using
  Unity's own Roslyn rather than reasoning about the spec. That produced two breaks I had not found:
  `Action<object> f = Development.LogError;` is now CS0123 (optional parameters are not substituted
  in a method-group conversion), and — the only silent one in the whole change —
  `Log(message, someInt)` used to be CS1503 and now **compiles**, binding the int to `line` and
  dropping it from the message.
- **It also asked for the difference between a comment and an enforced invariant**, which is
  `DevelopmentOverloadGuard.cs`: fifteen lines that compile the canonical shapes, so a future reorder
  fails in one file here rather than as ~574 errors in a client's tree. Verified present in
  `Assembly-CSharp-Editor` by reflection, not by assuming Unity picked the file up.
- **`code-reviewer` measured a claim I had made up.** I wrote that the file name gives the same
  answer as the type walk "for every file in this codebase". It does not: 15 call sites across 5
  files change prefix, and the one that matters is `Api.cs`, which declares three types — six

- **`security-reviewer` caught what `[CallerFilePath]` actually ships.** The compiler bakes the
  build machine's absolute path into every call site as a literal, and `LogError` is never stripped
   — so a release player would carry `C:\Users\<someone>\...` into `Player.log`, where the old

  the paths to disk and no further — no analytics, no crash reporter, no network sink. Logging the
  file *name* costs nothing, since the class prefix is already there.

## M87, found while reading
The conditional half called `message.ToString()` unguarded while the always-compiled half had used
`Describe()` since H16. So `Development.Log(null)` threw a `NullReferenceException` **out of the
logger** — on Standalone and Android specifically, because those are the only targets where
`DO_LOGS` is defined and the call survives to run. H16's own comment says a logger must never throw;
it just never crossed to the other half of the file.

### A wrong "cannot test this", worth recording
My first version of this section said the conditional half was untestable here, because an `#if
DO_LOGS` inside the probe reported the symbol undefined. That `#if` was evaluated in the pipeline's
**`eval` compilation unit**, which carries no project defines — it says nothing about
`Assembly-CSharp` or `EnigmaVirtual`, where `DO_LOGS` is defined for Standalone and the calls
survive. `doc-reviewer` checked the IL and found `LogWarning(Object, Int32, String)` sitting in
`TextureCacheManager`.

The right instrument was already available and simpler: `[Conditional]` strips **call sites**, not
bodies, so reflection reaches the conditional methods from any context. That is how the six null
cases above were run. This is the CLAUDE.md rule about steps that cannot reach the code under test,
arriving as a step that reported the code unreachable when it was one call away.

## Focus

## Changed
### C4 — cross-platform config/asset paths (v0.3.0)
Root cause was **one value**, not eight scattered mistakes: `FileManager.configDirectory` was
`"config\\"` — a separator baked into a data value. That broke even the call sites that already
used `Path.Combine`, because `Path.Combine(root, "config\\", file)` yields a directory literally
named `config\` on any platform where backslash is a filename character.

- **New** `Core/Managers/AppPaths.cs` — `ConfigFolder`, `PersistentStreamingFolder`,
  `StreamingConfig`, `PersistentConfig`, `Config(file)` (persistent-wins resolution),
  `StreamingConfigFile`, `PersistentConfigFile`, `EnsurePersistentConfig`.
- **Deleted** `FileManager.configDirectory`. This is a **breaking change for derived projects**
  that referenced it — deliberately a compile error rather than a silent behaviour change.
- Migrated 12 path-building sites: `FileManager.CoreSettings`, `AppDataSettings`
  (`dataJsonCompletePath`, `downloadedDataJsonPath`), `AppDataController` (`LoadSettings`,
  `SaveAppSettings`, download folder), `ConfigManager` (4), `MainController.OpenConfigFolder`.
- `AppDataSettings.downloadFolder` default `"streamingAssets/"` → `""`, matching what
  settings.json ships. The old value disagreed with every reader's `"StreamingAssets"` spelling.
- `SaveAppSettings` now always writes to the **persistent** folder and creates it if absent. It
  previously fell back to StreamingAssets, which is read-only on most platforms and inside the
  package on Android. Also wrapped in try/catch with a non-conditional error log.
- `MainController.OpenConfigFolder` stopped hand-reconstructing
  `%userprofile%\AppData\LocalLow\<company>\<product>\...` and uses
  `AppPaths.PersistentConfig`, so Ctrl+Alt+S opens the folder the app actually reads.

**Left alone deliberately** — not every backslash is a bug:
- `BatchFileCreator` emits a Windows `.bat`; backslashes there are required. It now appends the
  separator explicitly (`AppPaths.ConfigFolder + "\\"`) instead of relying on a shared value.
- `MainController`'s `@"\explorer.exe"` / `@"\System32\taskkill.exe"` are Windows process paths
  inside Windows `#if` guards.
- `DirectoryWrapper` deliberately normalises to `\` and splits on it — Windows-specific utility,
  separate decision.

### M20 groundwork — break the framework→App cycle, part 1 (v0.4.0)
Went to add the `.asmdef` files and found the split is **blocked**: `App` depends on the
framework by inheritance while the framework depends on `App` by concrete type. That is a cycle,
and assembly definitions cannot express one. So the asmdef is the last 20 minutes of M20, not the
first — the work is breaking four clusters. Two done here:

- **`ScreenView` → `ScreenViewBase`.** `ScreenControllerBase` held `List<ScreenView>` and a
  `ScreenView _currentScreen` — a base class depending on its own derived type. Now
  `ScreenViewBase` (which already implements `IScreenView`). **Not** `List<IScreenView>`: Unity
  cannot serialize an interface and the field is `[SerializeField]`. Widening the type keeps
  existing scene references valid; verified `Intro.unity` has `screens: []` so nothing was
  authored anyway.
- **`MainController.AppData`/`AppSettings` → `AppDataBase`/`AppSettingsBase`.** No framework
  consumer needed a derived member — everything goes through `AppDataController.AppSettings`
  directly, and the only members used (`languages`, `isMediaType`) are on the base classes.
- Also fixed a latent bug found while in there: `ScreenControllerBase.Awake` appended the
  component scan to `screens` unconditionally, so an Inspector-authored entry that is also a
  child ended up in the list twice. It now adds only what isn't already listed — deliberately
  *not* a `Clear()`, which would have discarded authored entries that are **not** children
  (a screen on a sibling canvas), a case the original append supported.

Deferred deliberately: `ScreenType` (it sits in `IScreenView`, so it needs a string id, a generic
base, or a ScriptableObject key — an API decision every derived project inherits), `MediaVO`
(4 signatures), and `AppDataController`'s construction of the concrete types (wants
`AppDataControllerBase<TData, TSettings>`).

### M24 — Ctrl+Alt+S regression from C4 (v0.4.1)
Tiago reported the config-folder shortcut had stopped working. Caused by my C4 change:
`OpenConfigFolder` handed `AppPaths.PersistentConfig` straight to `explorer.exe`.

`Application.persistentDataPath` returns forward slashes on Windows; `Path.Combine` joins with
backslashes. So the composed value is `C:/Users/.../Product\StreamingAssets\config` — perfectly
valid for `File`/`Directory` (config loading was never affected), but `explorer.exe` **silently
does nothing** when the path contains a forward slash. No exception, so the existing catch never
fired and nothing was logged.

- Added `AppPaths.ForShell()` — normalises separators for shell hand-off. Put on `AppPaths` rather
  than inline, so every future caller routes through it.
- `OpenConfigFolder` now calls `EnsurePersistentConfig()` too: explorer also opens nothing for a
  folder that doesn't exist, which is the normal state on a machine that has never saved a config
  override. The old hand-built path had the same gap.
- `OpenInstallFolder` needed nothing — `Directory.GetParent(...).FullName` is normalised by .NET.

### C7 + H16 — error logging survives every platform (v0.5.0)
`[Conditional]` removes the **call site**, not just the output. With `DO_LOGS` defined only for
Android and Standalone, ~129 `LogError`/`LogException` sites compiled to nothing on iOS, WebGL,
macOS, Linux and UWP. Every fix made this session reported its failures into the void there.

- The 4 `LogError` overloads and `LogException` are now **always compiled**. Verbose `Log`,
  `LogWarning`, `CheckPoint`, `Break`, `TimeActionToLog` stay conditional. Zero call-site edits —
  removing the attribute doesn't change signatures.
- `Log(LogType, …)` stays conditional even though it can emit at Error level: it is named `Log`,
  and callers wanting a guaranteed error should use `LogError`.
- **`Assert` deliberately stays conditional.** All 77 sites pass
  `Core.settings.System.doLogs`; because `[Conditional]` strips the *arguments* too, making it
  unconditional would evaluate that expression on every platform and spread H17's NRE everywhere.
  This is load-bearing, not a style choice.
- **H16 fixed in the same pass** — all four stack-frame properties are null-guarded.
  `GetMethod()` is null for inlined/IL2CPP frames and `DeclaringType` is null for global methods,
  so the logger could throw from inside a `catch` that was reporting the original error.
- Added a null-safe `Describe()` for message rendering and a null check in `LogException`: now
  that these are always compiled, a `LogError(null)` must not throw.
- Added an **ALWAYS COMPILED** banner in `Development.cs` explaining why, so the attribute
  doesn't get "tidied" back on.

**Reviewed with `silent-failure-hunter`, which verified the reasoning empirically rather than
taking it on argument:** 73 of the 77 `Assert` sites pass `Core.settings.<Module>.doLogs` (the other 4 pass a
local field), `Core.settings` does stay null when parsing fails (`Core.cs:88/114/204` all `return`
before assigning), and — the part I had only assumed — **none of the 77 passes `LogType.Error`**. So keeping `Assert` conditional
costs zero error reporting. It also confirmed no new per-frame error path was opened.

It found two stale comments of mine: `MainController.cs` and `AppDataController.cs` both justified
using raw `UnityEngine.Debug.LogError` "because `Development.LogError` is `[Conditional]`" — no
longer true after this commit. Reworded: both stay as `UnityEngine.Debug` deliberately, so those
two catches cannot be silenced by any future change to the wrapper. And it caught that
`Log(LogType, …)` routes `Error` to `Debug.LogError` while staying conditional — dormant (no call
sites) but the banner now warns about it.

**Logged as M26, not fixed here:** the sweep also surfaced ~10 places where a genuine failure is
still reported at Warning level or not at all — worst being `AppDataController.cs:418`, where an
appSettings parse failure goes only to a notification and the app continues on silent defaults.
C7's scope was the logger, not an audit of 151 callers' severity choices; each is a one-line change
and the pattern is the finding.

## Decisions
- **Deleted `configDirectory` rather than deprecating it** → a derived project referencing it
  gets a compile error, which is strictly better than inheriting the silently-wrong value.
- **`CLAUDE.md`'s "framework must not reference App/" was stated as fact; it is not true** →
  corrected to name the cycle, tabulate the four clusters with why each is hard, and say plainly
  not to add new ones. A convention documented as already-holding is worse than no convention:
  the next person writing framework code had no way to know they were deepening a cycle.
- **`List<ScreenViewBase>`, not `List<IScreenView>`** → Unity cannot serialize interfaces, and
  that field is authored in the Inspector. The base class is the framework-side type that both
  removes the App dependency and keeps serialization working.
- **`SaveAppSettings` no longer falls back to StreamingAssets** → writing there fails on most
  platforms; the persistent folder is the only writable location, so create it rather than
  attempt an impossible write.

### M27 + M28 — one version truth (v0.6.0)
Asked to make `AppDescriptor` follow `AppVersionSync`. It was worse than unsynced: the descriptor
kept its **own** version with its own Major/Minor/Patch buttons, and the two had already diverged —
`VERSION.txt` at `0.5.1`, `Descriptor.asset` at `1.0.0`. That field is the one that actually reaches
people: the splash screen (`AppInfo.cs:60`), the analytics payload (`AnaliticsSender.cs:34`,
`Analitics.cs:22`), and the build folder + exe name (`MakeBuild`). So every build shipped stamped
`1.0.0`.

- `AppVersionSync` is now the single propagator: `VERSION.txt` → `bundleVersion` **and**
  `Descriptor.Version`, with `Read()`/`Write()`/`Sync()` so callers don't re-implement the file I/O.
- `AppDescriptor`'s Version field is **read-only** with a HelpBox pointing at `VERSION.txt`. The
  bump buttons now call `AppVersionSync.Write()`, and Build bumps first so the version it stamps is
  the version it persisted (it previously incremented `_build`, built, *then* wrote the asset).
- **M28, found on the way — and I got it wrong first.** Four editor files loaded the descriptor
  with a backslash AssetDatabase path. I logged it as destructive (load returns null, next branch
  `CreateAsset`s over the asset). `code-reviewer` disproved the premise with better evidence than I
  had: the descriptor's non-default `Slug`/`Client`/`Year` are intact, and
  `DesignScalerEditor.OnEnable` runs that same load-then-create on *every* selection — so the
  backslash form does resolve on Windows. The real issues are that it is undocumented and not
  portable off Windows, and that three **read-only** consumers carried a destructive `CreateAsset`
  fallback. All four now share `AppVersionSync.DescriptorPath`; only `AppDescriptor` may create.

**Review round on this change caught one thing that would have defeated the whole point:** the
bump buttons derived their base from `_data.Version` (the descriptor), not `VERSION.txt`. If
`Sync()` hadn't run or had bailed, pressing "Patch Update" would push the descriptor's stale version
*back into* `VERSION.txt` — truth flowing backwards, re-creating the exact drift M27 fixes. Now
parses `AppVersionSync.Read()` and hides the controls entirely when it returns null. Also from that
round: sync a freshly-created descriptor (it carries the class default `1.0.0`), ask for the build
folder *before* bumping so cancelling leaves no phantom version, catch
`UnauthorizedAccessException` (not an `IOException`, so a read-only `VERSION.txt` would have escaped
out of `delayCall`), and drop a redundant `Save()` that cost a full `AssetDatabase.Refresh` per click.

### C2 — the destructive one (v0.7.0)
Asset cleanup recursively deleted every file under a computed root that wasn't in `mediaAssets`.
Resolved against the shipped config before touching it: `localSettings.assetsPath` is `"assets/"`,
so today the root is `StreamingAssets/assets/` — scoped. Set that field to `""`, a plausible thing
to do for a project whose media sits at the root, and the root becomes **all of StreamingAssets**,
including `config/settings.json` and `appData.json`.

Four independent failure modes, all fixed:
- **Root collapse** → `IsSafeCleanupRoot` refuses an empty/missing root, and refuses any root that
  *is* streamingAssets or persistentData rather than a subfolder of one.
- **Case-sensitive compare** → the keep-check was ordinal `==` on raw strings, so `Baboon.BMP` on a
  case-insensitive Windows filesystem didn't match `baboon.bmp` in appData and was deleted. Now a
  `Path.GetFullPath` + `OrdinalIgnoreCase` `HashSet`.
- **Unguarded `File.Delete`** → one locked file threw, killed the coroutine, and
  `onAssetCleaningCompleteEvent` never fired, hanging boot on the same run that had already
  half-deleted the media. Now per-file `try/catch`, and *every* exit path fires the event.
- **Shared switch** → cleanup rode on `AssetDownload.isActive`. Now its own
  `cleanUnlistedAssets`, default false and present in `settings.json` so it's discoverable.

Also `GetFiles` instead of `GetFileSystemEntries` (the latter returns directories), and O(n) lookups
instead of O(n·m) with a `Regex` per comparison — 1000 files × 500 assets was 500k regex runs.

**Deliberately still gated:** the keep-list comes from the properties-only reflection walk (M3/M4),
so an asset referenced by a *field* never enters it and would be deleted. Canonical comparison can't
fix that. Noted on both C2 and the flag's XML doc; the flag stays off until M4 lands.

**Security review round on C2 — the guard I wrote was on the wrong side.** My root guard was
correct and defeated every escape I was asked about (`..`, `""`, `"/"`, `"assets/../"`, absolute
paths, URL roots, sibling-prefix folders all refuse properly). But the remaining hole was the
**keep-set**, and three ways to empty it that the guard happily deletes against:

- `GetAssetPath` is `string.Concat(assetsPath, value)` with **no separator**. Set
  `localSettings.assetsPath` to `"assets"` instead of `"assets/"` — an easy thing to do — and every
  keep entry becomes `.../StreamingAssets/assetsvideo.mp4`. Zero matches, root guard passes, whole
  folder deleted.
- `GetAssetPath` returns **rooted** values as-is, so a CMS emitting `/video.mp4` produces a keep
  entry of `C:\video.mp4` while the real file sits under the root, unreferenced. It deletes exactly
  the files it names.
- The `mediaPaths` allowlist (default `["url","thumb"]`) is operator-editable, and the reflection
  walk is properties-only (M3/M4) — both silently shrink the keep-list.

The fix is one invariant, and it closes all three plus the M3/M4 case: **refuse cleanup unless at
least one keep entry resolves under the enumeration root.** Every systematic keep-set failure
presents identically as "nothing resolved here", and that is never a legitimate empty cache. Added
alongside: keep entries composed with `Path.Combine` against the root rather than via
`GetAssetPath`; a 50%-of-folder blast-radius cap; **persistentDataPath only** (StreamingAssets media
is shipped and not re-downloadable, so deleting there is never a cache operation); refuse reparse
points, since `GetFullPath` doesn't resolve junctions but `GetFiles` follows them; and refuse in the
editor, where the root is project source.

One review claim I did **not** accept: it reported the old cleanup as live rather than dormant.
`SetupAssetManager()` is the only caller of `ValidateAssets()` and it sits in the `else` of
`if (!AssetDownload.isActive)`, so with the shipped `false` the AssetManager never ran at all. C2
was dormant, as originally logged.

I also used `Application.isEditor` rather than `#if UNITY_EDITOR` for the editor refusal: an `#if`
with an `#else` would leave the player-only checks uncompiled in the editor, so a mistake in the
most dangerous code in this file would only surface on a player build — and an editor compile is the
only verification available here.

### M4 — one media walker, and it reads fields (v0.8.0)
Tiago hit this live: loading a real `appData.json` left `AssetManager.cs:371`
(`data.GetType().GetProperties()`) returning **0**, so nothing was ever queued.

Diagnosis, in two layers. The immediate cause is that `AssetSorting` reflected over
`GetProperties()` only, and `AppData : AppDataBase` declares no properties at all — `languages` is a
**field**. So the enumeration was empty and the walk terminated on entry. Under that sat a second
cause: `AppData` was still the empty template class, so `ToObject<AppData>()` deserialized the whole
`data` object into a type with no members and discarded it. Tiago wrote the content model
(`menus` / `MenuVO` / `MediaLibraryVO`) — with fields, per the convention — which is exactly the
shape the old walk could not see.

- New `Data/MediaWalker.cs`, one implementation replacing two drifted copies (~7k chars of near
  duplicate). Covers **fields and properties**.
- Reference-identity visited-set: a back-reference used to recurse to `StackOverflowException`,
  which .NET cannot catch. Depth cap as a backstop.
- Per-type member cache; one `GetValue` per member (was up to three, plus a redundant
  `GetProperty` re-lookup); a throwing getter is logged and skipped rather than aborting the walk —
  a truncated media list means missing downloads, and for the cleanup path, deleted files.
- Iterates `IEnumerable` rather than casting to `IList`, which threw on any other collection type.
- The image-extension filter stays at `TextureCacheManager.AddMediaAsset` — that was the one real
  difference between the two copies, so it belongs at the call site, not in the shared walker.

This also **clears C2's blocker**: the keep-list now sees field-referenced assets, so
`cleanUnlistedAssets` is defensible to enable (L12 updated). And it narrows M3 — properties are no
longer *required* for an asset to be found, so the VOs can standardise on fields.

### M29 — my own C2 guards blocked the real workflow (v0.8.1)
Tiago downloaded one appData's assets, switched to a different appData, and nothing was pruned. The
log told the whole story, in order: `cleanup disabled` ×4, then `skipped in the editor`, then
`REFUSED: not under persistentDataPath`, then `REFUSED: would delete 225 of 434, over the 50% safety
limit`. He had already commented both guards out of the source to get any work done — which is the
clearest possible signal that a guard is wrong.

Both were mine, and both were badly designed:

- **The 50% blast cap cannot tell a legitimate content swap from a broken keep-set.** Point the app
  at a different appData and *every* previous file is correctly unreferenced. By volume that is
  identical to the catastrophic case the cap exists to stop. Replaced with **corroboration**:
  cleanup runs after the download phase, so the assets appData names should be on disk. If ≥50% of
  the keep-list is present, the list is real and deleting the remainder is correct at any volume;
  if none is present, the list does not describe this folder and it refuses. That is the property
  that actually separates the two cases — volume never was.
- **The `Application.isEditor` refusal ran before the persistentDataPath check**, so cleanup never
  ran in the editor at all. persistentDataPath-only already guarantees the thing that guard was
  for, so it is deleted rather than reordered.

Also: **emptied folders are now removed** (deepest-first, root always kept). 42 empty directories
survived the file pass, which reads as "cleanup did nothing" even when 225 files had gone.

Verified by simulation against the real cache before committing: 3 referenced assets, 209 files,
corroboration 3/3 once downloaded → proceeds, deletes 209, removes ~42 folders; with the host down
→ 0/3 → refuses.

### M30 — a different content set must still prune the cache (v0.8.2)
Tiago, correctly: *"if it is a different model it still should run the file cleanup, because the new
model doesn't use the old model files."* It didn't, because `OnAssetsSorted` returned early whenever
the walk found nothing — behind the `// TODO: not the best procedure, files might need cleaning`
comment that had been sitting there admitting exactly this.

The trap is that an empty keep-list has **two opposite meanings**:

| | meaning | correct action |
|---|---|---|
| appData declares no media | every cached file is stale | delete them all |
| the model can't see the media it declares | we don't know what's needed | refuse |

Both look identical from inside the walk. The discriminator is the **raw JSON text**:
`AppDataController.RawMediaValueCount` counts `"url"/"thumb"` values before deserialization, so it
reports what the payload contains independently of the model that is in doubt.

- Empty walk now calls `ValidateExistingMedia()` instead of returning.
- Declares 0, collected 0 → deletes the whole cache. This is the case Tiago asked for.
- Declares N>0, collected 0 → refuses, naming the model mismatch. Deleting there would also bin the
  files the *new* content needs, and the same blindness prevents re-downloading them, so the app
  goes from "stale content" to "no content".
- Corroboration treats an empty keep-list as satisfied, since it was already vetted above.

His actual run falls in the second bucket: the JSON declares 4 media values, the walk collected 0,
because the model has `menus` while the payload has `items`/`ctaMedia`. So it still refuses — but
now it says why, instead of silently doing nothing. One model change away from working.

### M31 — safeguard removed by decision (v0.8.3)
Tiago overrode the v0.8.2 refusal, twice and explicitly: *"if the appdata is different the old files
aren't needed."* His call, and it is a reasonable one — this is a download cache, so over-deleting
normally costs bandwidth rather than data.

The concern I raised and he overruled, recorded so the trade-off is visible rather than lost: in the
model-mismatch case the same blindness that emptied the keep-list also stops the *new* assets being
queued, so clearing the cache takes the app from "stale files on disk, harmless" to "no media and no
way to fetch any" until the model is fixed. On an unattended kiosk that is a visible outage.

Implemented: the empty keep-list always prunes. The diagnostic survives — the model-mismatch case
still logs at **error** level with `CLEARING THE CACHE ANYWAY`, so the cause remains visible in the
log even though it no longer blocks. Root-safety refusals are untouched: they bound *where* it
deletes, not how much, and were not part of the objection.

Logged as M31 with status **by design**, so a future reader does not "fix" it back.

### H17 - the recovery hotkey threw in the failure it recovers from (v0.8.8)

Worklist item #1 after M26. `Update` is a Unity message, so it runs whether or not the boot chain
ever completed - which is what made this live. With `Core.settings` null, the very first statement
in the Ctrl+Alt+S branch was `Assert(Core.settings.System.doLogs, …)`, and because `DO_LOGS` *is*
defined for Standalone (`ProjectSettings.asset:772`, the only platform the block compiles for) the
argument was evaluated and threw before `OpenConfigFolder` was reached.

Two changes. The three shortcut breadcrumbs are now plain ungated `Development.Log` calls: an
operator reaching for a recovery hotkey is precisely what you want in the log of a machine whose
startup already failed, and `doLogs` is unreachable in that state, so gating it bought nothing and
cost the deref. `killExplorer` reads through a `KillExplorerRequested` property that is
null-conditional along the **whole** chain, not just at the root - a partially parsed settings.json
can leave `System` or `Windows` null while `Core.settings` itself is fine. It defaults to false,
which is safe in both directions: not killing the shell is the non-destructive choice, and
`OnDestroy` only restores explorer if it believes it killed it.

**Found past the register's scope.** The same deref sits in `MainController.Awake` on the Android
permission path, and it is worse placed - `Awake` ordering between components is undefined, so
`Core.settings` is likely still null when it runs, and `DO_LOGS` is defined for Android too. Fixed
identically. Unverified on device; Android is not an exercised target.

**Checked and deliberately left alone.** The register also cites `:300` and `:333`; both are inside
`Init`/`OnDestroy`, which are gated on `Core.IsSet`, so guarding them would imply a risk that does

### H10 - the download path, reviewed before applying (v0.8.9)

First fix of the session put through the review agents *before* being applied rather than after, at
Tiago's request. That changed the outcome twice, so it is worth recording how.

**What H10 actually was.** Four defects that all ended in the same place. `ValidateAndDownloadMedia_IE`
increments `chunkValidated` as its **last** statement, and `OnAssetsSorted_IE` waits on that counter -
so any exception inside the coroutine kills the chunk, the `WaitUntil` never completes, and the app
sits on the preloader forever with nothing surfaced. C3's shape, reached four different ways: an
undisposed `DownloadHandlerFile` holding the file open across `File.Delete`; `DateTime.Parse` of an
RFC1123 header under `CurrentCulture` (throws on pt-PT, the deployment locale) and on a null header;
`(10 * count) / 100`; and an unguarded `File.Delete`.

**`code-reviewer` caught that one of my four fixes was a no-op.** I had replaced
`(10 * count) / 100` with `Math.Max(1, count / 10)`. But `(10*c)/100` **is** `c/10` for every
non-negative c, so the only case that changed was c < 10, where the limit moved 0 → 1 - and since the
test runs *after* `filesFailedToDownload++` the counter is already ≥ 1, so `>= 0` and `>= 1` both fire
on the first failure. Identical behaviour, with a comment claiming it was fixed. Verified the algebra
against a table of counts before accepting it. Now floored at **3 absolute failures**: one or two
missing files is ordinary CMS drift; three-plus alongside a failed remote appData means the host is
down.

**`silent-failure-hunter` found three more instances of the exact bug I was fixing.**
`GetAssetPath` → `Path.IsPathRooted` throws `ArgumentException` on a CMS value containing invalid path
characters, and sat outside every guard. `Directory.CreateDirectory` and the `DownloadHandlerFile`
constructor were likewise unguarded. Each one escapes the coroutine and hangs the boot chain - so a
fix aimed at exactly that failure mode would have shipped with three fresh copies of it. All guarded
now; note C# forbids `yield` inside a `try` with a `catch`, so the loop body cannot be wrapped as a
whole and each throwing call needs its own guard.

It also found the 0-byte trap: if the delete fails, the partial file's mtime is *now* - newer than any
remote timestamp - so the retry's freshness check skipped it as "available and updated" and shipped an
empty asset silently. The skip now requires `length > 0`.

**Two dormant ones, both one-liners.** `filesFailedToDownload` was the only one of four counters
`OnAssetsSorted_IE` never reset, so a second `ValidateAssets()` would start poisoned. And the
`WaitUntil` compared `chunkValidated == divUrls.Count`, which a late increment from a previous run
would overshoot permanently; `>=` now.

**Logged rather than fixed** (M34-M37), because they are not H10 and two of them want a different
change: a dead asset host or a fresh install can never trip the cancel threshold at all, so the app
can sit on the preloader for hours - that wants a wall-clock cap, which is C3's watchdog, not this;
`DownloadHandlerFile` truncates an existing good file at construction, so a failed refresh destroys
working media, which wants `.part` + rename; `onAssetDownloadEvent` has no subscriber; and skipped
URLs bypass the progress event so a clean run ends showing "48/50".

**Decisions.** Unknown freshness re-downloads rather than skips - a stale asset on an unattended kiosk
costs more than one wasted transfer. The lenient second parse attempt exists because strict `"r"`
would make a proxy-rewritten header re-download everything on every boot, forever. Per-asset detail
stays at `Assert`/`LogWarning`, but the chunk now ends with **one Error-level summary** of how many
assets will be missing at runtime, since both of those vanish without `DO_LOGS`.

**Verified:** braces balanced; no `yield` inside a `try` with a `catch` (CS1626) by parsing the file;
both `yield break` paths still increment the counter; `DateTime.Parse`, `GetLastWriteTime(` and the old
threshold expression all gone. **Not verified:** compile, and none of this runs on a healthy network -
by construction these are all failure paths, which is exactly why they survived testing.

## Gotchas hit
- **`[Conditional]` strips arguments, which makes it load-bearing in unexpected places.** It is
  why `Assert` cannot be made unconditional: 73 of 77 sites dereference `Core.settings` in the argument
  expression, and the attribute is currently the only thing preventing an NRE on platforms where
  settings parsing failed. Fixing C7 naively would have converted a silent-logging bug into a
  crash-on-boot bug.
- **A clean compile proved less than I implied.** I confirmed C4 compiled — twice, from
  `Editor.log` — and treated that as the change being sound, while flagging runtime verification
  as merely "outstanding". The Ctrl+Alt+S regression compiled perfectly and failed silently at
  runtime, which is exactly the class of defect this codebase is full of. For a change to a
  shell/filesystem boundary, "it compiles" is close to no evidence at all; the check had to be
  pressing the shortcut.
- **`Path.Combine` output is not shell-safe on Windows.** Mixed separators are valid for .NET file
  APIs and rejected — silently — by `explorer.exe`. Any path leaving for a shell needs
  `AppPaths.ForShell()`.
- **Shell-heredoc escaping put an invalid escape sequence into C# source.** Writing
  `"%userprofile%\AppData..."` through a Python heredoc collapsed to a single backslash, i.e.
  C# `\A` — a CS1009 compile error. Caught by writing a scanner to a *file* rather than another
  heredoc. For multi-level escaping, use the Edit tool (no escaping layer) or a script file.
- **Multi-line string matching fails on CRLF files.** These sources are CRLF in the working
  tree, so `
`-joined needles never match. Line-based edits are the reliable approach here.
- **The previous round did compile clean.** `Editor.log` shows 0 `error CS` entries for the
  C1/C8/M22/H3/H4/M23 commits — the first real compile evidence this project's fixes have had.

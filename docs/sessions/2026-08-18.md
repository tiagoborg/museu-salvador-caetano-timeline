## M46 write-side + M116 — a save nothing read, and a null nothing reported (v0.50.1)

`SaveAppSettings` always writes to the persistent config folder; the read goes through
`AppPaths.Config`, which returns the **shipped** copy unless `UsesDeployedConfig`. Where those
disagree — the editor without `DEBUG_MODE`, and WebGL — a branched project's settings panel appeared

**`LogError` is load-bearing, not a style preference, and I measured it rather than asserting it.**

heap: my `LogError` literal is present, and `AppPaths.Config`'s existing
`Development.Log("Ignoring the deployed…")` is **absent**. That last result is the interesting one —
it means on WebGL there was previously no report at *either* end, which is worse than the register
described. The first version of this test kept `DO_LOGS` in the define set and proved nothing; a
build that still defines the symbol cannot demonstrate what stripping it does.

### Why the namespaced `RangedExtensions` is the right survivor, despite L17

L17's convention says an extension holder belongs in the **global** namespace, because an extension
method is only in scope where its namespace is — so on the face of it I kept the wrong one. It holds
here for a specific reason: `RangedExtensions` extends `RangedFloat` and `RangedInt`, which are
themselves in `EnigmaVirtual`. Any code that has a value to call `.LerpFromRange()` on already needs the
import to name the type, so the extension comes with it. The convention protects `someString.Bold()`,
where the receiver is a BCL type and the import would otherwise be invisible; that is not this case.

## M44 — one guarding style, and the stated reason was wrong (v0.52.1)

Seven sites in `Api.cs` dereference `Core.settings.Api.doLogs` unguarded; one used
`Core.settings?.Api?.timeout ?? 0`, with a comment calling the null-conditionals "load-bearing".

**The comment's reasoning did not survive reading it.** It said the `LogIf` above is stripped without
`DO_LOGS`, so this line becomes the first dereference — true, but on the platforms where `DO_LOGS` *is*
defined the `LogIf` dereferences first anyway. So the guard only ever covered iOS and WebGL.

**What actually decides the direction is an invariant, and I measured it rather than assuming it.**
`Init()` runs only from `CoreSetupComplete()` after a successful parse; `SetupApiController()` is called
from `Init()`; no type in the Api hierarchy declares a Unity message, so nothing runs at scene load; and
no `ApiController` is authored in any scene, so there is no instance before `Init()`. The last two are
the ones worth checking, because `SetupApiController` *adopts* an authored instance if it finds one —
that is how M76's dual-AssetManager defect worked — and a MonoBehaviour's `Awake` runs at scene load,
before any parse. Neither applies here.

So both styles were safe, and the mix was the whole defect. Unified on the unguarded one with the
invariant stated once, in the place that used to imply it was doubtful. **Dormant either way**:

## L26 fixed, and the register's own prescription was the wrong fix (v0.54.2)

`Assembly-CSharp-Editor` named three `App/` types, so any branch renaming one lost the whole editor
assembly - `BuildValidator` and `AppVersionSync` included - with no framework csproj reporting it.

**The entry prescribed moving the files to `App/Editor/`. That would not have worked, and it is worth
knowing why before anyone tries it again.** A folder covered by an `.asmdef` gets no `Editor/`
special-casing, so `App/Editor/` needs an asmdef of its own; and **an asmdef assembly can never
reference a predefined assembly** like `Assembly-CSharp-Editor`, so the moved menu items could not
have called `GemaMenuItems`' private panel builders. Most of a 280-line file would have had to move
with two menu items. I wrote that prescription this afternoon from a structural reading, without
checking what the types were.

**What they are made the fix small.** All three are trivial subclasses of *abstract* framework bases,
so the inspectors target the base with `editorForChildClasses` - the idiom
`AppDataControllerEditor.cs:9` was already using. The two menu items need a *concrete* type, which a
base cannot supply, so they ask `UnityEditor.TypeCache.GetTypesDerivedFrom<T>()`. Four files, no new
assembly, no `.meta` moves, and it covers a branch that renamed its subclass - which the file move
would **not** have done, since the moved code would still have named `ScreenController`.

**Read the types before designing the move.** The whole difference between a one-session refactor and
a four-file edit was one question - "what do these three types actually derive from?" - that the
structural pass never asked, because at the layer it was looking, `App.ScreenController` and
`EnigmaVirtual.ScreenControllerBase` are just two nodes with an edge.

**Only `Assembly-CSharp-Editor` caught the compile break, exactly as the entry claims.** The bases are
in `EnigmaVirtual.Screens` and `EnigmaVirtual.Components.Video`; the App types were **global**, which
is why the old files needed no `using`. Retargeting produced six `CS0246`s that `EnigmaVirtual`, `App`
and `Assembly-CSharp` all reported as `0 Error(s)`. The entry demonstrated itself while being fixed.

**Both reviewers independently found the same defect in my fix, from opposite questions.** Adding a
guard part-way through `CreateScreenControllerCanvasGO` meant that when the second lookup failed, a
fully-built canvas was left unparented in the scene with `Undo.RegisterCreatedObjectUndo` never
reached - so it could not even be undone. The original code could not reach that state, because the
types were statically guaranteed. **A guard inserted mid-construction converts a compile error into a
half-built object.** Fixed by doing both lookups before the first side effect, not by destroying the
wreckage afterwards.

**And I wrote a mitigation into a doc comment without implementing it.** The remark said an ambiguous
subclass pick was acceptable because "the caller names what it added in the Undo entry" - it does
not; both Undo labels are `"Create " + go.name`. That clause was load-bearing: it was the *reason*
the arbitrary first match was defensible. So the fix was to make the code true rather than to delete
the sentence - `ConcreteSubclassOf` now counts candidates and reports at `LogError` when there is
more than one. **A comment justifying a shortcut is a promise; keep it or drop the shortcut.**

**One thing deliberately not fixed, and named so it is not mistaken for an oversight.**
`GemaMenuItems` still instantiates `Prefabs/TextPanel` and `Prefabs/ImageGalleryPanel`, whose prefabs

words so that "the editor assembly is framework-only" is never inferred from this fix.

### A method note worth keeping

**The dll byte-search cannot distinguish a declaration from a reference, and I nearly used it as the
proof.** A type name lands in the metadata `#Strings` heap either way, and `AssetList.cs` touches

reference *within* one heap, which no byte search can separate. The L22 pair-assertion rule still

## Decisions and defaults (not user requirements)
Defaults set by root as routine choices, recorded so nobody mistakes them for client decisions:
- Card widths default to 260 / 380 reference px, both cards share one fixed height, and the font
  shrinks in steps down to a minimum.
- All categories off is allowed and collapses every decade.
- Home with one category starts with only that one on; "Todas" starts with all on.
- The Timeline's back button goes to Home.
- The top-right arrows are a decorative hint, not a button.
- Any filter change resets the timeline to its start.
- The closing boundary is labelled with the next decade and has no strip of its own.
- One dot stays for a single-image gallery; zero images shows no dots.
- Identical image URLs are kept once in a gallery, so a shared placeholder path doesn't produce
  duplicate slides.
- Each card opens on its own first image and keeps its own gallery position.
- The footer is small as in the design, with enlarged invisible touch areas.

Implementation decisions:
- **UI content built in code, not prefabs.** The worker had no editor and a collaborator was editing
  `Intro.unity` live, so hand-written prefab or scene YAML was the riskiest option. The scene keeps
  its authored objects (screen component, CanvasGroup, background, Home's chrome and back button).
- **Scene wiring through an editor utility, not YAML edits.** It is idempotent, never deletes
  anything, and fills only empty references. It finds the App types through `TypeCache`, because
  `Assets/Editor/` must not name App types.
- **Textures from the existing `TextureCacheManager`, not `DownloadableImage`.** `DownloadableImage`
  refuses a second `Load` while one is in flight and fades every load, which is wrong for swiping
  between cached slides.
- **Swipe claims the drag only with ≥2 slides.** With fewer, the swipe component is disabled and
  drags on the image pan the timeline.
- **Circles generated at runtime.** No circle sprite ships with the project. `TimelineScreenview`
  creates and destroys them.
- **Scroll hint drawn from two copies of the existing arrow sprite.** A TMP `↔` was rejected because
  Montserrat's glyph coverage is unknown.
- **Home up-right arrow kept at z = -135°.** Positive z is counter-clockwise in UI space, so a
  left-pointing arrow (180°) turned -135° points at 45°, which is up-right.
- **`TimelineItemVO.id` hides `ItemBaseVO.id` and was left alone.** It is a compiler warning only,
  and all 30 events deserialized in Play.
- **`LogError` for hidden events, overflow and out-of-range years.** Without a detail view nothing
  else witnesses them, and `LogWarning` is stripped on iOS/WebGL. Each is reported once, not on every
  relayout.
- **Years limited to 1920–9999.** A JSON year of 10000000 would have created about a million decade
  boundaries on the main thread.
- **Timeline back-button frame drawn as four 1 px edges.** The sliced `Rectangle 45@2x` did not
  render on that runtime-built Image, though the root probe showed geometry, alpha, culling and
  canvas mode were all correct. Magenta with no sprite made both frame and arrow appear. The
  mechanism is still unknown; the workaround is verified visually.
- **`AssetDownload.isActive: false` for this client.** In the final Play run, `AssetManager` tried
  a remote refresh of `placeholder.png`/`placeholder2.jpg` with no host configured, because the
  template ships the flag `true`. Card images load from `StreamingAssets/assets/` through
  `TextureCacheManager`, which that flag does not gate, so nothing depends on the download stage
  here. Only the shipped config changed; no framework code, remote URL or LocalLow file was touched.
- **Performance ceiling recorded, not fixed.** See `reviews.md`. The reviewer's 300-event figures are
  a projection; the shipped content is 30 events and two images.

## Follow-up: category tag sized to its name (user request, sizing verified)
- **Changed:** `App/Timeline/TimelineCard.cs` only.
  - New `SetTag(label)`, called from `Bind` in place of the plain text assignment. It measures the
    upper-cased name with `_tagText.GetPreferredValues(label).x`, at `tagFontSize` with auto-size
    off.
  - It clamps that width to `[tagWidth, 0.9 × card width]` and writes it to the Tag rect's
    `sizeDelta.x`. The height and the top-left anchor are unchanged.
  - When the measured width exceeds the maximum, TMP auto-sizing is enabled between
    `fontSizeMin = 1` and `fontSizeMax = tagFontSize`.
  - New fields: `_width` and `_tagRect`, set in `Build`. New `const MaxTagWidthFraction = 0.9f`.
    `tagWidth`'s tooltip now says it is the minimum.
- **Why:** names like "RESPONSABILIDADE SOCIAL" could be cut at the fixed 160 px.
  - `GetPreferredValues` was checked in the package source: `TMP_Text.cs:4836–4837` adds the left and
    right margins to the result, and character spacing is applied in the same layout pass. So
    nothing is added by hand. If anything the measurement errs wide, which is the safe direction.
  - A language change rebuilds every card, so `Bind` runs again and the tag re-measures in the new
    language without another hook.
  - The 0.9 factor is a constant, not an Inspector field, because the user specified it and no
    tuning was asked for.
  - The 1 pt minimum lets TMP find the largest size that fits. The supplied names are not expected
    to need shrinking at all (see step 2), so this is a safety net, not a design size.
- **Not changed:** the tag's black fill and top frame (the frame stretches with the rect), the card
  body, the photo geometry, swipe and dots.

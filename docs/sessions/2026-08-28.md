## Decisions
- **Fix the spacers, not just the arithmetic** → correcting `*` to `/` alone still leaves the
  toolbar's 1168.7-unit minimum above the 1096.8 available, so the window would keep auto-expanding
  off-screen. Both causes had to go.
- **`FlexibleSpace` rather than a smaller fixed `Space`** → a smaller constant would fit *this*
  resolution and silently re-break on a narrower one. Flexible spacing has no resolution
  assumption baked in, and it distributes evenly, which is what the fixed 50s were imitating.
- **No `overview.md` 5b breaking-change row** → nothing forces a branch owner to act. Note the
  reason I first wrote for this was wrong: I argued from `scaleFactor == 1`, where the old and new
  formulas are identical — but the field ships at `.95f` and is inspector-authored, so every branch
  *does* get different geometry (window ~68 px wider, controls spread rather than clustered left).
  The conclusion still holds, on the honest ground that no one can reasonably depend on the pixel
  geometry of a debug overlay. Caught by `doc-reviewer`.
- **`com.unity.pipeline` stays in the manifest** (user's call) despite being 9.55 MB of the build →
  it is the only thing making the editor drivable, and build size is not the binding constraint on
  a kiosk install.

## Drag-to-scroll on the log list (v0.56.0) — TESTED

Press and drag anywhere on the list to scroll it. `HandleDragScroll` runs at the top of
`DrawLogList`, hit-tests against the previous frame's scroll-view rect, excludes the scrollbar band
so IMGUI keeps handling thumb drags, and measures from where the press started rather than
accumulating per event. Tail-following is suppressed while a drag is in progress. `MouseDown` is
deliberately not consumed so the toolbar still works.

**The handler takes the `Event` rather than reading `Event.current`** — the `RFIDReader.HandleKeyEvent`
pattern. That was not tidiness: `simulate_pointer` is unavailable here (it needs
`ENABLE_INPUT_SYSTEM`, and this project is legacy Input Manager), so without the split there is no
route to test the logic at all.

### Verified

**Logic, 11 of 11** — handler invoked directly with constructed `Event`s: press inside starts a drag;
drag down 200 → scrollY 1500→1300; drag to +300 → 1200, proving it measures from the press rather
than accumulating; drag up → 1650; release ends it; a second drag resumes from where the first
ended. Counter-tests: a press on the scrollbar band, a right-button press, a press above the list,
and a drag with no prior press are all ignored.

**Integration, real OS mouse** (`SetCursorPos` + `mouse_event`), because the unit test cannot prove
IMGUI delivers the events or that `mousePosition` shares a space with `_lastOuterRect`:

| check | result |
|---|---|
| drag down 200 editor px | scrollY 1500 → **1067.2** (Δ432.8; predicted 429.6 from `200 / 0.49 / 0.95`) |
| drag up 200 px | 1067.2 → **1500.0**, symmetric and reversible |
| drag the scrollbar thumb | `_isDragging` **False** throughout, scrollY still moved 1500 → 2665.6 — IMGUI kept it |
| click `Collapse` on the toolbar | `isCollapsed` False → **True**, so `MouseDown` is not being swallowed |
| follow after dragging | entries 205 → 208 while pinned, `_isDragging` not stuck |
| Unity console | zero errors, zero `Mismatched LayoutGroup` |

Two scale factors matter when predicting where a click lands: the editor Game view zoom (0.49) and
`GUI.matrix` (0.95). Getting within 1% of the prediction is what confirms the coordinate space.

**Not tested:** the title-bar `GUI.DragWindow`, and touch on a real device. **Known limit:**
`GUIUtility.hotControl` is not taken, so a drag continuing outside the window may stop receiving
`MouseDrag` — harmless for a near-fullscreen console, would matter for a small floating one.

## Gotchas hit
- **`Mathf.Approximately` is a relative epsilon, so it is useless for pixel geometry.** At a content
  height of ~6000 it demands agreement to 0.006 px. Any "are these two layout numbers equal" test
  wants an explicit tolerance in the unit you care about — here one row.
- **`outerScrollRect` is not the viewport.** It includes a border the visible area does not, so
  `innerHeight - outerHeight` is not the maximum scroll offset — it lands about a row short. Only
  `BeginScrollView` knows the real clamp, which is why passing it `int.MaxValue` and letting it clamp
  is correct rather than lazy. I "tidied" this into a computed offset and had to measure my way back.
- **`dotnet build` does not write `Library/ScriptAssemblies`.** A reflection probe reported the
  `Log` struct as having no `countText` field, which reads exactly like the edit not landing. It had
  landed — `eval` was running against Unity's stale assembly, because only a Unity recompile updates
  the one the editor has loaded. Recompile in Unity and grep the dll for a member your edit
  introduces before trusting any reflection probe.
- **`GUILayout.Window` silently grows past the rect you give it.** It sizes to the larger of that
  rect and the content's minimum, so a row that cannot shrink moves the window off-screen instead
  of clipping or wrapping. A `Rect` passed to it is a *minimum*, not a bound.
- **`GUI.matrix` scaling inverts the arithmetic.** With `Matrix4x4.Scale(s)`, spanning the screen
  needs `Screen.width / s` GUI units. `* s` reads correct and is the opposite. Here it cancelled
  against the other bug well enough to look like one vague problem.
- **The pipeline's `build` command does not set `BuildOptions.Development`**, so `BuildValidator`
  validates it as a *release* build and refuses on H14/L12 — even with
  `EditorUserBuildSettings.developmentBuild == true`, which is a different flag from the one the
  validator reads. Pass `options: ["Development","DetailedBuildReport"]`.
- **A probe that sets state and reads the result of that state in one `eval` reads zeros.**
  Setting `isVisible = true` and reading `newWindowRect` in the same call returned
  `(0,0,0,0)` — no OnGUI pass had run in between. Two calls, not one, whenever the value you want
  is produced by a Unity message rather than by the setter.
- **A byte search could not prove this fix landed.** `FlexibleSpace` was already referenced by
  `UIKeyboard.cs:623`, so it is in `EnigmaVirtual.dll` either way. The runtime measurement was the
  only proof — the same trap L27 hit with `UIGeneratorModel`.

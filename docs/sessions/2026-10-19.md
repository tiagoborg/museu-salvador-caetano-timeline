## Image type check before loading (v0.56.5)

**Focus:** never request a url that is not an image the loader can decode.

**Changed:** `TimelineLayout.IsImageUrl(url)` wraps `MediaFile.isValidImageFileType` (the user named
it): false for null/empty, which that method throws on, and false when `Path.GetExtension` throws on
illegal path characters, so CMS content can never abort a rebuild. `Gallery` keeps only urls that pass,
so a rejected url gets no slide, no dot and no request. `TimelineScreenview.ReportHiddenEvents` logs
each rejected non-empty url once per screen lifetime at `LogError`.

**Decisions:**
- Filter where the gallery is built, not in the card or the texture cache → one place every load
  passes through, and the indicator count stays honest (a rejected url would otherwise be a dot that
  never shows anything).
- Pass the url, not `url.GetFileType()` → the helper extracts the extension itself (CLAUDE.md gotcha).
- Query-string urls (`x.jpg?v=2`) are rejected by the shared helper. Not worked around: the live CMS
  sends none, and changing `MediaFile` is a framework change for every branch. Documented in overview.

**Verification:** four `dotnet build`s `0 Error(s)`. The editor had been closed, so the self-check ran
in batch mode (`Unity.exe -batchmode -nographics -quit -executeMethod
TimelineLayoutSelfCheck.RunFromMenu`): `TimelineLayout self-check PASS (49 checks)`; the 2 new checks
reject mp4/pdf/extension-less/webp/gif and a url with `<|>"` (no throw), and keep an accented,
spaced `.JPG` CMS-style url plus `.jpeg`/`.png` (counter-test). `TimelineCard.SelfCheck` not re-run
(card untouched). **Not run:** the `LogError` report and play mode on live data - the live data has
only `.jpg`, so no rejection would show there anyway.

**Test plan:** 1) *Gema > Timeline > Run Layout Self-Check* → Console `PASS (49 checks)`.
2) In a copy of the appData, set one event's image url to `foo.mp4`; Play, open the timeline: Console
shows `Timeline: event N (year) lists "foo.mp4", which is not a supported image type`, that card shows
no photo or dots, and no download/load error for `foo.mp4` appears. Counter-test: every `.jpg` card
still shows its photo.

**Font assets:** the three Montserrat SDF assets were modified again by the editor/batch run
(dynamic glyphs); committed with this change at the user's request.

## Client failure: it is a HANG, not a crash

Client report: the app "crashes" going back Home -> Call. Five logs (three distinct runs; two files are
copies) contain **no** crash, exception or error - each simply stops. Event Viewer on the client
(DESKTOP-TouchTest) settles why: **Application Hang, event 1002, 14:27:22**, `Timeline.exe` 6000.3.22,
"stopped interacting with Windows and was closed", hang type Unknown, report id
9e958fbf-355a-48e2-9cc0-ba852dc1565d. A hang writes nothing to Player.log and no Unity Crashes folder.
The last log line in that run was at 14:22:15 (a language switch), so the freeze began somewhere in
14:22-14:27; navigation is not logged, so the step that froze is not in the log.

Code read for a main-thread spin, none found: `TimelineTextureCache.Trim` (every pass evicts and removes
an entry, or breaks), `Pump`, `SlideDue` (no loop), the pool loop in `TimelineScreenview`, and every
blocking call in active modules (only AppData is on; Sockets/OSC/Serial off).

Open, waiting on client evidence: the two WER 1001 events (14:26:36, 14:27:22) and their report folder
in `C:\ProgramData\Microsoft\Windows\WER\ReportArchive` (a hang report can carry a dump with the main
thread's stack); System log for Display 4101 (driver timeout). Note the GPU driver is 23.20.16.4901,
from 2017, on Iris Plus 640 - a D3D11 driver stall is a live candidate, not established.

**Update - the client's WER events point at a GPU driver timeout (TDR).** Sequence on DESKTOP-TouchTest:
14:26:32 Intel(R) RMT warnings + Desktop Window Manager 9027; 14:26:36 two WER 1001 **LiveKernelEvent,

it); 14:27:22 WER 1001 **AppHangB1** for Timeline.exe 6000.3.22.29294 + Application Hang 1002. So the
GPU hung first and the app hung behind it - the app was most likely running normally (navigation is not
logged) until ~14:26:32, which matches the report of failing on Home -> Call. The driver is
23.20.16.4901 (2017) on Iris Plus 640. Not established: whether something the app draws on Call trips
the driver, or the driver/hardware fails on its own. Next: update the Intel driver and retest

## Timeline: single touch only (v0.57.0)

**Task:** on the timeline only the first touch registers; additional simultaneous touches are ignored.
Worked on `main` in this checkout at the user's instruction; the uncommitted `settings.json` password
change was left untouched.

**Changed:** new `App/Timeline/SingleTouchInput.cs`, a `BaseInput` set as the module's `inputOverride`;
`TimelineScreenview` installs it in `Show` and removes it in `StopListening`. It locks onto the first
finger to begin and exposes only that one until it ends, is cancelled or vanishes; a finger already down
when the lock frees is never adopted; `mousePresent` is false while any finger is down, so touch-to-mouse
emulation cannot feed another finger in.

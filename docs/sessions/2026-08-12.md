The register proposed replacing the enum with a string, generic or ScriptableObject key. That

### M20 phase 2 — `MediaVO` out of the framework (v0.22.0)

Four overloads deleted, re-added as extensions. Small, because the primitive `(string ...)` overloads
already existed in all four cases and there is exactly one call site in the repo
(`App/UI/ImageGalleryItem.cs:57`).

**Two review findings changed the design, and one of them is the interesting kind.**

`architect-reviewer` pointed out that putting the whole method body in an App-side extension moves
*shared* behaviour — the thumb→url fallback, the M26 log-level fix, the event bookkeeping — into a
file every branched project owns a copy of. Four methods, N branches, each free to drift. And it had
`MediaVOExtensions` raising `onLoadFailedEvent` for a failure `DownloadableImage` never attempted, so
that class's own invariant was being enforced from outside it. The fix is that the fallback rule never
needed `MediaVO` — it needs *two candidate strings*. `Load(string url, string fallbackUrl)` now lives
in the framework, and the extension is down to `image.Load(isThumb ? media.thumb : media.url, ...)`:
the only thing that knows about `MediaVO` is which field to prefer, which is exactly the project's
business.

**The one that would have cost someone a day:** `Play(MediaVO)` is the exact single-parameter shape a
`UnityEvent<MediaVO>` Inspector binding targets, and this repo ships two such events
(`ImageGalleryItem.onMediaClickEvent`, `ImageGalleryPanel.onMediaClickEvent`) — "gallery item clicked →
video player plays it" is the obvious wiring. A persistent call is resolved by reflection over
**instance** methods, so an extension method can never satisfy it; and `UnityEvent` skips a call it
cannot resolve **without logging**. No binding exists in this repo (verified: no `m_MethodName:
Play|Load|Prepare` in any `.unity` or `.prefab`), but a branched project with one would have lost video
playback on gallery clicks, silently, on merge. Rather than write a migration note nobody reads, the
instance methods are restored App-side in `VideoPlayerController` — so a branch that merges keeps both
the binding and the override point, and no migration step exists to forget.

Also found: `StringExtensions.GetTranslation(this string) => message` is an identity function, and this
change removed the last of its 14 call sites. Logged as **M62** rather than fixed — see below.

### M20 phase 3 - the last cycle, and a design that did not survive review (v0.23.0)

`AppDataController` now deserializes into `AppDataBase`/`AppSettingsBase`, told what to build by two
`protected virtual Type` properties. **The cycle is broken**: 0 framework/External references to any of the
17 `App` types, verified twice by independent methods with comments and string literals stripped.

**My first version had four hooks and both reviewers rejected the shape.** Create, deserialize-appData,
deserialize-settings-file, deserialize-settings-block. They are all-or-nothing with nothing saying so: a
project overriding only the creator would write a full settings file - `JsonUtility.ToJson` serialises the
*runtime* type - and read it back through a base-typed deserializer, so the object reverted to the base and
the **next save erased the derived keys from disk**. Two `Type` properties cannot get out of sync, and they
also stop exporting the two-serializer split, which is a framework fact rather than the project's business.

**And the premise I had repeated was false.** Both the earlier review and I said "`MainController`
discovers the subclass for free". It does not: `SetupAppData` returned immediately after
`GetComponentInChildren`, *before* subscribing `OnDataLoadedEvent`, marking the boot stage and calling
`Init()`. A scene-authored controller was found and then abandoned - no data load, boot chain stalls, C3's
shape. Nothing in this repo authors one, so it had never fired, and M20 is what made it matter. Fixed so
both paths subscribe and initialise.

**The remaining risk is a silent one, and it is why the template ships the subclass rather than a comment.**
`App/Data/ProjectAppDataController.cs` only applies if it is authored on a GameObject under `Core`.
Unauthored, the model deserializes into `AppDataBase` - one `languages` field - the project's members are
never populated, and **nothing fails to compile**, because `MediaWalker` is reflective and every consumer
takes `object`. With `cleanUnlistedAssets` on, which the shipped `settings.json` has, the empty keep-list
also clears the media cache: `AssetManager` reports the model blindness loudly but clears anyway, by M31's
decision. Silent content loss plus a destructive cleanup is the worst outcome in this session, and it
exists in the window between merging this and wiring the component.

Also from review: `AppDataControllerEditor` now passes `editorForChildClasses`, or a project's subclass
silently gets Unity's default inspector; and a comment justifying "not a field initializer" gave the wrong
reason - derived initializers run *before* the base constructor, and the real reason is that a
MonoBehaviour's serialized fields are not deserialized at construction time.

### M20 phase 4 - the assemblies (v0.24.0). M20 is closed.

`Assembly-CSharp` went from **260 scripts to 13**: `EnigmaVirtual` 214, `App` 12, `LeanTween` 8. An
`App/`-only edit now recompiles twelve files instead of everything, and `internal` finally means something.

**The shape nobody had planned for.** The decomposition and both reviews recommended one asmdef on
`EnigmaVirtual/`, leaving `App/`, `External/` and `Editor/` in `Assembly-CSharp`. That cannot work:
`External/` is **mutually dependent** with the framework - `MainController` uses `RawKeyInput` while
`RawKey.cs` calls `Development`, and `SerialPortsManager` uses `UnitySerialPort` which calls
`Development` in seven places - so it can sit neither above nor below it. Everyone had been looking at
framework-to-`App` and nobody at framework-to-`External`.

The fix is structural rather than code: `EnigmaVirtual.asmdef` at the **`01_Scripts` root**, covering the
framework *and* its forks, with `App.asmdef` **nested** in `App/` taking precedence for its own subtree.
Zero file moves, zero behaviour change, and `App` gets its own assembly as a bonus. It also states the
real relationship - these forks are not independent third-party code, they are framework-dependent forks,
which `CLAUDE.md` has said in prose since v0.4.0 without the structure reflecting it.

**Both predictions about the first breakage were wrong.** Not the package references: Newtonsoft,
Phidget22 and MidiJack are auto-referenced precompiled DLLs and cost nothing while `overrideReferences`
stays false. The actual reference list is `UnityEngine.UI` - **51** framework files, by far the biggest
dependency and unmentioned anywhere - plus `Unity.TextMeshPro` (4 files, and it lives inside
`com.unity.ugui` now) and `LeanTween`. `UnityEngine.UI.Extensions` turned out to be declared *inside* the
framework, and `UnityEngine.InputSystem` sits behind `#if NEW_INPUT_SYSTEM`, which is off because this
project uses the legacy Input Manager. The `internal` prediction was right but small: two members.

**What actually cost a compile round, and it is my mistake to keep.** My dependency scan read `using`
declarations - which **cannot see global-namespace types**. LeanTween's `LTDescr`/`LeanTweenType` and
`ApplicationDescription` are exactly that, so 69 errors landed on ground I had declared clear. Third time
today a check was narrower than the claim I made from it: a truncated grep hid `.ToObject<AppData>()`
twice, and now an import-based scan hid two whole dependencies. The replacement sweep matches declared
type *names* across the assembly boundary and found nothing further.

`ApplicationDescription.cs` moved into the framework - it is `namespace EnigmaVirtual`, and only the
*asset* ever needed to live in `Resources/`, not the script. GUID preserved, so `Descriptor.asset` still
resolves. `LeanTween.asmdef` went on `Framework/` rather than `LeanTween/`, so its `Editor/` subfolder
stays in `Assembly-CSharp-Editor` instead of being swept into a runtime assembly where its `UnityEditor`
usage would break.

### M62 - the identity `GetTranslation` (v0.24.1)

One line deleted. `StringExtensions.GetTranslation(this string) => message` did nothing, its own doc said
"Returns same value..", and M20's `MediaVO` move had already taken the last of its **14** call sites.

**The interesting half is what it was standing in front of.** `MediaVO.url` and `.thumb` are plain
`string` while `title`, `description` and `keywords` beside them are `TranslatableField<string>`, so
`Load(media.url.GetTranslation())` read as "the URL for the current language" and meant `Load(media.url)`.
**Per-language media is silently unsupported** - a project shipping a different video per language gets
the same file in every language, no error anywhere.

I did **not** decide it for everyone, and the architect review agreed with the reasoning: it is an *absent capability,
not a regression* - it has never worked - and making it work is a content-format change to `appData.json`
for every deployed site plus the API behind it. That is a product decision with a data migration
attached, and the base project is the wrong place to make it on everyone's behalf. So `MediaVO` - a project file, which exists to be
edited - now documents how to make them translatable, with the two traps named: four call sites
in `MediaVOExtensions` pass those fields into `string` parameters, and the obvious `GetLocalized()`
returns **`null`** rather than `string.Empty` (M6), landing straight in `Load(url, fallbackUrl)`.

**Delete over `[Obsolete]`, for a reason I had not articulated until the review did.** An extension method
cannot be bound in a `UnityEvent` persistent call, cannot be serialized, and cannot be reached by
reflection over instance methods. So a branched project's every consequence is `CS1061` - **there is no
silent-break path at all**, which is the bar for a hard delete rather than a deprecation. My own M6
analogy did not survive contact: `[Obsolete]` earns its keep there because a successor with *different*
semantics exists to name, and here it would say "use nothing".

**Three review findings on my own comments, all of them me over-claiming:**

1. The migration recipe said "change these two fields" - really two fields **and four methods**. And it
   pointed at `GetLocalized()` without mentioning it returns `null`, which is inviting the M6 mistake.
2. The framework comment cited the literal path `App/Model/AppData.cs`. Shared code every branch copies
   should not name a project file a branch may move; nobody re-points comments the way `known-issues.md`
   gets re-pointed. Names the type now.
3. I asserted the extension "existed only to keep call sites compiling after the fields were flattened".
   **Git cannot confirm that** - both the extension and the plain-string `url` are present in the initial
   import. The register hedged with "at some point" and my comment did not. Hedged to match.

## Verified

   so `.unity`/`.prefab`/`.asset` are covered too - and a `UnityEvent` persistent call cannot target an
   extension method regardless. The 14 historical sites reproduce at `80cb581~1` in

2. **No overload-resolution change is possible.** Instance methods always beat extension methods, so the

3. **The "nothing in the framework needs to change" advice survives the asset-walk test** -

### M2 - the texture loader (v0.25.0). Six defects, and the two that mattered were not on the list.

**The texture belongs to the cache.** `SetRawImageTexture` wrote `filterMode` onto it and called
`Apply()` - on an instance shared with every other loader showing the same url. `Apply()` on a
2048x2048 RGBA32 is a **16.78 MB** main-thread re-upload (~3-8ms), and it ran on **cache hits** too,
because `GetOrSetTexture2D` invokes the callback synchronously from the dictionary: eight swaps in a
frame cost 25-65ms. It also could never do what it looked like - `UnityWebRequestTexture` yields
mipmap-free textures and `Apply(true)` cannot add mips afterwards - and it **threw** on the error
placeholder, a non-readable Resources sprite (`isReadable: 0`).

**`fitType` was a serialized field the code assigned to.** First load rewrote `Both` to `Width` or
`Height`; every later image reused the first one's orientation, and the Inspector showed the rewritten
value. `case FitType.Both` was unreachable and `FitType.Fill` had no case at all - it silently resized
nothing.

**The two the register did not have, both from review:**

1. **The same `fitType` self-assignment is in `DownloadableImage`, and *that* is the copy that ships** -
   `ImageGalleryItem.prefab:221` has `fitType: 2`. `TextureCacheLoader` is on no prefab in this repo. So
   the file the register named was the dormant one and the live one was two folders away. Fixed both.
2. **The fit maths read `sizeDelta`, which is not a size.** On a stretch-anchored rect it is an offset
   from the anchors and reads `(0,0)`, so the comparison was `0 < 0` for every texture and chose
   `Height` every time. I had called my version "byte-for-byte identical on the common path" - it was,
   and that was the problem: I faithfully reproduced a computation that never worked.

**Reversed on `filterMode`.** I deleted the field; `silent-failure-hunter` pointed out that a branched
project using `Point` for pixel art goes silently `Bilinear` - blur nobody attributes to a framework
bump. It is back, deprecated: applies nothing, logs an error at startup if non-default, removed next
minor. `generateMipMaps` stays deleted - provably a no-op.

Also fixed: the `Awake` NRE when `rawImage` is unassigned and `useFadeIn` is on (the default); `Clear()`
allocating an undestroyed `Texture2D` per call; `AddComponent<ImageResizer>()` whose four calls were all
commented out; public `ResizeTexture` being the one entry point with no guard; `EnsureReady` re-entering
`Awake` and re-logging on every call for a broken loader; and `"Missing RawImage or invalid texture!"`,
which named neither the url nor which of three unrelated causes fired, and left the previous item's
picture on screen at a freshly-reset size.

**Logged, not fixed: M63.** Cached textures are requested readable, so each keeps a CPU copy the size of
its GPU copy - ~3.3 GB instead of ~1.7 GB for 200 images. M2 removed the `Apply()` that required it, so
`nonReadable: true` is now available. Not done here: different file, and `DownloadableImage.GetImageData`
calls `EncodeToJPG` on whatever texture it holds, which would throw.

## Test plan

**Corrected after `doc-reviewer`, and the correction is the interesting part** - see the note below.
Nothing in this repo instantiates a gallery: `ImageGalleryPanel.prefab` is referenced by no scene,
prefab or script, and `ImageGalleryPanel.SetData` has zero callers. Every step is therefore hand-driven.

**1. The sticky `fitType`, on one instance.** Drop `ImageGalleryItem.prefab` into a scene, select the
`ImageHolder` child, and set its `DownloadableImage` **Url** to a **landscape** image. Right-click the
component → **Force Load**. Then change **Url** to a **portrait** image and **Force Load** again.
- **Pass:** the **Fit Type** dropdown still reads `Both` after the second load, and the rect matches
  each image's own aspect in turn.
- **Fail:** **Fit Type** reads `Width` or `Height` after the first load - that is the field being
  rewritten under you - and the portrait image is letterboxed into the landscape one's shape.

Two loads into **one instance** is the whole point: a wired gallery would `Instantiate` a fresh
`ImageGalleryItem` per media and each loads exactly one image, so the rewritten field never reaches the
next item. The defect needs reuse, not a list.

**2. Counter-test for step 1.** Same instance, first **Force Load** only.
- **Pass:** the image is fitted to `ImageHolder` as before, *and* the Console has no
  `DownloadableImage` error. A guard that refuses everything passes step 1 too.

**3. The stretch-anchor case.** On the **`ImageHolder`** object - not the child `Image`; the code
measures `transform as RectTransform` on the component's own GameObject (`DownloadableImage.cs:363`) -
set the anchors to stretch **and then set Left/Right/Top/Bottom to 0**. Changing the anchors alone is
not enough: the Inspector preserves the rect, so `sizeDelta` stays non-zero and the old code still
half-works. `ImageHolder` is 560x605 in a 560x642 parent, so anchors-only leaves `(0, -37.17)`.
Now **Force Load** an image **wider in aspect than the container**.
- **Pass:** it is fitted by width and fills the holder horizontally.
- **Fail:** it is fitted by height. The rule is `container.x / w < container.y / h`, and the old code
  read `sizeDelta`, giving `0 < 0` = false = `Height` for *every* texture - so only an image wider than
  the container tells the two apart. A taller-than-container image looks identical either way.
  Revert the anchors afterwards.

**4. The deprecation is loud.** Add a `TextureCacheLoader` to any Canvas, assign a `RawImage`, set
**Filter Mode** to `Point`, press Play.
- **Pass:** Console shows `TextureCacheLoader on [<name>] has filterMode Point, which is no longer
  applied` at startup.
- **Fail:** nothing in the console - the silent regression the field was kept to prevent.

**5. Counter-test for step 4.** Same component, **Filter Mode** left at `Bilinear`, `Load(url)` a real
image.
- **Pass:** no deprecation error **and** the image appears. The absence alone is also satisfied by a
  loader that never ran.

**6. The `Apply()` removal, on the Profiler.** This needs the **hand-authored `TextureCacheLoader`** from
step 4, not the gallery - `DownloadableImage` never called `Apply()` and never touches
`TextureCacheManager`. `Load(urlA)`, then `Load(urlB)`, then `Load(urlA)` again so the third is a cache
hit. Deep Profile on, watch the third load's frame.
- **Pass:** image A is visibly back on screen **and** the frame contains no `Texture2D.Apply` and no
  `Gfx.UploadTexture`. Expect ~3-8ms to disappear from the main thread for a 2048x2048.
- **Fail:** either marker present. (Both halves needed: "no markers" alone is also what a load that
  never happened looks like - which is exactly the absence-only criterion this file's own rules forbid,
  and which the first draft of this step got wrong.)

**Why `TextureCache.isActive: false` does not make this dormant:** `MainController:346` calls
`SetupTextureCacheManager()` outside every `isActive` gate and `GetOrSetTexture2D` has no gate of its

It is **irrelevant to steps 1-3**, which are `DownloadableImage` and never enter the cache at all.

**What this cannot reach.** Every step is hand-driven, so all six test the code rather than a shipped
path - `TextureCacheLoader` is in no prefab or scene, and the gallery that would exercise

### M1 - the image loader that is not a thread (v0.26.0)

**Reachability first, because M2 taught me to.** `DownloadableImage` appears in exactly one prefab,
`ImageGalleryItem.prefab`, instantiated only by `ImageGalleryPanel`, whose `SetData` has zero callers.
**Nothing in this repo runs any of this.** It is live in any branched project that wires a gallery and
dormant here. I said "this is live, not dormant" mid-session on the strength of the prefab wiring
`_image` rather than `_rawImage` - that establishes *which branch* runs if it runs, not *that* it runs.

**The register's headline was the least reachable of the five, and its footnote was the whole thing.**

*The recursion, listed first, is latent.* `LoadImage` was an `IEnumerator` whose only `yield` sat after
its own `TryDequeue()` call, and `StartCoroutine` runs a body synchronously to the first yield - so the
chain ran inside the original call, one frame per item. But the queue only exceeds one item through **a
callback that enqueues**: every `Enqueue` calls `TryDequeue`, which drains before returning, so a
caller looping over 550 media still nests exactly two deep. Fixed anyway; a `while` loop is identical
work, flat.

*The leak, listed last, is the reason this entry mattered - and it is the **texture**, not the sprite.*
The entry said "Sprites never destroyed", so I destroyed sprites: a few hundred bytes per image, while
the pixels stayed. `DownloadHandlerTexture.GetContent` allocates a `Texture2D` per download, nothing
destroyed it, the `UnityWebRequest` was never disposed, and `Resources.UnloadUnusedAssets` never runs
on this path - **megabytes per image shown**. Both reviewers caught it independently, against a comment
I had just written saying the leak was closed. That comment was the worst part: it would have stopped
the next person looking. Texture and sprite are freed together now, in one `ReleaseCreated()`, and the
request is in a `using`.

**Two more the reviews found, both worse than the recursion:**

1. **A throwing callback killed sprite loading app-wide, permanently.** `activeLoads--` sat after
   `LoadImage`, and the callback fans out through `onLoadCompleteEvent` into arbitrary project code.
   One throw pinned the counter at 1, and every later `TryDequeue` returned at the re-entrancy guard.
   `ImageLoaderThread` is a singleton on `Core`, so that is every image in the app, after one
   exception, with nothing further logged. A `finally` closes it.
2. **My ownership fix was itself a hazard.** `SetImageSprite` is `public` and `UnityEvent`-bindable
   with a dragged `Sprite` argument. Having it take ownership meant a project wiring a sprite *asset*
   to it would have that asset destroyed on the next load - silent in a player. Ownership moved to a
   private `OnSpriteCreated`, the loader's own callback and the only path that knows the sprite was
   made for this component. The public method is back to non-owning.

**`SpriteCreateLayerJob` is deleted, not fixed** - managed `UnityEngine.Object` references in an
`IJobParallelFor` struct, main-thread-only `Sprite.Create` called from a worker, and an unreferenced
caller seeding it with `Sprite.Create(null, ...)`. Three independent reasons it could never run, plus a
fourth: the struct copy meant `outSprite` never propagated back anyway.

**The name stays.** Renaming breaks the `Core.prefab` and `CoreSetup.unity` bindings for every branched
project, so the class documents what it is: an image load *queue*, ordering work that must be on the
main thread and is cheap there. The queue's ordering and priority are decorative while the drain is
synchronous - noted in the remarks rather than removed, since removing them is a public-API change for
no gain.

### M16 - the Timer (v0.27.0)

The entry listed four defects. The one that mattered was underneath them, and two more were not there
at all.

**`interval` was an auto-property, so Unity's serializer could not see it.** Two consequences the entry
never connected: it could not be authored in the Inspector *beside* `tickInterval`, which is a plain
field and shows up fine - and it defaulted to **0**. So a `Timer` given a bare `StartTimer()` satisfied
`_currTime >= interval` on its first frame and completed immediately; every frame with `loop` on. This
is M3/M4's rule - an auto-property in a type Unity serializes does not merely go unread, it does not
exist - applied to a `MonoBehaviour` rather than a content DTO. Dormant here, since both call sites set
an interval first; live in any branched project that starts a `Timer` bare or authors one in a scene.

**`GetProgress()` has zero callers**, which is why the NaN the entry predicted never surfaced. It was
also `internal`, so since the v0.24.0 split the only plausible caller - a progress bar, which is
App-side - could not see it. Now `public`, guarded, `Clamp01`'d. Worth recording for the next one: a
`NaN` in `Image.fillAmount` propagates into layout rather than throwing, so it would have failed as a
wrong picture with a clean console.

**Two the entry did not have, both from review.** The tick accumulator did `_secsCount = 0f`, throwing
away the overshoot past `tickInterval` - up to a frame per tick, drifting late over a long countdown.
Then, having fixed that with `-=`, `code-reviewer` pointed out that the *completion* overshoot was
still discarded by `Reset()`, so a looping timer kept drifting one level up: the comment I had just
written claimed to close a drift the same method reopened four lines later. Both carry now, and both
are capped, so a hitch drops the backlog instead of replaying it as a burst of ticks or completions.

**`0` already means "no timeout" in this codebase, and now the Timer honours it.** `DebugSettings`
ships `errorTimeout: 0` and `NotificationPrefab` tests `> 0` before starting. My first patch logged an
*error* and forced 1s, which is both the wrong severity - a failed validation is not an exception - and
the wrong answer. It warns and declines to start.

**One fix created a hole and one nearly did.** Removing the `IsRunning` setter left `PauseTimer(false)`
assigning `_running` directly, skipping the interval guard and any subclass override - a second way in,
against a remark claiming there was now one. It routes through `StartTimer()`. And I first made
`Update()` private, which is worse than public for a class with six `virtual` methods: a subclass
declaring its own `Update()` gets **no** CS0108, because private members are not inherited, and Unity
dispatches only the most-derived declaration - so the base tick would stop, silently, in the one method
a subclass is most likely to write. It is `protected virtual`.

**Deprecated, not deleted.** `SetDuration` forwards to `SetTimer` with `[Obsolete]`. M62's precedent
was to hard-delete, but that was an identity function; this does real work, so deleting it takes
function away from a project that calls it. `TranslatableField.GetTranslation` already set the pattern.

`Reset()` collides with the Unity message of the same name - the editor calls it when the component is
added or Reset is picked from the context menu. Harmless, and renaming a `public virtual` breaks every
branched project's callers, so it is a remark on the class.

### TranslatableField -> LocalizedField (v0.28.0). Tiago's call, not a register item.

The type had three words for one idea: *translatable* in its name, *translation* in its methods,
*localized* in the accessor that replaced them - and the odd one out was the only one anyone was
supposed to call. Now one vocabulary.

| was | is |
|---|---|
| `TranslatableField<T>` | `LocalizedField<T>` |
| `HasTranslation` / `HasAnyTranslation` | `HasLocalized` / `HasAnyLocalized` |
| `TryGetTranslation` | `TryGetLocalized` |
| `TryGetTranslatableByKey` *(private)* | `TryGetByKey` |
| `TryGetValue(out T, string, bool)` | `TryGet` |
| `[Obsolete] GetTranslation` x2 | **deleted** |

**The safety argument, which `architect-reviewer` tried to falsify and could not.** The break is
compile-only: this type derives from `Dictionary`, so Unity never serialized it into a scene or prefab,
and Newtonsoft matches `appData.json` by *field* name rather than type name. The vector that could have
made it silent is `TypeNameHandling` - which writes `$type` strings into JSON - and there is **zero**
use of it anywhere, and zero `$type` in StreamingAssets. Also negative: `SerializeReference`, name-based
reflection, property drawers, and any hit for the old name in `.unity`/`.prefab`/`.asset`/`.meta`.

The review made the case better than I did: since v0.24.0 the only symbols a branched project can
*reach* are the type name and `GetLocalized`. Everything else is `internal`, so a branch calling it
already gets CS0122. **The real public break surface is one type name** - unless the project added its
own files under `EnigmaVirtual/`, which share the assembly and see the rest.

**`TryGetValue` -> `TryGet`, taken because this was the free moment.** It shadowed
`Dictionary.TryGetValue` with the arguments in the opposite order. Never ambiguous to the compiler - an
`out` argument cannot bind to the base's first parameter - but typing the familiar order silently took
the base method, which throws on a null key and skips the "key not found" warning. `internal`, one call
site.

**The rule that separates deleting from deprecating is now written down**, because I made opposite calls
two commits apart and neither comment gave the real reason. It is not "how much work the member does" -
it is **visibility across the v0.24.0 boundary**. `public` means a branch can reach it, so it earns an
`[Obsolete]` naming its replacement (`Timer.SetDuration`). `internal` with no in-assembly callers means
no branch could ever have called it, so deprecation buys nothing (`LocalizedField.GetTranslation`).
Either way, check for a silent-break path first. In `overview.md` section 5b.

**Where the rename stops is deliberate.** `Translations` keeps its name and its `GetTranslation`: it is a
*store* mapping a key to a `LocalizedField`, which is a different concept from one value with per-language
variants. The lookup path does two different lookups and the naming now says which is which - on
`LocalizedField`, `*Localized` resolves a **language** and a plain name looks up a **key**. That matters
because the same type is used both ways: `LocalizedField<string>` is keyed by language, and
`Translations`'s `LocalizedField<LocalizedField<string>>` is keyed by translation key. Renaming
`Translations` would cascade into the public `MainController.GetTranslation` for no behavioural gain.

**M6 is half closed.** Deleting `GetTranslation` removes the two-semantics problem - `string.Empty` on a
miss versus `default`. What remains is a call-site guard: `GetLocalized` returns null for a missing
string and that into `TMP_Text.text` risks a throw inside TMP's parser.

**M64 logged, split out of M6 on review's advice.** `TryGetLocalized` returns **true** for a key present
with a `null` value - unlike `HasLocalized`, which tests `value != null` - and
`TextMeshProUGUIExtension.SetText` dereferences it immediately. That is a different defect from M6 in
both method and exception: `ArgumentNullException` out of `Regex.Replace`, not an NRE. Unchanged by this
rename; the pre-rename method was byte-identical.

**Two things I got wrong, both caught.**

1. **Seventh BOM.** I rewrote the class through the `Write` tool, which emits plain UTF-8, and dropped
   the BOM every sibling in that folder carries. Six previous occurrences were all `utf-8-sig` in a
   script, so my note was written around scripting; the real rule is **whole-file replacement by any
   means**, checked against `git show HEAD:<old path>` - the old one, since a `git mv` leaves the new
   path with no history.
2. **I over-claimed in the deletion comment**, saying the removed overload differed from `GetLocalized`
   "in exactly one way". It also returned `value.ToString()` rather than `T`, which diverges outright
   for `LocalizedField<MediaVO>`. Zero callers either way, so nothing behavioural - but it is the fourth
   time today that the sentence claiming a fix is sound was the part that was not.

**One wrong doc claim found by walking into it.** `overview.md` said seven framework types live in the
global namespace and listed `TranslatableField` and `MediaFile` - both are in `namespace EnigmaVirtual`
and never were. Measured properly: **51**, of which ~21 are `*Extensions` holders where global is
deliberate, since an extension method is only in scope where its namespace is. `Assets` and `Colors` are
the collision-prone ones. Corrected in `overview.md` and in L6.

### M6 and M64 - the localization nulls (v0.29.0)

**M6's premise was false, and checking it changed the whole fix.** The entry had said for months that
assigning `null` to `TMP_Text.text` risks an NRE in TMP's parser. It does not, in the TMP that ships
with Unity 6: the setter stores null (`TMP_Text.cs:131`), `PopulateTextBackingArray` null-checks at
`:2056` and `:2073`, `SetText(string)` at `:2442`, and `m_text` is dereferenced in exactly one guarded
place. The only null-unsafe route is an `ITextPreprocessor`, and none is assigned here. So
`ImageGalleryItem.cs:46`, one of M6's three cited sites, never threw. `Library/PackageCache/` had the
answer the whole time.

**What it actually did was worse than a crash: nothing, forever.** `Translations.GetTranslation`
promises in its own summary to return the key when nothing is found, and returned `GetLocalized`'s
result unconditionally instead - null for a language the entry does not carry. `MultiLangText` seeds
`langText` with `"[key]"` as a deliberate on-screen diagnostic, overwrote it with that null, then
skipped the **whole assignment** on `!string.IsNullOrEmpty(langText)`. The placeholder was discarded and
whatever was on screen before stayed. It *did* warn in the console - so the failure was loud in the log
and invisible on screen, which is the half that matters for a kiosk nobody is watching. My first comment
about this said "nothing logged", which `code-reviewer` falsified against the very line that does it.

**Three fixes, and the third is the one I had missed.** `GetTranslation` honours its contract.
`MultiLangText` moves the assignment **outside** the formatting gate, so an empty result clears the
label instead of leaving a stale one - the same silent-staleness shape, one level up. And
`ImageGalleryItem` takes the *direct* `GetLocalized` route, which my first patch did not touch at all:
`silent-failure-hunter` pointed out I had fixed the `Translations` path and left the other one rendering
a permanently blank gallery label, with nothing thrown and nothing logged, while the register still
described that exact path as a crash. It asks for `fallToDefault: true` now and logs when an entry has
no value in any language. `TextPanel` was discarding the bool from its own helper at all three sites;
same shape, now logged.

**Empty string is a value, not a miss.** Only `null` falls through to the key, so a label deliberately
blanked for one language stays blank rather than showing `menu_title_home`. Both reviewers pushed on
this and landed in different places; the deciding fact is that an intentional blank never worked anyway
- pre-fix, `"en": ""` made `MultiLangText` skip the assignment and leave stale text - so returning the
key for `""` would have replaced one broken behaviour with a louder one rather than fixing anything.
`LocalizedField` and `Translations` now draw the line in the same place.

**M64 fixed at the shared function.** `TryGetLocalized` treats a null value as absent, so `true` always
means the out-value is usable. `HasLocalized` and `GetLocalized` already worked that way. My own comment
from yesterday had defended the old behaviour as "what a dictionary entry means" - true of a dictionary,
wrong for a method whose job is to say whether the caller has something to show.

**Two review findings about making things quieter.** The `ConvertTextTagsForUnity` null guard replaced a
loud `ArgumentNullException` with a silent null, which is a downgrade for a branched project - it logs
now. And `RemoveAllTextTags`, its sibling, still threw: guarding one of a pair is its own trap, so both
now agree.

**Verified, not assumed:** `code-reviewer` compiled the `&& output != null` shape to confirm definite
assignment, and measured the generic cases - `LocalizedField<int>` with `0` gives `true`,
`LocalizedField<int?>` with null gives `false`. A `default(T)` test would have made `0` and `false` read
as absent, and a `where T : class` constraint would be a compile break for any branched project holding
a value-type instantiation. `!= null` is right.

**Left alone deliberately:** the warning is `Development.LogWarning`, which is `[Conditional("DO_LOGS")]`
and so compiled only for Android and Standalone. On iOS and WebGL there is no log - but the key now
renders on screen, and that is the louder instrument anyway.

Set back to `false`. Enabling it is a per-installation decision for a deployed config in

### M11 - regex-parsing JSON (v0.30.0)

`APIResponseModel.GetValueAsString` ran `new Regex("\"values\":([{\\[].+[}\\]])")` then `matches[0]`.
The register listed three defects; there were four, and the fourth is the worst.

1. **No match check.** Any response without a `values` member - an error payload, an HTML error page from
   a proxy, an empty body - threw out of the `MatchCollection` indexer instead of reporting a missing
   field. `ArgumentOutOfRangeException`, incidentally, not the `IndexOutOfRangeException` the register
   said; both reviewers measured it.
2. **Greedy `.+`.** The capture ran to the last `}` or `]` on the line, and the trailing
   `Substring(0, s.Length - 1)` existed to chop the root object's own closing brace back off. Correct JSON
   came out only when `values` was the final member of the root.
3. **It returned silently truncated JSON on a pretty-printed body.** `.` does not match a newline without
   `RegexOptions.Singleline`, so the capture stopped at its own line end and the `-1` then ate the closing
   bracket - `[{"a":1}`, invalid, no exception, no log. For the same reason a single space after the colon
   matched nothing and threw. `code-reviewer` established this by running the regex; I had reasoned about
   it and got a more generous answer.
4. **`Regex` rebuilt per call**, uncached, uncompiled.

Now `JObject.Load` with `DateParseHandling.None`. Newtonsoft was already a `using` in this file and
`AppDataController` parses the same string with `JObject` twice - the regex was never the only option,
just the one nobody revisited. `System.Text.RegularExpressions` is now unused and gone.

**I introduced a defect and both reviewers caught it independently.** `values == null` misses
`"values": null`: a JSON null is a `JValue` of type `Null`, not a C# null, and neither `JToken` nor
`JValue` defines `op_Equality` in the vendored Newtonsoft (13.0.2, verified by reflection) - so `==` is
reference equality and the method returned the literal four-character string `"null"` as a successful
read. The caller's `DeserializeObject<T>("null")` then returns null with no error anywhere. The old regex
required a `[` or `{` and threw on that shape, so my fix would have been strictly worse for it. Now
`values.Type == JTokenType.Null` too.

**Three more things the reviews changed.** The missing-`values` report was `LogWarning`, which is
`[Conditional("DO_LOGS")]` and therefore compiled out on iOS and WebGL - a null return with no artefact
anywhere, which is the exact silence M11 existed to remove. It is `LogError` now, like the two branches
above it. `ToString(Formatting.None)` re-serializes rather than slices, and Newtonsoft's default
`DateParseHandling` would have rewritten date-shaped strings (`"2026-08-12"` as `"2026-08-12T00:00:00"`)
on their way to the caller - my comment had claimed whitespace was the only difference. And
`ChangeValueName` no-ops silently when `oldName` is absent, which is the likely case rather than the
exotic one, so it reports now; its empty-body branch is a warning rather than an error, because `""` is a
value this same file produces on its own error path and `"".Replace()` was always harmless.

`ChangeValueName` keeps its string replace: `AppDataController` writes `raw` verbatim as the offline cache
and re-reads that same text, so a parser round-trip would rewrite the cache and change what
`CountRawMediaValues` counts. Both reviewers agreed. Its real limitation - every occurrence, any depth -
is documented; the "inside a string value" risk I had written down is unreachable for valid JSON, since a
quote inside a JSON string is escaped.

**M65 logged, not fixed.** `AppDataController`'s "Error parsing remote appdata JSON" catch wraps
`OnGetAppData`, and therefore `ParseAppData` -> `OnDataLoadedEvent` -> `SetupAssetManager` and
`LoadNextScene`. An asset-manager or scene-load exception is reported as a JSON parse error, and
`OnDataLoadFailedEvent` fires *after* `OnDataLoadedEvent` already did - one boot, both outcomes, in that
order. Narrowing the try is a restructure of the boot hop, not a guard.

**My own near-miss, worth more than the fix.** A heredoc-delivered Python replacement string containing
`\n` and `\u00e9` had those decoded by Python, so a real newline landed in the middle of a C# doc comment
and split it across three lines - leaving a bare `}` at class scope. **The file would not have compiled.**
My crude brace count flagged it as 86/87, and I dismissed that as an artefact of a `}` inside a doc
comment, which is exactly what it had been the previous time. It was real the second time. Two rules out
of this: a replacement string containing backslashes goes in a scratchpad file, never a heredoc; and when
the crude count disagrees, confirm with a stripper instead of reasoning about it. There are now
`balance.py`, `depth.py` and `trace.py` in the scratchpad that strip comments and string literals and
report the first line where depth goes wrong.

### M65 - one try doing two jobs (v0.31.0). Four rounds, the first two wrong.

**The reported defect.** A single `try` wrapped `JsonUtility.FromJson` *and* `OnGetAppData` - and
`OnGetAppData` runs `ParseAppData`, which raises `OnDataLoadedEvent`, which reaches `MainController` and
from there `SetupAssetManager` and `LoadNextScene`. A failure anywhere in the rest of boot was caught
there and shown to the operator as "Error parsing remote appdata JSON", carrying an `ex.Message` from a
completely different subsystem. Split in two, accurate label on the second.

The second catch is **kept** rather than allowed to propagate, and the architect review agreed: an
escaping exception from a `protected virtual` a project overrode would kill the coroutine with
`loadingData` stuck true, and the boot chain has no timeout. A stall is worse than a wrong label, and
`LogException` preserves the stack either way. The knock-on to accept knowingly is that the remote-to-local
fallback then re-enters the same throwing override on the local payload, so a subclass bug costs a second
identical toast five seconds later - that fallback was designed for "the payload is bad", not "the
handler is bad", and it cannot tell them apart.

**Round 1 was a regression, and both reviewers found it independently.** I gated
`OnDataLoadFailedEvent` on `dataLoaded`, reasoning that it is the flag the *success* event is gated on.
It is not the same question. `dataLoaded` is set **before** the work that throws, and means "entered the
parser, no known failure yet". A null `jObj` from a `"null"` body, or `jTokenData["texts"]` on a `JValue`,
escapes `ParseAppData` with `dataLoaded` still true and the success event never raised - so my guard
suppressed the failure report *and* printed "look there, not at the JSON" on the one occasion when the
JSON is exactly the problem. That is worse than the mislabelling it replaced: confidently misattributed
beats vaguely misattributed only in the wrong direction. There is a dedicated `successAnnounced` now, set
on the line before each raise and reset per load.

**Round 2 enforced the invariant at two of six raise sites.** The architect review's phrasing is the one
to keep: an invariant enforced at some of its sites is worse than none, because the next reader finds the
rule written down and assumes it holds. Every raise of `OnDataLoadFailedEvent` now goes through one
method - including the appSettings paths, which carry a different payload but the same event, so the
helper lost its `AppData` prefix. **One raise site, nine callers.**

**Two more from the reviews.** `ParseOneCoreAppData` raised `OnDataLoadedEvent` *unconditionally*,
including immediately after setting `dataLoaded = false` - the same "one boot, both outcomes" defect
inverted, and still live on that path after round 1 because round 1 only touched the failure side. And a
response whose `code` is not `Success` returns from `OnGetAppData` normally, so control reached the cache
write and **`WriteAtomic` stored the failure body as the offline cache**, to be read back as content on
the next boot. Both closed.

**The recovery block was written four times**, not the three I found - `loadingData`/`refreshRequest`,
`failedRemoteJson`, `Invoke("LoadLocalData", 5f)`. The fourth is in a branch that cannot run
(`www.result == Success` implies `www.isDone`); it is routed rather than deleted, and labelled
unreachable, because deleting a branch is a bigger claim than routing it.

**Confirmed, not assumed:** `OnDataLoadFailedEvent` has **zero subscribers repo-wide** - it is M48 - and
`MainController` is the single subscriber of `OnDataLoadedEvent`, which is the only route off the
preloader. So suppressing the failure event cannot hang boot; that was the thing I most feared and it is
not a risk here. It does change behaviour for any *branch* that added a handler, which is why it has an
`overview.md` row despite no signature moving.

**M66 logged.** A payload with a non-`Success` code never raises `OnDataLoadedEvent`, so boot stalls on
the preloader. It is now reported through one place, no longer cached, and named by the boot watchdog -
diagnosable rather than mute, but still a stall. Fixing it means deciding what a kiosk does when the CMS
answers with an error and there is no local fallback: retry, holding screen, or advance empty. A product
decision, so it is logged rather than guessed.

### M63 and M67 - the cache's second copy, and an escape hatch that never worked (v0.32.0)

Both `TextureCacheManager` requests now pass `nonReadable: true`. Two lines of behaviour change; the
rest of the round was finding out that most of what the register said about it was wrong.

**The premise, verified at IL level rather than from documentation.** `performance-reviewer`
disassembled `UnityWebRequestTextureModule.dll` from the installed 6000.3.13f1 with the editor's own
`ikdasm`: `GetTexture(string)` is literally `ldc.i4.0; call GetTexture(string, bool)` - `nonReadable:
false` is hard-coded, not an optional parameter default - and the `bool` overload sets **only** the
Readable bit. So decode, upload and mipmap behaviour are byte-identical before and after; what goes away
is the staging copy that used to be kept after upload.

**My numbers were wrong in two directions.** Unity's decoder produces **RGB24** for a JPG or an
alpha-less PNG, so the CPU copy is 3 bytes per pixel against the GPU side's 4 - a **43% saving, not
50%**. And the headline "6.7 GB to 3.4" described 200 textures at 2048x2048, which is 3.4 GB of GPU
memory alone: a machine that is already dead. At a realistic 1920x1080 JPG it is 14.5 MB to 8.3 - about
**6 MB an image, ~1.2 GB across a 200-image cache**. Worth noting the register disagreed with itself: the
entry said 6.7/3.4 and the worklist row said 3.3/1.7. The worklist was closer, and it was the one I
"corrected" away this morning during M2's doc pass.

**Nothing here reads pixels from a cached texture**, established independently by both reviewers:
`GetTexture2D` has no callers, `TextureCacheLoader` reads `width`/`height` and assigns
`rawImage.texture`, every pixel-reading helper in `TextureExtensions`/`ColorUtil` was checked for a
caller that could receive one, and no `.unity`/`.prefab` carries a texture-related `UnityEvent` binding.

**The change makes failure louder.** Before, a project reading pixels off the cache worked on every hit
and threw only when a download had failed and `Placeholder()` served the Resources image - which is
already `isReadable: 0`. That is a fault which first appears at a site, on the one machine with a missing
file. Now it throws on the developer's first run. Uniform beats intermittent.

**M67: the escape hatch I was about to recommend had never worked.** The M63 comment originally pointed
branched projects at `TextureExtensions.ReadableClone`. Both reviewers independently established that it
cannot do the job: `Graphics.CopyTexture` is a **GPU-side** copy, and populating the destination's CPU
array is a separate conditional step that needs the source to have CPU data - when it does not, the
engine emits **no diagnostic at all**. Then `Apply(updateMipmaps: false)` uploaded the freshly-allocated,
uninitialised CPU buffer back *over* whatever the GPU copy had managed. On top of that `mipChain: true`
against a `DownloadHandlerTexture` texture (`mipmapCount` 1) trips "mismatching mip counts" and copies
nothing at all.

The result reported `isReadable == true` and passed `IsReadable()` - **it failed a readability check by
passing it**. `SaveAsPNG` is the composed consequence: clone an unreadable texture, read the garbage,
write a blank PNG, no exception. Neither has ever run.

Rewritten on Blit + `ReadPixels`, which is the only route from GPU to CPU, into `RGBA32` rather than the
source format because `ReadPixels` needs a format it can write and a compressed source would fail. The
`RenderTexture.active` restore is in a `finally` - a throw mid-copy would otherwise leave it pointing at
a released target and corrupt whatever draws next, somewhere else entirely. Fixed rather than documented
as a landmine, because the M63 comment has to point *somewhere* and `ReadableClone` is the name a
developer reaches for.

**Two slices of L1 also closed here.** Tiago removed three unreferenced `public static` methods from

`HTTPMethods` survives it and is not a BestHTTP dependency: it is declared locally at `Api.cs:445` and

### M5 - StringUtil (v0.33.0). Five clauses, one live, and the entry named the wrong defect in it.

**Only `RemoveFileNameFromPath` is on a live path** - `AssetManager` uses its result as the folder to
create before downloading an asset, and `AssetDownload.isActive` ships `true`. The entry blames
`Replace` corrupting a repeated path segment. That is real and exotic. What actually bit is that it
**split on `'/'` only** and returned **empty** for a path whose final separator was a backslash, so the
download folder was never created; a trailing separator did the same, discarding the whole path. One
`LastIndexOfAny` answers all three, and `GetFileNameFromUrl` had the identical flaw - `Api.cs` already
carried a comment about it - so the two now share a separator array.

**I got the cause of that wrong too, and `code-reviewer` traced it.** I wrote that composed paths are
mixed-separator because `Path.Combine` joins with `\` (C4). True in general, not the mechanism here:
`AppDataSettings` concatenates a literal `/` and collapses doubles by regex, so framework-composed paths
are forward-slash throughout. A backslash arrives only through a **rooted value authored in the CMS**,
which `GetAssetPath` returns verbatim. The fix was right; the stated reason was not.

**The other four clauses have zero callers**, which the entry does not say and which changes how urgent
it reads: `ToClock` (its own headline), `PrintArray`, `GenerateRandomCryptographicKey`, `FormatNumbers`,
and `CalculateMD5Hash` - whose only mention anywhere is `PanelPassword` telling people not to use it.
Fixed rather than deleted, since all are `public static` on a class every branch inherits.

`ToClock` floored the minutes but handed the seconds to `ToString("00")`, which *rounds* - so 119.6 read
`01:60`, a clock that does not exist, for every value in the last half-second of a minute. It is
`[Obsolete]` delegating to `TimeFormat`, which truncates both halves and was always correct: duplicates
where only one worked, the same call M16 made for `Timer.SetDuration`.

**`security-reviewer` caught an asymmetry in my own judgement.** I marked `ToClock` `[Obsolete]` for
being a duplicate whose output differs only below half a second - and gave `CalculateMD5Hash`, which
**silently changes its return value**, a `<remarks>` paragraph. Prose never reaches a call site; quick-info
shows the summary, and someone reaching for a method with `Hash` in its name has stopped reading. It is
`[Obsolete]` now, and the message names the value change, because that is the only channel that fires at
the moment of misuse - and in a base project the misuse happens in someone else's repo.

**And the sentence explaining that change was false.** I wrote that ASCII made an accented word and its
unaccented spelling collide. It does not: ASCII maps bytes above 0x7F to `?`, and `e` is a real letter
that survives - so the collision was between two *differently-accented* spellings, not with the plain
one. It was the sentence a branched project would read when its stored hashes started missing, which is
the worst place to be wrong. Corrected, with a note that an earlier draft said the opposite.

Also: `GenerateRandomCryptographicKey` uses `RandomNumberGenerator.Create()` in a `using`, matching
`PanelPassword` - `RNGCryptoServiceProvider` is obsolete from .NET 6 and would stop compiling the day
this leaves the Framework profile. `FormatNumbers` resolves `pt-PT` once and falls back to invariant,
because `GetCultureInfo` **throws** under invariant globalization and it was called on every format; the
fallback's log is `LogError`, not `LogWarning`, because `LogWarning` is `[Conditional("DO_LOGS")]` and
would have been compiled out on WebGL - the exact target the message is about. The hardcoded `pt-PT`
stays: a client default in a base project, same shape as L3, and changing it is visible behaviour for
every branch.

**H22 logged, not fixed, and it is the most consequential thing this round turned up.**

`localFilePath + ".part"` with nothing checking where that lands - while the cleanup pass four hundred

delete a file it would happily create.** Live in the shipped config. Not fixed here because the guard

- **Pass:** the two differ, and the second differs from what this build produced before v0.33.0. Under
  the old ASCII path the second hashed as `caf?`.
- Also expect `CS0618` on both lines, carrying the note about the encoding change - that warning is the
  deliverable here as much as the hash is.

**5. The culture fallback reports itself.** This one **cannot be run on Windows Standalone**, which is
the honest status: `pt-PT` is present, so the fallback never fires. It needs a culture-stripped IL2CPP
or WebGL player, where the pass criterion is the Console line `Culture [pt-PT] is unavailable in this
build` **and** numbers still rendering - rather than the `CultureNotFoundException` that would have come
out before.

**What this cannot reach.** Steps 3-5 need a scratch script; nothing in the repo calls those methods.
Step 1 requires authoring a deliberately odd CMS value. `GetFileNameFromUrl`'s live caller is behind
`Api.isActive`, which ships `false`, so its half of the separator fix is dormant here. And nothing
verifies H22, which is logged rather than fixed.

### M7 - the language event (v0.34.0). Dormant, and the register said otherwise.

`Core.LanguageChangedEvent` was a `public static Action` **field**, so any code anywhere could drop
every subscriber in the app with one `= null` - and nothing would report it, because the next language
change would simply update no text. `public static event Action` now; the compiler restricts outside
code to `+=`/`-=`. Nothing ever assigned it, so no call site changed.

**The unsubscribes were gated on `Core.IsSet`, which skips the detach exactly when Core has gone.**
`TextPanel` had the rule written directly above the bug - "Always unsubscribe to avoid leaking handlers
even if Core.IsSet changed", sitting on top of the `return` that prevented it. Someone knew. All three
detach unconditionally now: `-=` needs nothing from Core and is a no-op for a handler never added, so
the guard was protecting nothing.

**It was dormant, and I would have shipped the entry's claim unchecked.** Core is `DontDestroyOnLoad`
and `_isSet` only goes false in `Core.OnDestroy`, so an ordinary scene change unsubscribed correctly and
app quit is harmless. My first draft of the comments asserted a session-long leak as current behaviour.
`code-reviewer` established it was armed rather than firing - the seventh time in two days that a
register claim turned out to be a prediction.

**What it cost when armed, traced per subscriber**, which the entry never said and which is the
difference between tidy-up and fix: `MultiLangText` is **inert** - its `_text`/`_textMesh` live on the
same GameObject, so both are Unity-fake-null and the handler returns immediately. `TextPanel` and
`ImageGalleryItem` are not: their cached data are plain C# objects that survive destruction, so each
handler runs on to a destroyed component and throws `MissingReferenceException`. A multicast delegate
**aborts at the first exception**, so every subscriber registered after the dead one keeps the old
language. Half the UI, with an exception in the log that names none of it.

**M68, found by both reviewers and worse than M7.** `Core.Awake` destroys a duplicate with
`DestroyImmediate(gameObject)` - which runs `OnDestroy` **on the duplicate** - and `OnDestroy` set the
*static* `_isSet = false` unconditionally. Nothing sets it back; `CoreSetupComplete` runs once, on the
original. So a second Core anywhere leaves the real one running while **every `if (!Core.IsSet) return;`
in the application bails forever**, silently. `CLAUDE.md` already says to check `Core.IsSet` first when
something does nothing; this makes it false while everything looks healthy. `if (_instance == this)`.
One line. It is also the mechanism that armed M7.

**M69 logged.** `LocalizationSettings` calls `ChangeCurrentLang(defaultLanguage)` at boot with
`refresh: false`, and both languages initialise to `Langs.PT` - so for a PT-first project the equality
check returns early and **no subscriber is ever notified**. It looks fine because `MultiLangText.Start`
self-calls, but that self-call is behind `if (!Core.IsSet) return;`, so a component whose `Start` beats
boot keeps its design-time Inspector text for the session. Not fixed: `refresh: true` makes the
broadcast fire but subscribers whose `Start` has not run still miss it, so the ordering wants tracing
first.

**Also added:** one `Development.Log` before the invoke, naming the language and the listener count -
because "the language button does nothing" had three indistinguishable causes and no evidence for any of
them. It is `Development.Log`, so `[Conditional("DO_LOGS")]` and absent on iOS and WebGL; that is the
right level for routine telemetry, and the comment says so rather than leaving it as a hidden
assumption. And `LanguageChangedEvent = null;` joins Core's domain-reload reset block - it is the one
static there that accumulates references to destroyed objects, and now that it is an `event`, that block
is the only place that *can* clear it.

**On UnityEvent**, since it came up: not for this one. A `static` field gets no Inspector, which is the
only thing UnityEvent buys; making it an instance field to get one would route every subscriber through
`Core.Instance`, reintroducing the dependency this fix removed from `OnDestroy`. And `RemoveAllListeners`
is public, so the "anyone can wipe every subscriber" half comes straight back. All three subscribers are
scripts, not designers. If designer wiring is wanted, a small `MonoBehaviour` holding a `UnityEvent` and
forwarding from `Core.LanguageChangedEvent` gets it per-instance without touching Core - the same shape
as `DownloadableImage.onLoadCompleteEvent`.

## Test plan

**1. The listener count is visible, which is what makes the rest testable.** Play, change language from
the settings panel or a `LanguageToggle`.
- **Pass:** Console shows `Language changed to [EN], notifying N listeners.` with N matching the number
  of `MultiLangText`/`TextPanel`/`ImageGalleryItem` components alive in the scene.
- **Fail:** no line at all - meaning `ChangeCurrentLang` early-returned because the language was already
  current, which is M69's shape rather than this fix failing.

**2. Counter-test - text actually changes.** Same switch.
- **Pass:** every localized label updates **and** the count in step 1 is non-zero. The count alone
  proves subscription, not delivery; the screen proves delivery.

**3. The detach happens, which is M7 proper.** With the Console filtered to the language line, load a
screen with localized text, leave it, and switch language.
- **Pass:** N **drops** by the number of components that were destroyed.
- **Fail:** N keeps climbing across screen changes - the detach is being skipped, which is the defect.
  This is the step that distinguishes fixed from not; step 1 passes either way.

**4. The duplicate-Core fix, M68.** Drag a second `Core` prefab into the scene and press Play.
- **Pass:** the duplicate is destroyed, `Core :: Boot complete.` still appears, **and** step 1 still
  produces a listener line when you switch language.
- **Fail:** the boot line appears but nothing responds afterwards - `IsSet` was clobbered, which is
  precisely what this fixes. Remove the duplicate afterwards.

**5. The `event` keyword, compile-time only.** In any scratch script write
  `Core.LanguageChangedEvent = null;`
- **Pass:** `CS0070` - the event can only appear on the left of `+=` or `-=`. That error *is* the fix;
  delete the line afterwards.

**What this cannot reach.** M7's own symptom needs a duplicate Core to arm, so step 3 tests the detach
rather than the leak it prevented - honest, and the reason M68 is in the same commit. The domain-reload
reset line only matters with *Enter Play Mode Options* enabled, which this project has off, so it is
untested here. Nothing is verified off Windows, where the new log line does not compile at all.

### M69 - not a defect (v0.34.1). Logged one day, disproved the next.

I logged M69 yesterday from a `silent-failure-hunter` finding during M7, and wrote it up as a live
defect. Checking it took twenty minutes and it is **not one**. Everything the entry asserts is literally
true - `SetLanguages` does call `ChangeCurrentLang(defaultLanguage)` with `refresh: false`, and for a
PT-first project the equality check does return early without notifying anyone. Three measured facts
make it harmless:

1. **There are no subscribers at that moment.** `SetLanguages` runs inside
   `AppDataController_OnDataLoadedEvent`, which is *before* `LoadNextScene()`. A sweep of every `.unity`
   and `.prefab` finds `MultiLangText` in **nothing at all**, and `TextPanel`/`ImageGalleryItem` only in
   `Resources/Prefabs/`, instantiated later. The broadcast reaches an empty invocation list either way,
   so `refresh: true` - the obvious fix, and the one the entry proposed - would change nothing.
2. **Every subscriber initialises itself**, which is the correct design for a component that starts
   after the broadcast. `MultiLangText.Start` self-calls `OnLanguageChanged()`; `TextPanel.SetData` and
   `ImageGalleryItem.SetData` both call it as their last statement.
3. **The `Core.IsSet` guard I claimed would block the self-call is true by then.** `_isSet = true`
   happens in `CoreSetupComplete`, which precedes `LoadNextScene`, so a component in a later scene
   passes it. The "keeps its design-time text forever" case needs `IsSet` false at a subscriber's
   `Start`, which means boot failed (C3) or a duplicate Core clobbered the flag (M68, fixed yesterday).

**Kept from it:** the early return was the one outcome in `ChangeCurrentLang` with no log at all, so
"nothing happened" was indistinguishable from "fired into an empty list" - which is exactly what
yesterday's listener-count line was added to disambiguate, and it sat *below* the return. One line.

**The lesson is the one this session keeps teaching, now from the other side.** I have spent two days
finding that register entries overstate; this is an entry *I wrote*, from a review finding, less than a
day old, doing the same thing - asserting a consequence from reading the code without checking scene
membership or boot ordering. The fifth not-a-defect in the register, and the first one that was my own.

## Gotchas hit
- **`using EnigmaVirtual;` does not reach `EnigmaVirtual.Components.Video`.** C# does not import child
  namespaces. Caught by both reviewers as a hard compile break in the new file.
- **A `UnityEvent` Inspector binding cannot resolve an extension method, and fails silently.** Worth
  remembering whenever an instance method is moved out of a class in this codebase.
- **Sixth `utf-8-sig` BOM incident**, on `TextureCacheLoader.cs`. The rule in my notes is right —
  preserve rather than assume — but I wrote a fresh helper that assumed anyway. The recurring failure
  is not the rule, it is writing a new throwaway helper for each task and re-making the choice.

## Focus
Worklist items 1-5 in one sitting: H5, H15, C5, M12, M13 - all rated S, all reviewed before commit.

## Changed
- **H5** `ConfigManager`: the reflection merge is gone, replaced by `JObject.Merge` at the JSON level.
- **H15** `RawKeyInput`: the two hook procs are `static readonly` fields, so the GC cannot collect a
  delegate Windows is still calling.
- **C5** `ActionExtensions`: both `InvokeLater` overloads deleted.
- **M12** `FileManager.LoadStreamingFile` and `Api.LoadJsonFile`/`SaveAsJsonFile`: `File.ReadAllText`
  / `WriteAllText` with try/catch, replacing undisposed readers and writers.
- **M13** `AssetManager` clamps `downloadThreads`/`chunkSize` (matching `TextureCacheManager`), and
  `Split` clamps defensively. Logged at the clamp sites.

## Decisions
- **C5 deleted rather than fixed** -> zero callers, smaller diff, and it stops the next project
  reaching for a helper whose name gives no hint it cannot work. It is a compile break for any
  branched project that calls it; loud, but real.
- **H5 merged as JSON, not as objects** -> reflection over a deserialized object cannot tell "key
  absent from the operator's file" from "key present and equal to the field initializer", and that
  distinction *is* the feature. Walking fields instead of properties would not have fixed it.
- **M13's clamp logs at the call sites, not inside `Split`** -> with both callers clamping first,
  `Split`'s guard can never fire, so logging only there would have left an invalid `downloadThreads`
  as silent as before. `Split` keeps its guard as a backstop for a future caller.
- **Did not touch `MainController.OnDestroy`** despite M38 being a real H15 residual: that file has
  uncommitted work in it, and entangling someone else's in-progress change with a fix commit is worse
  than carrying the finding for one more session.

## What the reviews caught
Both agents ran before the commits, on the real diff.

`silent-failure-hunter` found the worst of it, and it was in my own H5 fix: `File.WriteAllText`
truncates before it writes, so rewriting the site's only `settings.json` on **every boot** - even when
the merge changed nothing - opens a data-loss window for a power cut or an AV lock. Worse, the catch
around it logged "The deployed file was left unchanged", which would be a lie precisely when the write
was the thing that failed, and the next boot would blame the operator's file. Now: skip the write
entirely when `JToken.DeepEquals` says nothing changed, write via temp file + `File.Replace`, and split
the try/catch so the message matches what actually happened.

It also found that M13's new `LogError` inside `Split` is **unreachable** - both callers clamp
upstream, so an invalid `downloadThreads` would have stayed 100% silent, which was the defect. Moved.

`code-reviewer` found `MergeNullValueHandling` defaults to `Ignore`, so an operator's explicit `null`
would be silently overwritten and then erased from their file on write - and the code being replaced
had set `NullValueHandling.Include` with the comment "critical for seeing explicit nulls", so the
intent had been dropped rather than decided. Also `DateParseHandling.DateTime` is the `JObject.Parse`
default, so a date-shaped string setting would be silently reformatted; and M12 was only half done -
the register names `Api.LoadJsonFile`/`SaveAsJsonFile` explicitly and I had missed them.

Three new defects logged rather than fixed: **M38** (the hook installs with no log on failure, and
`OnDestroy` can skip the unhook - in the Editor that survives a domain reload, which is H15 again),
**M39** (`CopyFile` has no failure branch, so the persistent config is silently never created), **M40**
(`PlayerPrefs["Settings"]` silently beats `settings.json` once the panel has been used).

### C3 + M34 + M35 - the boot watchdog and the two download defects that needed it (v0.10.0)

Done together because they interlock: C3 catches a boot that stops, M34 catches one that crawls
uselessly (which C3 cannot see, because it is progressing), M35 stops the crawl being destructive.

**C3.** Every hop calls `Core.MarkBootStage`; a coroutine armed at the top of `Core.Awake` - before
the settings parse, so it covers that failure too - fires when nothing changes for a stall budget.
Stall, not total: a legitimate first-run download outlasts any fixed budget.

**M34.** The cancel threshold now also runs on the download path, and the `failedRemoteJson`
conjunct is gone. Only *connection* failures count toward it.

**M35.** Downloads go to `<file>.part`, swapped in with `File.Replace`/`File.Move` on success.

**Both reviewers blocked the first version, and the findings were mine.**

`code-reviewer` and `silent-failure-hunter` independently found the same two worst ones. First: no
stage was marked *inside* the asset phase, so the 90s budget had to cover the whole download - two
assets hitting the 60s request timeout back to back would have put "STARTUP FAILED" on a client's
screen mid-boot. The per-asset events already existed for the preloader readout; they just were not
wired to the watchdog. Second, and worse: `_bootComplete` was set on entry to `LoadNextScene`, but
with the shipped `UseAppInfo` the real `SceneManager.LoadScene` is several unguarded callbacks later
(a LeanTween completion, and a `CoreSystemUI.Show()` that silently does nothing if `_appInfo` is
null). So the watchdog disarmed itself immediately before the one hop it most needed to watch: a
stuck tween left the app on the splash forever with a log ending in "Boot complete." Now marked at
all three real `LoadScene` sites.

Third: the watchdog *claimed* "the app will not start" while having no power to prevent it, and
`yield break`d, so a later stall was silent. Now it latches `_bootFailed`, which `LoadNextScene`
honours, and keeps watching.

On M34 they caught that the abort still could not fire on a fresh install - it sat inside
`if (File.Exists(...))`, so with no local files the HEAD branch never runs, and the 6.5-hour case my
own comment claimed to have fixed was untouched. Also that dropping `failedRemoteJson` conflated a
404 with a dead host: three stale CMS references would abort the chunk, abandon brand-new assets, and
log "the host is very likely unreachable". Now only `ConnectionError` counts, 404s go to the missing
count, and the abandoned remainder is counted before the bail since `yield break` skips the summary.

**One thing I added on my own after the reviews**: the latch makes a false fire severe - it refuses
to boot - so the budget is now `max(90s, requestTimeout * 2)`. The longest gap a healthy boot leaves
between marks is one network request, and a project raising `timeout` past 45s would otherwise have
made the watchdog fire on a working install.

**A doc error the cross-check caught**: M13 had been dropped from the worklist entirely when it was
marked partly-fixed last session. Partly-done items belong in the list. The register/worklist
cross-check is now the thing I run instead of trusting the header arithmetic - the header had also
drifted into saying both "ends at 50" and "row is not 51".

**Verified:** braces on all three files; all three `SceneManager.LoadScene` sites preceded by
`MarkBootComplete`; the abort reachable from both the HEAD and the download path; register and
worklist agree exactly (48 rows, no gaps, nothing missing or stale). **Not verified:** compile, and
none of this runs on a healthy boot with the shipped config - `AssetDownload.isActive` is false.

**Not touched:** the 2.5s `WaitForSeconds` in `SetupAssetManager_IE` is in Tiago's uncommitted work,
not this change. Both reviewers flagged it; it is his call.


### Two defects found by reading Editor.log, not by review (v0.10.1)

Tiago asked how to test the fixes; I checked the current Unity log first. It contained a complete,
correct C3 firing - broken settings.json, `Error parsing core settings JSON` (M26, which logged
nothing at all before this session), then 90s later `BOOT STALLED ... Last stage reached was
[Core.Awake]` and a STARTUP FAILED notification - plus a `Boot complete.` from a healthy run, so no
false fire. The budget was 90s rather than 120s because `Core.settings` was null and the
null-conditional timeout read fell back to the floor, which is the path it exists for.

It also contained two defects in code committed hours earlier, neither of which either reviewer had
caught, because both are only visible with real numbers:

**The abort threshold scaled the wrong way.** `max(3, count/10)` at 4 x 60s per failure means a
225-asset set needs 88 minutes before giving up - the hang M34 exists to prevent. Now three
**consecutive** connection failures: bounded regardless of catalogue size, and a better diagnosis,
since a dead host produces an unbroken run and scattered 404s do not.

**The summary said `3 connection failure(s) ... 0 will be MISSING at runtime`.** Splitting the
counters so a 404 would not be mistaken for a dead host had routed connection failures away from the
missing tally entirely.

Fixing that over-corrected, and the review caught it: counting them made a fully-cached kiosk against
a dead host report "225 asset(s) will be MISSING" while also saying it would "start with whatever
media is already on disk" - both in the same sentence. Those assets are on disk and render fine. So
there are now three tallies, because two was never enough: **missing** (not on disk), **stale** (on
disk, could not be refreshed), **abandoned** (never checked, unknown). The lesson is narrow and
worth keeping: a counter that answers two questions at once will be wrong in both directions in turn.

Also from the review: the download path counted *any* failure as a connection failure while the HEAD
path correctly excluded 404s - and the download path is the only one a fresh install takes, so three
dead CMS references would have abandoned a chunk while blaming the network. And the success reset sat
after the file swap, so a download that arrived but failed to move into place left the failure streak
intact.

`filesFailedToDownload` became write-only once the abort went consecutive, and was deleted with its
reset - a field added earlier the same day for H10.

**Not verified:** compile. The log run that produced these findings was against `10.255.255.1` with
`timeout: 60`, which is why it was still going after 16 of 225 assets.


### The BuildValidator batch - M33, H14, L12 and a new L13 (v0.11.0)

Four rules in one file, because they are all the same shape: a state that is fine in a working tree
and dangerous in a build.

- **M33** - fails a release build when `VERSION.txt`, `bundleVersion` and `Descriptor.Version`
  disagree. The lag itself is inherent to the domain-reload timing and is *not* fixed; what is fixed
  is that it can no longer reach a build. It needed a catch-up commit four times in this one session,
  which is what moved it from "annoying" to "gate it".
- **H14** - fails a release build still carrying the default panel password. Partly fixed only: the
  password is still compared in plaintext and there is still no lockout, so the gate stops the
  default *shipping*, it does not make the panel secure. The register now says so.
- **L12** - fails a release build whose shipped `settings.json` enables `cleanUnlistedAssets`.
  Enabling it on a site's deployed config remains entirely fine; baking it into a build is not.
- **L13** (new) - fails **any** build when the config folder holds a backup-shaped filename.
  StreamingAssets is copied into the player verbatim, so the `settings_bck.json` that existed
  earlier today would have carried the password, key and client hostname to a site. It was caught
  by eye, which is not a control.

**Two design decisions worth keeping.**

*Release-only for three of the four.* The first version hard-failed everything, and the dry-run
showed it would block **every** build of this base project - the template ships the default password
by definition. A gate that stops you making a test build is a gate people delete. So the deployment
risks are release-only and the leak risk is not, since a credential in a dev build leaks just as
well. The skip is logged rather than silent, because an unannounced gate is worth very little on the
day it matters (M26's lesson applied to my own code).

*All rules run before any throws.* Failing on the first means an operator fixes one thing, waits for
a build, and finds the next. A build is not a fast feedback loop.

Matched on backup-shaped *name fragments* rather than an allowlist of permitted files, so a derived
project can add its own config without editing the framework.

**Verified by dry-run** against the real tree: a development build passes, a release build fails on
the default password and on `cleanUnlistedAssets` (true in the working copy, false in the committed
one). From a clean checkout a release build fails on the password alone - which is correct and is
the point. **Not verified:** compile, and no actual build has been run through it.


### H19 - a wrong-type bind that was quietly overwriting the descriptor (v0.11.1)

Found while fixing a compile error in the BuildValidator batch, which is the only reason it surfaced
at all: I copied `ApplicationDescription` from `AppVersionSync` without its `using EnigmaVirtual;`,
and chasing that turned up a *second* `ApplicationDescription` in a `Gema` namespace.

`PositionerEditor` bound to that legacy copy, so `LoadAssetAtPath` returned null every single time
and the `if (_appData == null)` fallback ran `CreateAsset` over `Descriptor.asset` - replacing the
project's real descriptor with a blank one. This is the destructive create-branch M28 concluded had
been left only in `AppDescriptor`. It survived because a wrong-type bind produces an ordinary-looking
null, and a null check is exactly what nobody re-reads.

The descriptor is intact (`Slug: unityDefault.app`, `Year: 2025`), so it had not fired yet - because
the *same method* then read `StreamingAssets/assets.json` unguarded, and that file does not exist
here, so the constructor threw before Unity could finish building the inspector. One bug was hiding
behind another.

**Which made the fix more interesting than it looked.** Guarding the file read made the inspector
render for the first time, and review caught what that exposed: with no asset table `_data` stays
null, so `GUI.enabled = !_positioner.Locked || _data == null` is *always true* - and "Set & Destroy"
calls `SetPosition()` (which early-returns when locked) and then `DestroyImmediate` regardless. So
fixing a silent data-loss bug had made a silent component-deletion bug reachable. Now
`!Locked && _assets != null`.

Fully qualified rather than adding a using: `Gema` is still needed for `Positioner` and `AssetsVO`,
and importing both namespaces makes `ApplicationDescription` ambiguous (CS0104).

Also folded in two pre-existing NREs on the same line of reasoning - `_image` null when the
Positioner is not on an Image, `_image.sprite` null on an Image with no sprite - and gated the
missing-assets.json warning to once per domain reload, since the constructor runs on every selection.

**Left open deliberately:** the `Gema.ApplicationDescription` copy still exists, referenced by no
asset. Deleting it is a separate decision and a separate blast radius - branched projects may bind
to it exactly as this file did.

**Verified:** braces; both `GUI.enabled` sites (Reload Data correctly stays enabled so the missing
file can be added and retried); the create path is gone from code and survives only in a comment;
the other four descriptor consumers all null-guard and only `AppDescriptor` still creates.
**Not verified:** compile.


### H13 + H1 - and a fix that created the bug it was removing (v0.12.0)

**The register was wrong about the size of H13, in both directions.** It claimed "~13 others". A scan
found 9 classes with the `if (!Core.IsSet) return;` pattern and only one - `ActivityMonitor` - with a
per-frame dereference. Then review corrected me in turn: in *this* project even that is unreachable,
because `MainController.Init()` creates these components after `Core.IsSet` is true and nothing
scene-places them. So the fix is defensive for derived projects, not a live bug here. My code comment
claimed "a NullReferenceException every frame" as present tense; it now says what is actually true.
That is the same over-claim I have corrected three times today in other people's text and written
twice in my own.

**The one that matters: my own fix introduced the failure it was removing.** Adding `OnDestroy` to
`MainThreadDispatcher` to clear the static opened a TOCTOU - `RunOnMainThread` read `Instance` three
times (guard, lock, enqueue), so a worker thread could pass the null check and then dereference null
on the lock, on a socket thread, where `SocketConnection`'s catch swallows it. The old code read it
three times too and was *benign precisely because nothing ever cleared it*. Both reviewers found it
independently. Snapshotted into a local now.

Two rationales in my comments were also wrong and are corrected on the record: the dispatcher's static
cannot be stranded by a scene unload (Core is `DontDestroyOnLoad`, so `OnDestroy` realistically only
runs at quit), and `RunOnMainThread`'s throw was not escaping into the void - its only caller wraps it
in a try/catch. The change is still right; the reasons were not.

**`PhidgetsManager` was wrongly excluded.** I put it in the "no per-frame message, safe" group. It has
the same shape as `SerialPortsManager`: `_controllers` is null after the bail, and it is dereferenced
by public `SetState` **and** by `OnApplicationQuit` - which Unity delivers to disabled components, so
`enabled = false` does not cover it, and an NRE there aborted `CloseAll` and left every board's handles
open at shutdown, when nobody is reading a log.

**Also fixed while in there:** both serial send methods looped zero times and returned as though they
had worked when the port name matched nothing - a dropped hardware command reported as a send. And
`MainController`'s duplicate branch now sets `enabled = false` before `Destroy`, because `Destroy` is
deferred while `Core` resolves `main` with `GetComponentInChildren` under undefined Awake ordering, so
Core could bind to the copy that is about to die and call `Init()` on it. Worth noting that this guard
is *live code for the first time* - as an instance field it could never fire.

**Logged, not fixed:** H20 - `UnitySerialPort.SendSerialData` raises its sent-event and sets
"Sent data" when the port is null, so the guard added here advertises "the command was NOT sent" for a
case that cannot happen on Standalone while the case that does happen on site still reports success.
That is the most likely of today's findings to reach production unnoticed. Plus L14 (work queued to a
dispatcher between its last Update and OnDestroy is dropped silently) and L15 (two dead guards that
read as protection).

**Verified:** braces on all five files; `Development` resolves in each - `MainThreadDispatcher` is in
the global namespace and needed a new `using EnigmaVirtual;`, the same trap that hit BuildValidator and
MiscExtensions earlier today; every read of `controllers`/`_controllers` is guarded or provably
post-assignment; register and worklist agree exactly (82 entries, 47 actionable, 47 rows).
**Not verified:** compile.


### H20 - and a premise I had wrong all session (v0.13.0)

**Correction first: the serial subsystem is LIVE in the shipped template.** `SerialPorts.isActive`
is `true` with COM3 active in the committed `settings.json`. I had been treating it as dormant, in
this log and when triaging H13. It is Windows-only, but it runs. And because `keepAliveInterval`
defaults to 30s while the JSON omits the key, `KeepAliveLoop` is the **only code in this project that
writes to a port** - unattended, every 30 seconds, forever.

**The defect.** `SendSerialData` wrote only `if (SerialPort != null)` but then set
`portStatus = "Sent data"` and raised `SerialPortSentDataEvent` unconditionally, so a null port
produced a complete success report with nothing written. It also had no `IsOpen` check and no `try`,
so a closed port threw an unhandled `InvalidOperationException` out through `SerialPortsManager` into
App code.

**I deliberately did not just copy the sibling.** `SendSerialDataAsLine` guards correctly and then
returns *silently* - the same defect in the other direction. Copying it would have fixed the lie and
kept the silence. Both share a reporting `CanWrite` now, and both return `bool`, so App code has a
failure channel instead of only a log line.

**Review then showed the fix was incoherent with everything around it**, which is the part worth
keeping. `SerialPortOpenEvent` fired *outside* the try, so a failed open still announced "Open!" one
line after the new "did not open" error. The open failure's actual reason - "Access to the port
'COM3' is denied" - went to `Debug.Log` while the caller reported at Error with no cause attached. And
the keep-alive had its own duplicate pre-guard that returned early, so **the one path that writes
unattended was the one path that would never have reported a dead port**. Adding an error message to
a method nobody calls, while the method everybody calls stays silent, is not a fix.

**One thing I caught that review did not.** With the keep-alive firing every 30s, reporting each
failure would put an error in a kiosk's log twice a minute for as long as it runs. `CanWrite` reports
the *transition* and says so in the message, then stays quiet until a write succeeds again.

Also null-guarded both `ShowNotification` calls in `OpenSerialPort` - they sat outside any guard, and
`Core.notificationManager` can legitimately be null, in which case the throw would have propagated
out of the coroutine and silently abandoned every remaining configured port.

**Logged, not fixed:** M41 - `OpenSerialPort` replaces the handle without closing the old one and
never resets `isRunning` before its try, so a reopen that throws leaves `IsRunning` true against a
closed port. That is a false OK for the open check added here. Dormant as the framework uses it (one
open per fresh component), armed by any App-side reopen.

**Version bumped minor, not patch:** both send methods changed `void` -> `bool`. Source-compatible
for callers that ignore the result, but it is a public surface change on shared framework code, which
CLAUDE.md says to treat as a breaking-change candidate for every branched project.

**Verified:** braces; every return path of both send methods returns a bool with no bare returns;
`GUIManager`'s call site discards the result as a statement, which is legal; `IsRunning` is set
synchronously inside `OpenSerialPort` before the thread/coroutine starts, so the manager's new check
cannot false-alarm on a healthy port. **Not verified:** compile, and nothing here has been exercised
against real hardware - which is exactly where it matters.

**This is the fourth defect in this file's error reporting found today**, all the same shape: a
failure that reports success or nothing. The file deserves a dedicated pass rather than more spot
fixes.

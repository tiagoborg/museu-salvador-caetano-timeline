# Session log — 2026-08-17

## Focus
The `CoreSystemUI` preloader defects: M77 + M78 together (they share a file), then M102, which
fell out of M78 and needed a different mechanism.

## Changed
- `CoreSystemUI.Init()` re-resolves `textureCacheManager` from `Core.main.TextureCacheManager` when
  the `Awake` lookup found nothing (**M78**).
- `CoreSystemUI.Init()` reports once, at `LogError`, when `assetManagerOutputText` is null and the
  phases that write to it will actually run (**M77**). Eight handlers previously returned silently.
- The two pre-existing `Development.LogError("… not available")` messages in `Init()` now name the
  cause and the remedy. A silent-failure fix whose own error says nothing useful is half a fix.
- **M102 filed and then fixed** — the `assetManager` half of M78. It needed a different mechanism,
  so it was filed first and fixed second, in its own commit.
- `MainController` gained a read-only `AssetManager` property, and `CoreSystemUI` gained an
  `OnDisable` (it had no teardown hook at all).
- **M96 + M103 (v0.49.8)** — `NotifyController.Show` cancels the outgoing tweens and clears a pending
  auto-hide; the entrance move runs unconditionally. **M104** filed and deliberately not fixed.
- **M43 (v0.49.9)** — one `internal` helper, `WebRequestExtensions`, now resolves every
  settings-driven `www.timeout` in the framework. Five call sites across `Api`, `AssetManager` and
  `TextureCacheManager`. `Api` resolves 0 to 30 and caps at 300; the two download blocks resolve 0 to
  **3600** and cap there.
- **M105 (v0.49.9)** — `this.StopCallLater(...)` → `MonoBehaviourExtensions.StopCallLater(...)`. One
  line, and v0.49.8 did not compile without it.
- Doc comments for the two `AppDataSettings.uint timeout` fields, which had none, and corrections to
  `ApiSettings.timeout`'s remark and `FileDownloader`'s comment — both described the divergence M43
  removed.

## Decisions
- **Fixed M78 for the texture manager only, and filed the asset manager separately.**
  `SetupTextureCacheManager` runs *inside* `MainController.Init` (`:354`), so the manager exists by
  the time `systemUI.Init()` is called and re-resolving works. `SetupAssetManager` is called from
  `AppDataController_OnDataLoadedEvent` (call at `:615`) — after `Init` on the remote path — so the same
  re-resolve would still find null. Same shape, different fix, so a different entry.
- **Gated M77's report on `AppData.isActive && AssetDownload.isActive`**, not on
  `AssetDownload || TextureCache` as first written. Both reviews caught it over-triggering; tracing
  it myself made the case stronger than they reported. The texture pre-cache is reached from
  `AssetManager_onAssetCleaningCompleteEvent` (`:692`, reaching `CacheAssets` at `:705`), so it is downstream of the **asset** phase —
  `TextureCache.isActive` alone can never produce a readout, and needs no term. The coupling is
  stated in the comment so a future entry point does not silently escape the gate.
- **Kept `LogError` rather than `LogWarning`**, knowing a branch that deliberately ships no preloader
  Text now gets a red line every boot. `LogWarning` is `[Conditional("DO_LOGS")]` and therefore
  invisible on iOS and WebGL. **That rationale was overstated and is corrected here:** `DO_LOGS` is
  defined for `Android` and `Standalone`, and Unity's Standalone group is Windows, macOS *and* Linux,
  so only two targets strip it, not four. The decision stands on the two that do.
  Recorded in `reviews.md` as an accepted trade rather than left implicit.
- **Kept the dead `Core.main != null` guard.** Both reviews confirmed `Core.cs:311` dereferences
  `main` one line before `systemUI.Init()`, so it cannot be null. Harmless, and the comment does not
  claim it guards a real case.
- **M43: the ceiling belongs to the caller, and so does the default — that second half was the
  mistake.** I parameterised the ceiling, reasoned carefully about why the download blocks need 3600
  rather than Api's 300 (a cut-off download deletes its `.part`, so nothing resumes), and then
  hardcoded a shared 30s fallback that would have made `timeout: 0` *shorter* than the shipped 60 on
  those same requests. Two reviewers caught it independently. **A ceiling only bites a value somebody
  typed deliberately; the default decides what 0 becomes, so it is the dangerous half.**
- **`internal`, not `public`, for the new helper.** Nothing outside the framework assembly touches a
  `UnityWebRequest`, and `CLAUDE.md`'s rule is to widen when a caller appears. The global namespace
  was kept deliberately — that is the recorded position (L17), and this round showed the cost of the
  two anomalies, since `NotifyController` has to spell out `MonoBehaviourExtensions.StopCallLater`.
- **Did not touch `Core.BootWatchdog_IE`, though review twice asked for it.** It sizes its stall budget
  off the unclamped timeout, so a mistyped value disarms the loudest boot diagnostic. Filed as M107
  instead: it changes boot-watchdog *timing*, which deserves its own test rather than riding along in
  a timeout commit, and it has a trade-off to settle first — reading the effective value is correct,
  and also gives a `timeout: 0` project a 2-hour budget that looks exactly like a disabled watchdog.
- **Kept the unreachable non-positive-ceiling fallback** that both reviewers wanted changed, and wrote
  down why: of the three wrong answers available for a bad ceiling, bounded-and-near-normal beats
  unbounded and beats 1 second. Deleting it would make `Math.Min(configured, 0)` assign 0. The doc
  comment now states that it discards a valid value rather than promising a contract it cannot
  enforce.

## M105 — v0.49.8 did not compile, and the pipeline said it did (v0.49.9)

## M43 — `timeout` meant two opposite things; now it means one (v0.49.9)

Five sites, three files, one helper: `WebRequestExtensions.SetTimeout(configuredSeconds, maxSeconds)`.
0 or negative becomes 30; anything above the caller's ceiling is capped. `Api`'s own
`DefaultTimeoutSeconds` const is deleted, so there is one answer to "what does 0 become".

**Decision, with the why: the ceilings are not equal, and unifying them would have been the
regression.** The register's prescription was "make all five clamp, one line each", which reads as
one shared ceiling. `Api` caps at 300 and that is right for a JSON call. Applying 300 to
`AssetDownload` would have been a new defect, because of something the entry does not mention and I
only found by reading the failure path: `www.timeout` bounds the **whole** request, and a failed
attempt calls `TryDeletePartialFile`, so **nothing resumes** — every retry restarts at byte zero. A
ceiling below the honest transfer time does not make a large asset slow, it makes it *permanently
undownloadable*, and the only trace is one "Giving up" line. The two download blocks cap at 3600,
where the ceiling's only job is turning infinity into a finite number. `AssetDownload.isActive` ships
**true**, so this is the live path, not a dormant one.

**A second defect fell out of measuring rather than reasoning.** I wrote in the helper's docs that
the old `(int)` cast of a `uint` field "reached the setter as a negative int". Measured, it reaches
it as **0** — Unity stores a negative timeout as zero, which is *wait forever*. So the cast turned an
absurdly large timeout into exactly the unbounded wait it looked like it was avoiding. Comment
corrected to say what was measured.

**Verified: 17 of 17, and unusually for this codebase all of it here.** `SetTimeout` is a pure static
over a `UnityWebRequest` — no `Core.settings`, no play mode, no arranged failure. Five are
counter-tests: shipped 60 → 60 on both download blocks, Api's 30 → 30, a value sitting exactly on the
ceiling is not capped, and a legitimate 1200s asset wait survives. The probe also reflects each call
site's private `MaxTimeoutSeconds`, so it cannot pass while a site names the wrong ceiling.

### What review changed, and it was the half I was confident about

My first version parameterised the **ceiling** per call site and hardcoded a shared **30s** default.
`code-reviewer` and `architect-reviewer` independently said the same thing: that inverts operator
intent. `timeout: 0` on a download block would have resolved to 30 — *shorter than the shipped 60*,
and the shortest bound anywhere in the framework — on precisely the requests that cannot resume. I
had reasoned carefully about the ceiling and then not applied the same reasoning to the default,
which is the number that actually decides what `0` becomes.

The fix is that both numbers are arguments. `Api` resolves `0` to 30 because there `0` means *unset*;
the download blocks resolve it to their **ceiling**, because there `0` has always meant *no limit* and
the nearest bounded reading of that is the largest legal wait. Worth writing down as a rule: **a
ceiling only bites a value somebody typed deliberately, so the default is the dangerous half.**

The probe now checks this at the **source** level too, because it is a call-site property no runtime
assertion can see: each download site must pass its ceiling in both positions. And one assertion
states the *rejected* design outright — a download `0` must not resolve to 30 — since a clamp that is
merely present looks identical to one that is right.

Two more from review, both taken: the helper is `internal`, not `public` (nothing outside the
framework assembly touches a `UnityWebRequest`, and `CLAUDE.md` says widen when a caller appears);
and three stale doc sites the fix invalidated — `ApiSettings.timeout`'s remark, which was the only
written record of the download semantics, `FileDownloader`'s comment citing those sites as the
exemplar of a trap they no longer have, and the two `uint timeout` fields that had no doc comment at
all despite being the ones an operator edits.

**One finding kept rather than fixed**, with the reasoning recorded because both reviewers wanted it
changed: a non-positive `maxSeconds` falls back to the default, which means it *discards* a valid
configured value — measured, a ceiling of 0 turns a configured 120 into 30. Unreachable while every
call site passes a positive `const`. Of the three wrong answers available for a bad ceiling (`0` =
unbounded, `1` = broken, the default = bounded and near-normal) the current one is least harmful, and
deleting the branch would make `Math.Min(configured, 0)` assign `0` — the exact wait the method exists
to prevent. The doc comment now states what it does instead of promising a contract it doesn't
enforce.

### Two entries filed, deliberately not fixed

**M106 — a clamp is never reported.** The failure is loud (`Giving up on [...] It will be missing at
runtime.`, always compiled); the *attribution* is missing. No line states the timeout in force, so a
timeout against a `settings.json` reading `86400` is not reconcilable by the person holding both. It
cannot be a log inside `SetTimeout` — 200 assets, 200 lines — and every cheap channel is stripped:
`LogWarning` and `LogIf` are `[Conditional("DO_LOGS")]` so they vanish on iOS and WebGL, and `doLogs`
ships `false` on the two where `DO_LOGS` is defined. It needs one ungated report at boot naming key,
typed value and applied value.

**M107 — the boot watchdog sizes its budget off the unclamped number.** `timeout: 86400` now caps
requests at an hour while giving `BOOT STALLED` a 48-hour deadline. Pre-existing, not caused by this
change, and left out on purpose: it alters boot-watchdog timing, which deserves its own test rather
than riding along in a timeout commit. There is also a real trade-off — reading the effective value is
correct by the comment's own logic, but then a project configuring `0` gets a 2-hour budget, which is
accurate and indistinguishable from a watchdog that is off. The likely answer is to do both: read the
effective value *and* have M106's report push the operator to a real number.

**The to-do count went 20 → 22 as a result.** That is the register working, not slipping: two real
defects that nobody had written down are now written down.

## M106 + M107 - a clamped timeout is reported, and the boot watchdog stops lying (v0.49.10)

**M107 was not what its own entry said, and finding that out is most of what this round was.** The
entry said a mistyped `86400` gave `BOOT STALLED` a 48-hour deadline. It did not: the configured value
was **never read at all**. `BootWatchdog_IE` computed the budget once, before the loop, and the
coroutine is started before the settings parse - deliberately, since that parse failing is what the
watchdog exists to catch. Everything before a coroutine's first `yield` runs on the first `MoveNext`
(measured in `eval`), which Unity performs synchronously inside `StartCoroutine` (documented; the
play-mode step is in the test plan). So `Core.settings` was null every time and the budget was
**always the 90s floor**.

**Which inverts the risk.** Not a watchdog that cannot fire, but one that fires *falsely*: the shipped
`timeout` is 60, so one slow asset can exceed a 90s stall budget, and the watchdog **latches** -
`LoadNextScene` then refuses permanently. A boot that refuses is worse than a boot that reports late,
and this is the second time that trade has come up today.

The fix is one change that is right under either reading: `StallBudgetSeconds` is called on every
deadline reset, returns the floor while settings are null, and scales off the *effective* timeout.

**M106** is `Core.ReportClampedTimeouts`, once at `CoreSetupComplete`, naming per key what the operator
typed and what requests will use. `LogError` because it is the only level always compiled. It is silent
on the shipped config, so a line there always means somebody edited a timeout and did not get what they
asked for.

### What review changed, and two of the three were bugs in my new code

- **The `AppData.isActive` gate silenced the one report I had written a comment insisting must never be
  silenced.** `SetupTextureCacheManager` is called outside every `isActive` check, so the loader
  downloads with `AppData` off. Two reviewers found it independently. The probe assertion that let it
  through had encoded the bug as the expectation - it asserted "AppData off reports neither block" -
  which is the second time this session a counter-test has been written to agree with the defect.
- **The budget was ungated while the report was gated**, so a project with downloads off got a 7200s
  budget for a request never issued.
- **The report only fires on a *clamp*, but the budget scales off the effective value regardless.** So
  a perfectly legal `timeout: 1800` silently took the watchdog to 3600s with no log line anywhere.
  `silent-failure-hunter` rated this the likeliest to reach production unnoticed, and it is the one
  finding that needed a design decision rather than a fix: cap the budget, or announce it. **Announce
  it.** A cap below a legitimately long request reintroduces the latching false fire that M107 exists
  to remove. `AnnouncedStallBudget` logs the budget whenever it changes.

### Two more defects, one fixed and one filed

**M108, fixed.** `TextureCacheManager`'s own stall watchdog used a flat 60s while the timeout it must
clear can be an hour - M107's defect in the sibling. Found by `silent-failure-hunter` as an aside
rather than a finding. Fixed because the fix is two lines reusing the helper this round already built,
and shipping M107's lesson applied to one of two watchdogs would be worse than not learning it.

**And the first version of that fix reintroduced the exact trap it was written against** - caught by
my own probe, not by review. It read the timeout as `?? 0`, and on that block 0 means *no limit*, so an
absent block resolved to the ceiling and handed the watchdog a two-hour budget. The probe asserted the
floor and got 7200. Worth keeping as the lesson: **`?? 0` is not a safe default for a field where 0 is
meaningful**, and this is the second time in two rounds that the same `?? 0` has been the bug.

**M109, filed and deliberately not fixed.** The texture pre-cache marks exactly two boot stages for the
whole pass, so `Core`'s watchdog sees one stage string for N images - a healthy 300-image pre-cache
holds it for minutes against a budget of twice one request. M107 improves the magnitude and leaves the
shape wrong. The real fix is per-image `MarkBootStage(..., log: false)` off `onTextureCachedEvent`,
which is what the asset pass already does. Dormant as shipped, since `TextureCache.isActive` is false.

### Decisions, with the why

- **The timeout policy constants moved into `WebRequestExtensions`, one commit after review approved
  them at the call sites.** Justified by new information rather than by taste: a third consumer
  appeared that is not a call site at all (the watchdog needs the *resolved* timeout without issuing a
  request), and two call sites already held an identical 3600 that Core would have made a third copy
  of. `architect-reviewer` was asked directly whether this was churn and judged it the right call,
  noting it also resolves its own earlier finding about three constants cross-referencing each other
  in prose.
- **Named policies rather than numbers at the call site.** `SetApiTimeout` / `SetFileTransferTimeout`.
  The naming is by *request kind*, not by subsystem, which is what keeps a generic extension from
  depending on the settings model.
- **The budget is not capped.** Recorded above; it is the same trade as M96's and it goes the same way.

## L18 + L10 - two low-severity guards, and four malformed register rows (v0.49.12)

**L18** was one guard: `DisplayError` blitted `Resources.Load<Sprite>(...).texture` with no null check,
on the error path - the one least likely to be exercised before a site visit. Both image sites already
guarded the same case and logged, so the framework disagreed with itself. The message names the
*consequence* rather than the fault, which is the part worth copying - and my first version named the
**wrong** consequence. I wrote that the RenderTexture keeps its last frame. It does not: `errorReceived`

is set, which it is by default - and that target texture *is* this RenderTexture. So the surface is
**cleared**, and my message would have sent the reader looking for a frozen video they do not have.
`code-reviewer` caught it by tracing the call order rather than reading the method in isolation, which

**L10 turned out not to be mainly about the exception filter.** The entry leads with the narrow

But the worse defect was the **placement**: the try/catch sat outside *both* loops, so the first process

names which one and says it is continuing.

And `taskkill /F /IM explorer.exe` was unguarded *and* unlogged. Killing the shell is the most
destructive thing this framework does to a machine it does not own, `doLogs` ships `false`, and there

`MainModule.FileName` is deliberately unchanged: `FullRestart` already catches bare `Exception` and logs
the full exception, which the entry's own closing note says.

### What review changed, and one finding worse than either defect

Three of the five findings were in code I wrote this round, and the fourth was a defect the round
walked past.

- **The L18 message named the wrong consequence** (above), and **the guard checked one half**. It tested
  `errorSprite != null` while the precedent its own comment cites - `DownloadableImage` - tests the
  sprite *and* its texture. A sprite whose texture broke on import loads non-null and would have reached
  `Graphics.Blit` with a null source. Parity that was only asserted, not implemented.
- **The `killExplorer` banner promised a restore that a setting can switch off.** It said "OnDestroy
  restarts it, so a clean exit restores the shell" unconditionally, but that is gated by
  `restoreExplorerOnQuit`. With `killExplorer: true` and that flag false, the single message an operator

  now reads the setting.
- **My per-process fix left the identical defect one level up.** The outer catch was re-scoped to

**And L21, which is the one that matters.** `WaitForExit()` in that loop was unbounded. `Kill()` is

## M101 - a serial port that goes away now says so (v0.49.13)

The entry had been open since 2026-08-11 and deliberately unpatched, because it needed a decision:
clearing `isRunning` on *any* exception would stop the loop on the first read **timeout**, and a timeout
is normal traffic on a serial port. Distinguishing "the device went away" from "nothing arrived this
cycle" was the actual work.

**The decision: a consecutive non-timeout failure count.** `TimeoutException` gets its own catch and is
not counted. Anything else, with the port genuinely open, increments; a completed read resets the run -
including an *empty* read, because the port answering is itself evidence the device is there. Under the
limit, report and keep reading, since a USB adapter re-enumerating can throw a few times and recover. At
the limit, clear `isRunning` and say in the log that `IsRunning` will now report false.

**The limit is 5 failures AND a 2s window, and I could measure neither.** `AssetManager`'s
`ConsecutiveFailureLimit` of 3 came from a real run against an unroutable host (M34); there is no serial
adapter here to unplug. The window exists because review pointed out the count alone is not a duration -
five iterations is ~83 ms over five frames, so my own comment claiming it "survives a USB re-enumeration"
was an order of magnitude out. The shape is copied from AssetManager; both numbers are invented, and the
code says so.

**The NRE half is the part that could be measured, and it was the worse one.** The old catch did
`SerialPort.IsOpen` - a second dereference of a field `StopSerialThreading` sets to null concurrently -
so a stop racing a read threw *out of the catch* and killed the read thread with nothing logged at all.
The catch now captures the field into a local first, and a null or closed port returns quietly without
counting, because that is what a deliberate stop looks like from inside the loop.

### What review changed, and it refuted most of the fix

Three premise corrections first, all verified directly rather than taken on trust:

- **`SerialPorts.isActive` ships `false`**, on **COM7**. H20 has said `true`, COM3 since v0.15.0 flipped
  it, and I repeated that to the reviewer and in the §5b row I had already written. So all of this is
  dormant behind one flag here.
- **There is no periodic health check.** `IsRunning` is read in exactly one place outside the file -
  `SerialPortsManager.cs:112`, inside `InitSerialPorts`, **once at boot**. M101's own entry called the
  stale `true` "a permanent false OK for the health check"; nothing re-reads it, so clearing it is read
  by nothing. The real cost was always the silence.
- **`LoopMethods.Threading` is unreachable.** `LoopMethod` is never assigned anywhere, so the `Coroutine`
  initializer always wins - which makes the marshalling I added a guard against a future assignment
  rather than a live thread-safety fix.

Then the findings, and two of them made the first version of the fix useless:

- **The quiet return did not clear `isRunning`, and inferred intent from `IsOpen`.** A removed adapter's
  stream disposes itself, so `IsOpen` goes false *with no exception* - identical to a deliberate close if
  `IsOpen` is all you look at. The loop returned quietly and then span forever on the open check, no
  count, no log, `IsRunning` still true. **M101 closed on paper and unchanged in fact, for exactly the
  failure it was written for.** Intent now comes from an explicit `stopRequested` flag.
- **And my probe asserted that as correct.** Assertion 4 read "a null SerialPort does not clear
  isRunning - a closed port is a stop, not a fault" and passed. It encoded the defect as the expectation.
  Third time today: M96's text-swap test, L18's... and this. The pattern is specific enough to name -
  **when a fix turns on distinguishing two cases, a counter-test that only exercises one of them will
  agree with whichever behaviour exists.** The flag made the two cases separable and the assertions had
  to be inverted.
- **`ParseSerialData` ran inside the read's `try`**, so an App subscriber throwing was reported as
  `Serial read failed` - the cable blamed for someone else's bug, at Error, once per message, forever,
  and unable to reach the limit because the reset ran before the parse. Hoisted out with its own guard.
- **`CloseSerialPort` stopped the loop *after* its catch**, so a throwing `Close()` - which is what a
  removed adapter does - escaped with the loop still running and the handle held, defeating the
  `OnDestroy` change in the one case it existed for.
- **The limit counted iterations with no delay**: ~83 ms over five frames, so "chosen to survive a USB
  re-enumeration" was an order of magnitude out. It now needs a 2s window as well as the count.

### Two things in scope that were not the counter

The notification in that catch called `ShowNotification` from the **read thread** in
`LoopMethods.Threading` - a Unity UI call off the main thread, which throws. Marshalled through
`MainThreadDispatcher` now, and null-guarded. Worth noting the shape: the defect was invisible because
the only path that reaches it is the path where the hardware has already failed.

And `OnDestroy` unsubscribed its five events and did nothing else, leaving the read thread running and
the COM handle held by a component that no longer exists - so the next open failed with access denied and
nothing connected the two. It closes the port now.

### On editing `External/`

`CLAUDE.md` records this package as already a fork rather than pristine upstream - it calls `Development`
in seven places - so editing it is in bounds. But this is a behaviour change in shared code that every
branched project inherits, and `IsRunning` changing from "stays true" to "goes false when reads fail" is
exactly the kind of thing a project may have built an assumption on. That is why it gets a §5b row
saying so, rather than only a register entry.

## M45 - one boot order on every target, and the fix's own first version was worse (v0.49.18)

M45: Android completed boot asynchronously on launch 1 and synchronously on launch 2, and the two ran

### The first version made things worse, and three reviewers caught it independently

Returning the text unconditionally made the empty string mean two incompatible things.
`LoadStreamingFile` returns `""` for a missing file, for a `ReadAllText` that threw, **and** for a
`settings.json` that exists and is zero bytes - while `Core` read empty as "a fetch is in flight, wait

The zero-byte case is the one that matters and `silent-failure-hunter` isolated it: `File.Exists`

straight regression on the C3 path, on every platform, on the shipped config.

returns **`null`** only when it started a fetch. Any string - empty or not - means a read happened.

I measured `JsonUtility.FromJson<T>("")` before writing the empty-string handling, got

whitespace, and type-dependent between class and struct. Both are now in the probe as assertions

## M86 - the offline fallback stopped eating its own cache, and the entry was wrong about why (v0.49.19)

M86: on Android and WebGL, `LoadLocalData` hands the local path to `LoadRemoteData`, which re-reads it
and writes it back to the cache path. The entry said the consequence was that M42's age readout reports
"just now" forever.

**It does not, because there is no age readout on that route at all.** `LoadLocalData`'s
`#if UNITY_ANDROID || UNITY_WEBGL` branch `return`s at the `StartCoroutine` line, *before* the block that
sets `fromCache`, computes `cacheAge` and logs "last written N ago". So the filed symptom never happened.
Both reviewers reached that independently, and `silent-failure-hunter` found the gap had been recorded
only inside the **fixed** M83 entry and in an operator log string - no id, no status, no worklist row,
which is exactly the situation M86 itself was created to avoid. It is **M112** now.

**What the write-back actually broke is placeholder detection**, and that is a better reason to fix it.
The timestamp *is* read on Android, by `IsShippedPlaceholderCopy`'s `length|ticks` stamp check, which
sits above the `#if`. Two shapes, and the entry's prescribed same-file test only catches the first:

- **cache exists** - the file being read is the file being written, `WriteAtomic` moves
  `LastWriteTimeUtc`, the stamp stops matching, and from the second fallback boot a seeded stub is
  classified as a real cache.
- **no cache** - the destination is a *different* file, so a same-file test passes. Worse case, and
  **the mechanism is not what I first wrote**: the write *creates* the file the seed would have created,
  and `ConfigManager.Apply` skips a deployed `appData.json` that already exists, so `StampSeededAppData`
  **never runs at all**. There is no stamp to mismatch. I had written "invalidates the stamp";
  `silent-failure-hunter` corrected it, and the distinction matters because the wrong version sends the
  next person to fix `Apply` instead of the write.

Either way `failedRemoteJson` stays false and an empty keep-list from a stub is treated as authoritative
by the asset cleanup - a media-deletion risk, dormant only while `cleanUnlistedAssets` ships `false`.

So the fix is **by provenance, not by path identity**: a required `bool isLocalFallback`, with the cache
write gated on it. Required and not defaulted because `false` is the direction that writes; both
reviewers asked for that independently.

### Relabelled Android-only

The write-back was never reachable on WebGL. The `file://` conversion inside `LoadRemoteData` is
`#if UNITY_ANDROID || UNITY_IOS` while the branch that routes there is `UNITY_ANDROID || UNITY_WEBGL`, so
on WebGL the local path hands a raw `/idbfs/...` path to `UnityWebRequest.Get` and 404s before reaching
the write. Pre-existing and loud, and it means this change strictly improves WebGL rather than touching
it.

### A verification gap this round closed

**A change inside `#if UNITY_ANDROID` is compiled by none of the four assemblies.** The changed call site
is in that branch, so all four builds reported `0 Error(s)` without ever looking at it. Compiling it on

build. **Assert `0 Error(s)` is present; never treat "no error lines matched" as a pass.** That is the
same lesson as CLAUDE.md's rule about absence-based pass criteria, met in a build command instead of a
test step.

Then my escaping pass rebuilt those seven rows as `"| " + " | ".join(cells) + " |"` with cells taken from

## M113 - the appData fetch gets a timeout of its own, and the Android target finally paid off (v0.49.20)

`LoadRemoteData` created its `UnityWebRequest` and never set `www.timeout`. The one site the M43/M106
sweep missed, so a half-open CMS socket never returned: `www.result` never evaluated,
`FailRemoteAppData` never ran, the local fallback never started, and the boot stopped until the
watchdog latched.

**The operator chose a dedicated `AppData.timeout` key over reusing `Api.timeout`, and the reasoning is
worth keeping.** The two blocks are independently switchable and ship *opposite* - `Api.isActive` is
`false`, `AppData.isActive` is `true` - so raising `Api.timeout` for a slow endpoint would silently move
the appData fetch too, and a deployment with the Api module off would have no way to tune appData at all.
It takes the **API policy** (0 means unset -> 30, ceiling 300) rather than the file-transfer one, because
this is a small JSON document and not a resumable download.

### The watchdog had to move with it, and my first version was 5s short

The fetch sits inside one `_bootStage` string, and the watchdog only resets when that string changes - so
a budget narrower than the request it times would latch `BOOT STALLED` on a request still legitimately in
flight. Folding the effective appData timeout into `StallBudgetSeconds` was not enough.
`architect-reviewer` did the arithmetic: on Android and WebGL that one stage issues **two** bounded
requests - the remote attempt, then the local fallback re-entering the same method - with
`LocalDataFallbackSeconds` between them. Doubling alone is short by exactly 5s whenever the appData
timeout dominates, so `AppData.timeout: 60` with downloading off gave 120s against a 125s honest worst
case. The delay is a **term** now, in one `StageBudgetFor` helper. `failedRemoteJson` caps the stage at
two requests, so there is no third.

**And the fold-in nearly ate the existing budget.** The `AssetDownload` branch assigned to `widest`
rather than maxing into it, so pre-seeding `widest` with the appData timeout would have *discarded* the
download timeout whenever downloading is on - which is the shipped config, so that would have been live,
not theoretical. Caught while writing it, and the code review confirmed `:363` was the only such
assignment.

Consequence worth stating: **the shipped stall budget moves 120s -> 125s.** Safe direction, and it made
four other places stale - a remark I had edited *in this same round*, two source comments, and an §5b
row. A derived number quoted in prose goes stale the moment the derivation changes, and only grep finds
them all.

### Verified on Android, which is the half this project usually cannot reach

The operator switched the build profile to Android on request, and it converted three claims from
"unverified" into measurements.

**M86, retroactively:** with a real 129KB CMS cache in place, the CMS made unreachable and two fallback
boots run, `appData.json`'s mtime was **identical** across both. And the pass is not vacuous - which
mattered, because if the *local* read had also failed the write would have been skipped for the wrong
reason and the mtime would have been unchanged either way. Both boots show `OnGetAppData raw data:` with
the real menu content, `ParseAppData`, `AppData parsing complete!` and `Boot stage: appData loaded`, so
execution reached the point where the write used to happen.

**M113 end-to-end:** pointed at a black-hole IP with `AppData.timeout: 5`, the request failed after
**5.7s** with `[ConnectionError]: Request timeout`, the boot fell back, and no `BOOT STALLED`. Before the
fix nothing bounded it at all.

**The first attempt was inconclusive for an informative reason:** an `http://` black hole never leaves
the process, because the Android player settings disallow insecure connections
(`InvalidOperationException: Insecure connection not allowed`). It took `https://` to a packet-dropping
address to exercise a timeout at all.

`settings.json` was patched and restored byte-for-byte in a `finally` for both runs, asserted rather than
assumed - it carries a password and a live client hostname.

### `eval` does not see the project's scripting defines

Worth its own note because it reports a confident wrong answer. With the Android target active, an
`#if UNITY_ANDROID` inside an `eval` snippet still took the `#else` branch - and so did
`UNITY_STANDALONE_WIN` and `DO_LOGS`, which is what gave it away. The pipeline compiles the snippet
without the project's define set, so **any probe that detects platform with `#if` is measuring the
probe, not the project.**

The assembly is the authority, and asserting both directions is what settles it: the desktop-only
literals were **absent** from `EnigmaVirtual.dll` while `ToFileUrl` and `isLocalFallback` were
**present**, which is only true of a build compiled with `UNITY_ANDROID`.

### The count did not move again

M113 closed, M115 opened: `LoadRemoteSettings` is the last `UnityWebRequest` in the framework with no
timeout. Both reviewers found it and both agree it is **not** the same defect and must not take
`AppData.timeout` - its path is always a local `file://`/`jar:file://` read compiled only for
Android/WebGL, and nothing on the boot chain waits on it, so it wants a local-read `const` like the two
siblings already use. Logged so the sweep is provably complete rather than nearly complete, which is the
entire reason M113 existed.

## M112 + M114 + M115 batched, and the count finally falls (v0.49.21)

Three small defects in one file, all three found by the reviews of the two previous commits, batched on
the operator's call because reviewing them separately was costing more than the fixes.

**M114 - the appData request was never disposed.** Fixed with a `using` **declaration** rather than a
block, which is the only reason this was cheap: a block re-indents ~130 lines of coroutine body, and that
is the change most likely to introduce a brace error in the method the whole boot chain runs through.
`code-reviewer` confirmed the semantics are identical rather than merely similar - it lowers to a
`try`/`finally` spanning the rest of the method, and in an iterator that `finally` is emitted **into the
state machine**, so it runs inside `MoveNext` on every `yield break` and from `Dispose()` if the iterator
is abandoned. That is a stronger guarantee than reading a block would have given.

**M115 - the appSettings package read had no timeout.** A `const` of 10s, not a settings key, which is
what the entry predicted and both reviewers independently insisted on: that path always comes from
`AppPaths.Config`, the method is compiled only for Android and WebGL, and nothing on the boot chain waits
on it. A settings-driven network timeout would have misdescribed the operation. It leaves three sibling
classes each owning a 10s local-read bound - recorded in the entry rather than fixed, because
consolidating them means refactoring two working classes to fix a third.

**M112 - the offline fallback never said what it served on Android or WebGL.** The marking block lived
only in `LoadLocalData`'s desktop `#else` branch and that route returns before it, so a weeks-old cache
was served with `fromCache` false, `cacheAge` null and not one line in the log. **Extracted** into
`MarkServedFromLocalFile` and called from both routes - copying it was the obvious move and the wrong
one, since this class has produced a copy-paste divergence three times in two days.

It takes the **path** rather than a timestamp, and that is load-bearing: a path still carrying a scheme
after the `file://` conversion is a package entry with nothing to stat, so the age reads **unknown**.
Handing it a `default DateTime` would floor to "0 second(s) ago" and assert freshness over a stub, which
is the trap M42 recorded.

### Verified on Android, both shapes, which is what made this worth doing today

| shape | what the log now says |
|---|---|
| real 129KB CMS cache, written 0.86h earlier | `last written 52 minute(s) ago ... The screen is showing content from that time` |
| cache moved aside, shipped stub served | `last written 146 day(s) ago ... there is no content here to be old` |

146 days is exactly the shipped file's date, and the whole tail switches rather than a clause. **Before
this change neither line appeared at all on that route.** The first shape's test was also checked for
vacuity - if the local read had failed, the marking would be absent for the wrong reason - and both boots
show the read parsing successfully.

`code-reviewer` compared the extracted block against `HEAD` with comments stripped and whitespace
normalised: identical apart from two renames. Worth copying as a technique - "I checked the extraction by
eye" is what produced the three divergences it was guarding against.

### Two stale texts in the file I was changing, one of them operator-facing

`FailRemoteAppData`'s `LogError` said *"On Windows the load reports the cache's age; on Android and WebGL
it does not"* - the exact behaviour this commit reverses, in a **string literal that reaches an
operator**, so it is a behaviour claim rather than a comment. And `failedRemoteJson`'s XML used the
Android marking gap as the load-bearing evidence for "the two flags diverge in both directions"; the
conclusion survives, but the evidence had to be re-pointed at a fetch that fails outright and so never
reaches the marking at all.

That is twice in three commits that closing a defect falsified prose **inside the same file**. The
pattern is specific enough to name: when a fix changes what a platform does, grep the file for the name
of that platform before committing.

### The review found the inverse defect: my new line cried wolf

`silent-failure-hunter` found no silent failure introduced - and then found the opposite one. In
`useLocalAppData: true` mode the local file is the *configured* source, so the extracted message fired at
`LogError` saying "because the remote copy was not used ... if the CMS is reachable this is a
configuration problem" over content that was exactly as intended. Pre-existing on desktop; my diff
widened it to Android and WebGL. An Error on every healthy boot of a local-mode kiosk trains the operator
to scroll past the one line M112 exists to make actionable. Local mode gets the facts at `Log` level now.

**M112 was about a missing report, and its fix introduced a misleading one.** That is worth naming as a
shape: when you add a report to a path that was silent, check every configuration that reaches that path
and ask whether the report is *true* there, not just present.

Two more dormant findings, both mine from this batch. The rationale I wrote for M115's `const` was wrong
twice: `LoadRemoteSettings` carries no `#if` so it compiles into every target (only the *call site* is
gated), and on WebGL `AppPaths.Config` falls back to StreamingAssets, which the web server serves over

A rationale that sounds obvious is the kind that goes unchecked; both of these did.

And `File.GetLastWriteTimeUtc` does not throw for a missing file - it returns `1601-01-01`, which is not
`default(DateTime)`, so the unknown-age guard would have sailed past it and reported "155000 day(s) ago"

and an unreachable case in an inlined block is exactly what becomes reachable when it is shared.

The check I would not have thought to make: `APIResponseModel` is a **class**, so mutating `response`
inside the helper propagates. Had it been a struct, M112's fix would have done nothing at all on either
route and every test above would still have passed the compile.

### Two things I checked and deliberately did not change

A **future-dated** cache file gives `cacheAge` a negative `TimeSpan`. `StringUtil.FormatElapsed` already
returns "an unreadable amount of time (the timestamp is in the future)", so the operator line is correct
today; what remains is that a consumer's `if (age > threshold)` would be defeated, and there are zero
such consumers. `Api.cs` has the byte-identical shape and would have to be clamped in the same commit, so
clamping widens the blast radius for no reachable symptom.

The **mixed-separator** path in the log line - `C:/Work/.../Assets/StreamingAssets\config\appData.json` -
is `streamingAssetsPath` returning `/` while `Path.Combine` joins with `\`, exactly as `CLAUDE.md`
documents. Display-only, same variable the desktop branch always logged, and `File.*` handles both on
Windows.

## M46 - the blocker was not real, and the fix broke its own consumer (v0.49.22)

M46 has been *partly fixed* since v0.16.1. The entry said the remaining appData half was structural: it
needed `downloadFolder` given a real default, a settings-schema change that also relocates downloaded
media, and therefore "needs its own decision".

**That decision was not required, and the reason is an ordering constraint.** `ConfigManager` seeds the
deployed appData to the config **root**, and the generated deployment `.bat` copies there too - neither
with `downloadFolder`, because `ConfigManager.Preload` is a
`RuntimeInitializeOnLoadMethod(BeforeSceneLoad)`: it runs before settings are parsed, being what makes
settings readable at all. So the deployed copy lives at the root **by necessity**, and the reader simply
had to look there. Three candidates now, most specific first: the `downloadFolder` cache, the deployed
root, the shipped copy. With `downloadFolder` empty the first two are the same path, so nothing changes
for the config everyone ships.

### Both reviewers found that the fix broke the consumer, and code-reviewer returned BLOCK

`LoadLocalData` decided "real cache versus shipped placeholder" from `filePath != cachedPath` - **two**
outcomes, where the resolver now has three. A deployed root file would have been announced at `LogError`
as "the shipped placeholder ... declares no media, expect empty content", flipped the age report to
"there is no content here to be old", and set `failedRemoteJson`, disabling the asset keep-list for a
keep-list that was fine. **False in exactly the deployment the third candidate exists to serve.**

That is the same shape as M112 three commits ago: *adding a resolution outcome without updating the
consumer that discriminates on it.* Twice in one day is enough to state it as a rule - **when a resolver
gains a candidate, grep for every caller that compares its result against one of the old ones.**

It discriminates three ways now and routes the deployed case through `IsShippedPlaceholderCopy`, because
the `length|ticks` stamp is what tells a seeded stub from a real deployment and the path cannot.

### Still partly fixed, and that was the reviewer's call rather than mine

I asked directly whether M46 could close. `architect-reviewer` said no, and it was right: the symptom the
entry opens with is untouched. At the shipped `downloadFolder: ""` the runtime cache and an operator
override *are one file*, so the editor still cannot tell a stale copy left by a past `DEBUG_MODE` session
from a deliberate override. Gating the read is known-wrong - the shipped stub carries `"code": 0`, which
is `APIResponseCode.Success`, so a failed fetch would load placeholder content and report success.

What changed is that the schema decision is now **optional rather than blocking**: a project can set
`downloadFolder` and get a working deployment, where before that choice silently broke the seed. It also
said explicitly not to give the collision a new id, because *the collision is M46* and a second id is the
competing-defect-truths failure `CLAUDE.md` warns about. Both calls went into the entry as given.

### A probe assertion of mine that could not fail

The first version tested "did it resolve to the shipped copy?" with
`path.Contains("StreamingAssets")`. The persistent config folder is itself
`.../Unity Default/StreamingAssets/config`, so that substring matches **both** candidates - the check
could not distinguish the two answers it existed to tell apart. It passed, which is worse than failing.
It compares against `AppPaths.StreamingConfigFile` exactly now.

The tell was in the output rather than the result: assertion 3 PASSED while printing the detail string
"fell through to SHIPPED - the defect", because that detail used the same broken test. **A diagnostic
that contradicts its own verdict means one of the two is lying.**

## M55 - the entry's prescription was wrong, and the operator caught it (v0.49.23)

M55 says `OneCoreCommand.command_data`/`event_data` are `dynamic` and invisible to `JsonUtility`, and
that typing them as `string` would make them survive. I implemented exactly that, verified it with a
14-assertion probe, and was about to run reviews when the operator stopped me with their real project
data.

**Their `appData.json` puts a JSON object in `command_data` in one activity and `""` in another - and
appData is parsed by Newtonsoft, not `JsonUtility`.** Measured: Newtonsoft deserialising a JSON object
into a `string` field throws `JsonReaderException`. The change would have broken every branched project
using OneCore commands.

**The lesson is not "test more", it is which serializer.** `CLAUDE.md` already says two serializers
coexist - `JsonUtility` for settings.json, Newtonsoft for appData.json - and this type is filled by
**both**. I verified against the one the entry mentioned and never asked which others reach the same
field. A shared model type is a shared *contract*, and its constraints are the union of every parser
that fills it.

The entry had the same blind spot, which is worth stating plainly: it was written from the settings.json
side, and its prescription was safe only for the half of the traffic it could see.

### What landed instead

The type could never have been the fix - no single type is both `JsonUtility`-visible and able to hold a
JSON object. So the type change is only `dynamic` -> `object` (identical in metadata, so Newtonsoft
behaviour is byte-for-byte the same), and the settings.json half is closed by the **parser**:
`Core.RereadOneCoreWithNewtonsoft` re-reads that one block after the `JsonUtility` pass, using
`PopulateObject` so an absent key keeps the initialiser `JsonUtility` already applied.

### Making the read work created a data-loss path, and I only fixed half of it

`JsonUtility.ToJson` cannot emit `object`, and `SaveCoreSettings` merges with
`MergeArrayHandling.Replace` - so the whole `ConnectCommands` array is swapped for one without
`command_data`, **erasing the operator's payload from their own file on the next panel Save**. I found
that myself, measured it, and fixed `SaveCoreSettings`.

`architect-reviewer` then found the half I missed, and it is the worse one: `ConfigsPanel` also
snapshots settings into `PlayerPrefs["Settings"]`, `Core.Awake` **prefers that snapshot over the file**,
and on Android and iOS the prefs toggle is the panel's only writer. One Save would have shadowed a good
file with a lossy snapshot permanently, on the platform where that is the default path. Both writers go
through one `FileManager.SettingsAsJObject` now.

**The general shape, and it is the third time today:** enabling a read without the matching write is not
half a feature, it is a new defect. M112 and M46 were the same class - a resolver or a payload gained a
capability and a consumer was left behind.

### Free with the type change, and none of it was in the entry

Three `#pragma warning disable CS1974` pairs are gone. That warning was load-bearing: a **dynamically
dispatched call cannot be elided by the compiler**, so those `Development.LogIf` calls were *not* being
stripped on iOS and WebGL the way `[Conditional("DO_LOGS")]` intends - and were dereferencing
`Core.settings.OneCore.doLogs` there, which is the H17 shape. And the `EVENT` and `PUSH_EVENT` cases
logged `command_data` while sending `event_data`, so anyone debugging a failed event read a usually-null
field.

## M76 - two lookups for one manager, and my fix missed the path that ships (v0.49.24)

`MainController.SetupAssetManager` resolved the `AssetManager` from its own subtree and created one if
that missed; `CoreSystemUI` resolved it from a serialized reference or a scene-wide scan. Same object in
`CoreSetup.unity`, so it held - but move it in a branched project and `MainController` drives a manager
`CoreSystemUI` is not watching. Every preloader label stops updating, nothing is logged, boot completes.

**The cause was an asymmetry inside one file.** `SetupTextureCacheManager`, twenty lines away, already
adopts its instance *wherever it lives* before creating one, and documents why active-only is right:
`StartCoroutine` on an inactive GameObject does nothing but log. `SetupAssetManager` was the sibling that
never got that rung. Adding it is most of the fix, and it is the half both reviewers called correct.

The other half: `CoreSystemUI` **prefers** the owner's instance now rather than falling back to it. The
old line was `if (assetManager == null) assetManager = Core.main.AssetManager;` - so it only helped when
nothing had been found, and a non-null *wrong* answer won permanently.

### The version I would have shipped did not cover the shipped path

Both reviewers found this independently, and it is the finding worth keeping. `Init` decided
subscribe-or-wait from the **local field**. On the shipped config appData loads remotely, so when
`systemUI.Init()` runs `MainController` has not resolved its manager yet: `Core.main.AssetManager` is
null, the new preference returns early, and because `Awake` had already found something the branch
subscribed and never called `WaitForAssetManager`. That made the appData-loaded handler - the first
moment the owner exists, and the only place a wrong binding can be corrected - **unreachable on the path
everything ships with**. The new "the scene has two AssetManagers" error could not fire there either.

The gate asks the owner now, not the local field. The two branches stay mutually exclusive, which is what
makes double-subscription and stranded handlers impossible by construction rather than by care.

**I had reached for a bigger fix.** My draft made subscription idempotent with a `_listeningTo` field and
an extracted teardown, so a rebind after subscription would be safe. `code-reviewer` proposed flipping
the gate instead - four words - which removes the possibility rather than tolerating it. That is the
better shape and it is the one in the tree. Worth remembering: **when a fix needs machinery to stay safe,
check whether the invariant can be restored instead.**

### What the reviews confirmed rather than changed

Both `==` comparisons are Unity's overloaded operator deliberately. Walked through all four cases: a
destroyed owner compares equal to null so the existing binding is kept rather than replaced with a dead
one, and a destroyed local binding against a live owner rebinds **silently** instead of falsely claiming
two managers exist. `ReferenceEquals` on either operand would break the second case - which I had half
suspected and asked about, and would otherwise have "tidied" the wrong way.

### An hour lost to shell escaping, and the lesson is mechanical

Three attempts to patch a probe file through a heredoc turned an intended literal backslash-n into a real
newline, twice, and a fourth broke on backticks. The pattern that works: generate Python with `chr(10)`
and `splitlines()` rather than escape sequences, and write files whose content is dense with backticks
and apostrophes through a dedicated file-writing tool rather than a shell heredoc. Recorded because it
cost more time than the fix did.

## M84 - four throws become one report, and my guard removed a fallback (v0.49.25)

`oneCoreDataModel.idContent` is a POSITION into the payload's `modules` member, so
`jTokenModulesData[idContent]["content"]` threw for every malformed shape - an object gave
`ArgumentException`, a short array `ArgumentOutOfRangeException`, a scalar `InvalidOperationException`,
and a module with no `content` added an NRE. All of them escaped to the call-site catch, which reports a
generic message naming nothing.

**The fix routes them into a recovery this method already had.** The end-of-method check
(`if (dataLoaded && ReferenceEquals(AppData, modelBefore))`) already logs a good message explaining that
`idContent` is a position rather than an id, and already calls `FailRemoteAppData`. A throw at the top
jumped straight over it. `ResolveOneCoreContent` validates four things in order and returns `null`
instead, which lands exactly there - with a line of its own naming what was wrong first.

I checked the assumption that rests on before writing anything: `dataLoaded` is set before any parsing
and cleared only in the *no `modules` key at all* branch, and `AppData` is assigned only inside the block
that gets skipped. So a null return reaches the check with both still as required. Confirmed by reading,
not assumed - which mattered, because if it were false the change would have made the failure quieter,
not louder.

### My own guard was a regression, and both reviewers said so independently

The `try` I added around `ToObject(AppDataType)` ended in a bare `return`. That skips the end-of-method
check **and** the `else` that calls `FailRemoteAppData`, so control fell back through `OnGetAppData` to
`LoadRemoteData`, which only declines to cache and `yield break`s. A content block that no longer matched
the project's model went from **booting degraded on the local copy** to sitting on the preloader until
`BOOT STALLED`. The throw it replaced did recover. `code-reviewer` returned **BLOCK**.

**Reporting better while recovering worse is not an improvement** - and it is the second time in two days
that a guard added for clarity removed a fallback. The first was M112's marking; this is the same shape
from the other direction.

### One deviation from the prescription, made deliberately

Both reviewers proposed `dataLoaded = false` plus a fall-through to the method's own failure exit.
`ReportIfModelCannotSeeTheMedia()` sits immediately after that `try`, with the entire
Settings/Translations parse after it - so falling through would run all of it against a model that had
just failed to map, and report about the wrong thing. The catch reaches the same destination directly
instead, and uses the tail's own message so one outcome reads as one string.

### The shape that leaked through was the one that landed worst

Validating that the *entry* is an object does not make its `content` one. A `"content": [ ... ]` or
`"content": "x"` passed every check in my first resolver and then threw inside `ToObject` - the exit with
the least useful message. So the single shape the guard missed was routed to the worst possible place.
`content.Type != JTokenType.Object` closes it.

### What review confirmed rather than changed

`IsNullOrEmpty` is the reason the four refusals are not a regression: the caller already applied that
identical predicate to the resolved token, so `null`, `[]`, `{}` and `""` all took the no-content path
before this change. What is new is that the log says **which**. Worth recording, because "does this guard
reject something that used to work" is the question a shape check always has to answer, and here the
answer came from the fact that the predicate was hoisted rather than invented.

Three smaller things also came from review: `Development.LogException(e)` now runs first in the catch,
because catching deletes the stack Unity would have printed and Newtonsoft's names the member path that
failed to map (M80); an empty `modules` array no longer offers a "valid range is 0 to -1"; and the helper
is `protected`, since `ParseOneCoreAppData` is `protected virtual` and an overriding branch could not
otherwise call it.

### A probe that tested its own output

Three assertions failed on messages that were correct: my `lastError()` helper truncated to 96
characters and then searched the truncated string for words that sat beyond the cut. Second time today
that an assertion read its own diagnostic instead of the thing under test. It matches the full message
and truncates only for display now.

## Gotchas hit
- **`new CoreSettings()` leaves every depth-1 block null.** Only `EditorSettings` has a C#
  initialiser; `AppData`, `DebugSettings`, `System` and six more do not. Harmless in production —
  `JsonUtility` builds depth 1 regardless — but any probe that constructs settings in code must go
  through `JsonUtility.FromJson`, not `new`. Cost a debugging round.
- **`Core` must be fully qualified as `EnigmaVirtual.Core` inside `eval`**, and `Core.settings` /
  `Core.main` are **null outside play mode**, so a probe has to build both by reflection (private
  setters) and restore them afterwards.
- **A pipeline `400` saying "Main thread operation timed out after 5000ms" just means the editor is
  still finishing a domain reload.** Retry rather than debugging the payload.
- **`recompile` reporting `up_to_date, errors: 0` is not a compile.** It reports Unity's last
  *successful* one, so with an error in the tree it says that forever over a stale assembly. It let a
  non-compiling commit reach `master` and made a whole probe round measure the previous build.
  `dotnet build EnigmaVirtual.csproj` is the authority; if you must use the pipeline, grep the dll for
  a symbol only your edit introduces, because an mtime cannot tell "rebuilt" from "rebuilt without my
  file".
- **`(int)uint.MaxValue` written inline is a compile error, not a wrap.** C# folds it as a constant and
  refuses the overflowing conversion (`use 'unchecked' syntax to override`). Assign through a variable
  to reproduce what a narrowed *field* did — which is how the real defect compiled.
- **Multi-line anchors in a scripted edit need the file's own line endings.** `AssetManager.cs` is
  CRLF and `Api.cs` is LF, in the same folder tree, so one batch of edits matched and the other threw.
  Normalise to `\n`, edit, restore.
- **`internal` types are invisible to `eval`.** The pipeline compiles the snippet into its own
  assembly, so an `internal` helper has to be reached with
  `typeof(EnigmaVirtual.Api).Assembly.GetType("WebRequestExtensions")` and invoked by reflection.
- **A citation in this register is not always `file.cs:N`.** Three shapes are in use - `:255`,
  `:255-296` and `:434,698`, and `Api.cs:387-388,419,445` mixes them. My re-point script matched only
  the first, so every ranged or listed citation was invisible to four consecutive passes over the same
  file. That is the entire gap between the 9 I re-pointed and the 17 `doc-reviewer` found.
- **And the filter was backwards.** I only re-pointed a citation whose *current* line looked weak
  (blank, brace, comment). A citation that drifts onto **other real code** is the dangerous one -
  `CLAUDE.md` says so in as many words - and it is exactly the set I skipped by design. Re-point every
  citation in an edited file, gated on whether it still carries its pre-commit number, not on whether
  the line it now hits looks wrong.
- **`DO_LOGS` covers `Standalone`, and `Standalone` is Windows, macOS *and* Linux.** So the targets
  that strip `Log`/`LogWarning`/`LogIf` are iOS and WebGL - two, not four. "iOS, macOS, Linux and
  WebGL" was repeated across five documents, including as the stated reason for preferring `LogError`
  in the M77 round. Corrected in place everywhere, and `CLAUDE.md` now spells out the group membership
  so the next reader does not re-derive it wrongly.

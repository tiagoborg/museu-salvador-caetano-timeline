## Focus
E1 - an operator key that skips asset validation at boot, so a slow or unreachable host does not hold
a site down.

## Changed
- `Core`: sticky one-way `SkipAssetValidation` + `RequestSkipAssetValidation()`, reset with the other
  boot statics.
- `MainController`: `Ctrl+Alt+K` alongside the existing shortcuts, a settings-backed key with a
  hardcoded fallback, and the pre-phase check in `AppDataController_OnDataLoadedEvent`.
- `AssetManager`: per-asset check in the download loop, and cleanup skipped outright.
- `SystemSettings.WindowsSettings`: `skipAssetValidationKeyCode`, defaulting to `K`.
- `settings.json` (working tree only): the key added so it is discoverable.

## Decisions
- **Cleanup is skipped, not just the download.** It would probably be safe - the keep-list comes from
  appData, not from what downloaded, and M29's corroboration check would refuse anyway once few files
  are present. But "probably safe" plus "deletes files" plus "a human just hit the panic key" is not
  a combination worth reasoning about at a site.
- **Behind Ctrl+Alt like the others.** A bare key that skipped validation would be far easier to hit
  by accident than to diagnose afterwards.
- **The trigger is Windows-only, the mechanism is not.** Another target can add its own trigger
  without touching the asset phase.

## What the reviews caught
Every finding was the same theme, and it is the theme the feature exists to serve: **a skip must not
be silent, and must not over-claim.**

The first version failed both. A skipped boot was indistinguishable from a clean one - no
notification, and the boot stage trace still read "assets validated". The abandoned tail was folded
into a count labelled "will be MISSING at runtime", which is the exact over-claim I removed from the
M34 abort **120 lines below in the same file** - a fully cached kiosk skipped at asset 3 of 225 would
have reported 222 missing assets that were all present. The `yield break` dropped the stale and
unparseable-header tallies that the M34 path reports. The cleanup-skipped line was `LogWarning`,
stripped without `DO_LOGS`, for a step that deletes files. And pressing the key after boot had
finished still logged a degradation that never happened.

Also: no acknowledgment that the press registered. The in-flight request has to finish first - up to
60s as shipped - so for a minute nothing changes, and the idempotent early return meant a second
press produced complete silence. Every press now raises a notification, before the idempotence check.

**A false claim in my own comment**, of the kind I have been correcting in other people's text all
week: I wrote that H5's config patching would add the key to deployed configs. It cannot - the
patcher copies keys the *shipped* file has, and the shipped file does not carry it. Corrected on the
record; the fallback is the mechanism, not a safety net for it.

**And the register's original design note for E1 was wrong.** I wrote that the key must not depend on
settings parsing, citing H17. But asset validation is only reached *after* settings parse, so that
is not the risk. The real one is a config deployed before the feature existed, where the absent key
reads as `KeyCode.None` and the shortcut silently does not exist.

### H7 - the dispatcher drain (v0.14.1)

Three defects in ten lines, all fixed by the same change: drain under the lock into a reusable buffer,
invoke outside it.

The `while (actions.Count > 0)` read Count while workers enqueued under the lock. `Queue<T>` is not
thread-safe, so a concurrent `Enqueue` resizing the backing array made that undefined behaviour, not a
stale read. The loop then re-read Count after every invoke, so an action that enqueued another kept
the drain alive - an unbounded livelock inside `Update`. And a throwing action exited the loop, so
everything behind it waited a frame while Unity logged an exception that named no queued action.

**Review caught a correctness bug I introduced.** `draining.Clear()` sat after the loop, unprotected.
Anything escaping it - a `ThreadAbort`, which Mono re-raises at the end of a catch - would leave every
already-invoked action in the buffer, and the next frame with queued work would append and run them
**a second time**. Silent duplicate side effects, which is worse than whatever caused the escape. Now
in a `finally`.

Two smaller ones from the same pass: the error message did not name the failing delegate, which was
the entire point of fixing defect 3 - it now logs Method/Target explicitly, because IL2CPP strips the
stack trace that would otherwise identify it. And the null-action guard sat *after* the dispatcher
lookup, so `RunOnMainThread(null)` with no dispatcher present blamed a missing component for a caller
bug; it is checked first now, since diagnosing a null needs no dispatcher.

**`performance-reviewer` recommended no changes**, which is worth recording because I had moved a lock
onto a per-frame path: an uncontended `Monitor.Enter`/`Exit` is ~20-50ns, against the ~0.1-0.5us Unity
spends dispatching into `Update` at all - so the lock is a rounding error on the cost of the method
existing. It also confirmed the buffer is allocation-free in steady state (`List<T>.Clear` keeps
capacity), that the per-action `try/catch` costs nothing when nothing throws, and that hoisting it out
of the loop would reintroduce defect 3. The alternatives that would avoid the lock - an `Interlocked`
counter, `ConcurrentQueue`, a volatile flag - all land in the same tens-of-nanoseconds band while
being harder to prove correct.

**Verified:** braces; every access to `actions` is inside a lock (checked by parsing lock spans rather
than by eye); the guard order in `RunOnMainThread` reads null -> snapshot -> dispatcher -> lock.
**Not verified:** compile, and the race itself is not reproducible on demand - which is why review
rather than testing was the only way to find any of this.

### M3 - standardise the content VOs on fields (v0.14.2)

Six auto-properties became fields, all in `App/Model/AppData.cs`. Nothing was broken beforehand -
`MediaWalker` has read both member kinds since v0.8.0 - so this is a consistency change, and the value
is entirely in what the template teaches the next project.

**The register overstated the scope in two ways.** It cited `AppSettingsBase.cs`, which has no
auto-properties at all, and implied a codebase-wide pattern. The other properties in the codebase -
`KeyData.button`, `Timer.interval`, `SimpleSideMenu`'s states, `RawKeyInput.InterceptMessages` - are
derived runtime state, are correctly properties, and would be actively wrong as fields:
`KeyData.button` is assigned from `GetComponent<Button>()` in Awake, so a field would offer an
Inspector slot someone could fill wrongly and Unity would persist a stale reference.

**`architect-reviewer` gave me a better argument than the one I wrote, and caught that mine was wrong
for this file.** I had put a header comment claiming JsonUtility and Inspector visibility as the
reason. Neither applies here: `AppData` is Newtonsoft-only and no serialized field holds these types.
The reason that does hold is that `JsonUtility` **round-trips** - `SaveAppSettings` writes with
`JsonUtility.ToJson`, so a property copied from this template into a settings DTO is not merely
unread, it is **erased on the next save**. Fields are the only member kind all three serializers see.
That is now what the header says.

It also killed a benefit I had claimed: the Inspector. `TranslatableField<T>` derives from `Dictionary`,
which Unity cannot serialize, so a `MediaVO` in a serialized field would show id/thumb/url and silently
omit title/description/keywords - worse than showing nothing. Removed from the rationale.

And it found `AppData` was the only class in the file without `[System.Serializable]`, which its six
siblings all carry. Added.

**Recorded for branched projects**, because this is the one part that can bite silently: property→field
is source-compatible for reads and writes, and Newtonsoft is unaffected. The compile breaks are cheap
(an interface the project declared that these VOs satisfy - a field cannot implement a property member).
The silent break is the M4 mirror: a project-side `GetProperties()` walk over these types now returns
zero, and the framework's model-mismatch net sits behind `cleanUnlistedAssets`, which ships false. The
mitigation is not code, it is one line of merge guidance:
`grep -rn "GetProperties" Assets/01_Scripts/App`.

## Verified
- All six converted, no auto-properties left in the file, seven classes and seven
  `[System.Serializable]` attributes.
- `AppData` is read only via Newtonsoft `ToObject<AppData>` (`AppDataController.cs:364,:416`).
- No `MediaVO` is a serialized MonoBehaviour field anywhere - every reference is a method parameter -
  so nothing became newly Inspector-visible or scene-persisted.
- `ReflectionExtensions.HasProperty` would have broken, but has zero callers (dead code, L1).

### The boot-stage marks are not logging (v0.15.1)

Tiago's clarification was that `AssetManager_onAssetProgress` was gated on `AssetDownload.doLogs`
deliberately, to stop a 200-asset pass writing one line per file. Fair, and the spam is real - but
`MarkBootStage` does two things, and only one of them is logging: it also resets the C3 watchdog
deadline. With `doLogs` shipping `false`, the whole longest phase of startup stopped feeding the
watchdog, so a healthy download set would trip the stall timeout on its own. That is the same
regression review caught when C3 was first written.

Split into `MarkBootStage(string stage, bool log = true)`: the deadline reset is unconditional and a
call site cannot opt out of it, the log line follows `doLogs`. The gate stays where Tiago put it, it
just applies to the half he meant.

Worth noting as a pattern rather than a one-off: this is the second time a change that reads as
"logging only" has turned out to carry behaviour. `DO_LOGS` stripping `Assert` arguments was the
first (H17). A flag named for logging is not evidence that only logging is behind it.

- `Core.settings?.AppData?.Cache?.AssetDownload?.doLogs ?? false` is fully null-conditional, so the

### H6 - config seeding off Windows (v0.16.0)

The register described H6 as one `#if` in the wrong place. It was four defects in three files, and
**deleting the `#if` on its own would have turned Android from working into a boot hang.**

`FileManager.LoadStreamingFile` routed on the *platform*, so on Android it sent every path to the
URL-only `LoadJsonWeb` - including `persistentDataPath`, which is an ordinary readable file there.
That branch was simply never taken, because with seeding `#if`'d out there was no deployed config to
read. Seed one and it returns an empty string; an empty settings.json means null `Core.settings`, no
`CoreSetupComplete()`, and the C3 preloader hang. **Android worked because H6 was broken**, and that
turned out to be true in two more places.

**What the four reviewers found, in the order it mattered:**

- **`code-reviewer` blocked the first version, correctly.** I had routed every platform through
  `UnityWebRequest` for the shipped file - tidy, and it moved Windows off the synchronous path. The old
  `Preload` patched inline, before `Core.Awake` read the config in the same startup; behind a
  `yield return www.SendWebRequest()` the patch cannot land until the update loop runs, which is after
  scene load. Every Windows config patch would have taken effect only after a restart, and the log
  would still have said "Patched … with new keys". It self-heals on the next launch, which is exactly
  why it would have been reported as "the setting only works the second time you launch it". Now: read
  inline where the shipped file is a real file, fetch only for `jar:file://`.
- **`code-reviewer` also found the first launch was still broken on Android.** `LoadJsonWeb` joined
  folder and filename with **no separator** - `.../configsettings.json` - and that is every
  StreamingAssets read on Android. H6 would have been fixed from launch two onward and still hung on
  launch one, with a bare `www.error` as the only clue.
- **`silent-failure-hunter` found the defect my fix armed.** `AppDataController` prefixed `file://`
  only when the path started with `/storage/` - but `persistentDataPath` is only under `/storage/`
  with Write Permission = External(SDCard), and this project ships `ForceSDCardPermission: 0`, so the
  real path is `/data/user/0/<pkg>/files` and the test never matched. Same shape as the `FileManager`
  defect, hidden for the same reason. Nothing in the boot chain waits on appSettings, so it would have
  failed with default settings and one blank error line. The iOS twin tested `"/Users/"`, a macOS path.
- **`architect-reviewer` reframed the root cause better than the register did.** The bug was not the
  `#if`'s condition, it was that the predicate existed in four sites in three spellings - and my fix
  made two of them agree *by comment*, which is how it comes back. There is one definition now,
  `AppPaths.UsesDeployedConfig`, `static readonly` rather than `const` so the guarded bodies still
  compile on every target instead of vanishing. That is the bug class H6 belonged to: code that cannot
  be wrong because it does not exist.
- It also caught that `SaveAppSettings` was `#if UNITY_WINDOWS || UNITY_STANDALONE` while its own
  remarks explain that it targets the writable folder *because* StreamingAssets is inside the APK on
  Android. Before H6 that gate was consistent - there was no deployed config to write. After it,
  Android would have had an `appSettings.json` it could read and never save, with the refusal reported
  through a `[Conditional("DO_LOGS")]` `LogWarning`. Gate removed; the existing try/catch reports a
  genuinely unwritable location.
- **`security-reviewer` cleared the new exposure and found the housekeeping.** `settings.json` now
  lands in `persistentDataPath` on Android/iOS, but `ForceSDCardPermission: 0` keeps it on internal
  storage and the identical file is already inside the APK, so there is no net exposure. Real: a
  blocked `File.Replace` left the whole merged config orphaned in a `.tmp` that nothing reads or
  cleans, and neither new request had a timeout on a boot path that has none of its own. Both fixed.
  The symlink/TOCTOU on a pre-planted `.tmp` it raised and then ruled out itself - the attacker
  already needs write access to the config directory.

**I caught one of my own:** applying the scheme fix, I changed the second site's guard to
`UNITY_ANDROID || UNITY_IOS` to match the first. But only Android and WebGL take the `UnityWebRequest`
branch there; iOS falls through to `File.Exists`, and `File.Exists("file://…")` is always false. That
would have broken the platform the change was meant to help. Reverted to Android-only, with the reason
in the comment.

**Logged rather than fixed:** M45 (Android now boots asynchronously on launch 1 and synchronously on
launch 2+, split on whether a deployed config exists - two boot orders on one platform), M46
(`AppPaths.Config()` has no editor gate, so a past `DEBUG_MODE` session leaves the editor half-reading
a stale seed), M47 (`DownloadableImage` still has the `/storage/` prefix test - live on Android,
independent of H6), M48 (a remote-settings failure logs an empty string and skips the one event, which
has no subscribers anyway). **M39 is closed by this change** - it was the `CopyFile` no-failure-branch
defect, and `CopyFile` is gone.

**Breaking change for branched projects:** `ConfigManagerHelper.CopyFile` was `public static` and is

### M46 - one line, and the one line was wrong for half of it (v0.16.1)

`AppPaths.Config()` was the only config resolver without the `UsesDeployedConfig` gate, so the editor

`APIResponseCode.Success`, so a session whose remote fetch failed would have loaded `Ipsum Lorem`
placeholder content **and reported success**. A regression on the failure path, introduced by a fix for
a silence. `downloadedDataJsonPath` reads `PersistentConfigFile` directly now, ungated, with the reason
in the file.

cache and the override are the same file only because `downloadFolder` ships empty, so the cache lands
exactly where an override would. Separating them needs `downloadFolder` to have a real default, which
is a settings-schema change - and that same split is what closes M49 below.

that a deployed copy which does exist was now skipped without a word - a developer dropping
`appSettings.json` into LocalLow would see no effect and no message, which is the same confusion in a
new place. `Config()` logs it now, and it can afford to: after the appData change its only caller is
`LoadSettings`, once per load.

### M49 - the cache was written in one place and read from another (v0.16.2)

The appData cache's write path and read path were two different expressions and agreed only because the
shipped `downloadFolder` is `""`. One resolver now, `AppDataSettings.TryGetCachedDataJsonPath`, used by
both sides. `code-reviewer` verified case by case that behaviour with `downloadFolder: ""` is
byte-identical - `Path.Combine` skips zero-length segments - so no deployed site changes.

**The interesting part is that my fix, as first written, was worse than the bug for one case.** I asked
the reviewers directly whether the new fallback was an improvement, because I was not sure. Both said no
and both were right: the shipped `appData.json` is a placeholder whose `"code": 0` is
`APIResponseCode.Success`, so falling back to it boots the app on two languages, one text key and zero
media. A kiosk showing blank screens, indistinguishable from a CMS fault, with nothing above `Log` level
to say why - against a stalled boot the C3 watchdog names in thirty seconds. The stall diagnosed better.

The fallback is still worth having, because a hang is not a good outcome either. It just has to
announce itself, so it now logs at `LogError` **and sets `failedRemoteJson`**.

**That flag is the half that mattered.** `silent-failure-hunter` traced it: `failedRemoteJson` is the C2
guard `AssetManager` checks before deleting unlisted files, and it was only ever set on the
`!useLocalAppData` branches. So a local-mode run on the stub would have presented an **empty keep-list**
as authoritative, and the cleanup - which ships `cleanUnlistedAssets: true` in this template - would have
removed the operator's entire media set, reported through a `[Conditional("DO_LOGS")]` `LogWarning` and
therefore silently on iOS, macOS and Linux. That is a data-loss path opened by a fix for a hang, and no
amount of reading my own diff would have found it; it took someone following the flag into another file.

**`security-reviewer` caught that my `try` did not cover what its comment claimed.** `Path.Combine` and
`Path.GetDirectoryName` sat outside it, and both throw `ArgumentException` on invalid path characters -
which both segments can contain, since both come from `settings.json` and `SetData("localDataJsonPath")`
writes it raw with no validation. I had also made the *read* side newly throwable by putting
`downloadFolder` into a path `LoadLocalData` reads without a try. The resolver returns `bool` instead of
throwing, which fixes both, and carries the containment check `Api.TryResolveCachePath` and the C2 guard
already have. Framed as consistency, not security: an operator who can edit `settings.json` can already
write anything the app can. What it stops is a typo silently redirecting a write, since `Path.Combine`
discards everything before an absolute segment.

**Three of my own comments were factually wrong** and `code-reviewer` caught each: "the boot chain
stopped" (it had not - `OnDataLoadedEvent` fires synchronously before the write, and nothing follows it),
"there will be nothing to fall back on" (there is, and that is the problem), and "one expression, so the
writer and the reader cannot disagree" (unqualified - `ConfigManager` and `BatchFileCreator` still write
appData without going through the resolver). All three corrected in place; the last one narrowed M46.

### M50 - the settings panel wrote to a file nothing read (v0.16.3)

### M54 - the Android settings block had never been read (v0.16.4)

`SystemSettings.Android` against a shipped `AndroidSettings` key. `JsonUtility` matches by field name, so
that block was dead: anyone who ever debugged Android behaviour against it was looking at the C#
initializer. Two lines to fix, and it survived this long because the shipped `sleepTimeout` is `-1` -
identical to the initializer - so the defect had no observable effect until an operator changed it.

**I asserted the severity and my evidence was invalid.** I said the old field was default-constructed
rather than null, so the setting was silently ignored rather than throwing. The evidence I gave: the
sibling nested fields have no initializers either, and `MainController.Init` dereferences them unguarded on
the Windows path that runs daily. `code-reviewer` pointed out that every one of those siblings *is present*
in the shipped settings.json, so they demonstrate only the present-key case - and `Android`'s key was
absent, which is the case in question. `JsonUtility`'s behaviour for an absent nested-class key is
undocumented and nothing in the repo settles it.

So the severity before this fix is genuinely unknown - silently ignored setting, or an NRE inside `Init()`
on Android, which is a boot hang. The register says that instead of picking one. **The field got
`= new AndroidSettings()`, which makes the question moot** - and covers the one case where an absent key is
*guaranteed*: a stale `PlayerPrefs["Settings"]` blob was serialized under the old name, on Android, the
only platform this field is read on and the only one where the panel writes prefs.

**`architect-reviewer` gave a better reason for renaming the field than the one I wrote, and corrected
mine.** I had justified it by saying H5's patcher would inject a stale `Android` block - wrong mechanism:
`PatchDeployed` merges shipped JSON into deployed JSON, not the C# model, so that only bites if the shipped
key is renamed too. The argument that settles it: `SaveCoreSettings` merges `ToJson(Core.settings)` back
into the operator's file, so **the field name is the write key as well as the read key**. One name is the
only stable state - supporting both would make the next save emit both and diverge, and a read-only shim
would have the first save write the old name.

**The compiler will mostly not catch this break**, because the only reader is inside `#if UNITY_ANDROID` -
so a Windows-targeting branch sees no error and silently inherits the fix. That is the good case, and it is
why the migration note is not optional. Rather than a `MIGRATION.md` that would go stale, `overview.md`
gained a **Breaking changes by version** table: it is already on CLAUDE.md's must-update list, and one row
per version is the whole deliverable. Five rows, covering today.

**Two things worth more than the fix.** First, a cross-check of all 181 keys in the shipped settings.json
against the 140 public fields in the model: `System.AndroidSettings` was the sole orphan, so this is one
defect and not the tip of a class. That check is logged as E2, warn-only, roughly 40 lines reusing
`CheckShippedSettings`'s existing JObject parse - worth far more in a branched project, where operators
hand-edit the file. Second, a new CLAUDE.md invariant that would have prevented it: **the field name is the
JSON key, in both directions** - a field whose name disagrees with its key is not merely unread, it is dead,
and a save writes a second key beside the operator's.

**A branch that patched this the other way now fails silently.** If a project renamed the *key* to
`Android` in its own deployed config, merging this makes that key unreadable with no compile error. In the
table.

### E2 - a build check for the bug class that cannot be seen (v0.17.0)

M54 survived the life of the project because nothing could surface it: `JsonUtility` matches by field name
and says nothing about a key it cannot place, so a mismatch is a block that is simply never read. It was
found by accident, while fixing something else. `BuildValidator` now walks every key in the shipped
settings.json beside the `CoreSettings` field that would receive it and reports the ones no field can take.

**Warn-only, and that was the design constraint rather than timidity.** Legitimately unreachable keys exist
today - M55's `dynamic` fields are `object`, which Unity's serializer skips - so a gate would have shipped
with a suppression list, and `architect-reviewer` was right that the list is what eventually gets the rule
deleted. It runs on every build rather than release-only, because a dead key is dead in a development build
too, and the warnings are emitted *before* the failure throw so they survive a failing build.

**Two things I would have got wrong without checking.**

Inheritance: my first Python simulation of the rule reported eleven orphans under `OneCore`, which had me
briefly convinced the config was worse than I thought. `OneCoreClient.Settings : SocketsSettings` gets those
eleven keys from its base, and my simulation did not follow base classes. The C# is fine -
`GetFields(Public | Instance)` includes inherited fields, and only `DeclaredOnly` would have excluded them -
but a version of this rule written with `DeclaredOnly` would have warned about eleven non-problems on every
build, which is precisely how a rule earns deletion. Worth recording because the failure was in my
verification, not the code, and I nearly believed it.

Descending into `object`: `OneCoreCommand`'s `dynamic` fields reflect to zero fields, so descending into one
would report every child key as an orphan. `CanDescendInto` refuses, which is the honest answer for a field
whose contents this check cannot reason about.

**Verified by mutation test, not by inspection.** Six cases, all as specified: the real config clean; M54's
exact shape caught; an operator's case-typo (`api_Host` to `api_host`) caught; a typo three levels deep
caught, which proves the walk descends; an undeclared top-level block caught; and a typo *inside*
`serialPorts[0]` not caught - the documented array limit, now demonstrated rather than asserted. Both limits
are named in the rule's own message so a clean result is not read as broader than it is.

**It found three things on its first run**, at Log level rather than warning, because they are not defects -
an absent key keeps the C# initializer by design. They are knobs an operator cannot turn because they were
never given them, which is what E1 ran into: `AppData.appDataMaxLenght` (whose spelling L6 already covers),
`OSC.clientName`, `SerialPorts.showNotifications`.

### H14 - a plaintext password and a lockout that never locked (v0.19.0)

**The register described the lockout bug backwards, and the truth was worse.** It said `numTries` is
*never reset*. It was reset - in `Show()`, line 36 - and that was the defect: three wrong guesses hid the
panel, the next long-press reopened it with the counter at zero, so an attempt limit of 3 cost an attacker
one extra gesture. Unlimited guessing, recorded in the register as the opposite mechanism.

**Hashing.** New `PanelPassword`: PBKDF2-HMAC-SHA1, per-password random salt, stored as one
self-describing field so no salt or iteration count needs configuring separately. SHA-1 is deliberate -
the `Rfc2898DeriveBytes` overload taking a `HashAlgorithmName` needs .NET Framework 4.7.2, which is not
safe to assume across Unity's Mono versions.

**10,000 iterations, chosen by measurement rather than folklore.** Verification is synchronous in a click
handler, so its cost is a frozen frame: 10k is 57 ms, 100k is 547 ms. Half a second of dead UI on a kiosk
reads as "the button did not work", so the operator clicks again - and now spends another attempt against
the lockout. The 600k+ advice is for an internet-facing credential store where the attacker has the hashes
and not the machine; here the threat is disclosure of a reused password from a committed template, and
against a five-letter word 10k and 600k are the same answer. The count travels inside the hash, so a site
can raise it with no code change.

**Lockout.** An instance `_lockedUntilRealtime` deadline, which works only because `PanelBase.Hide` fades
a `CanvasGroup` rather than destroying anything, and `Core` is `DontDestroyOnLoad` - so it survives closing
the panel *and* the CoreSetup→Intro scene load.

**Three of the review findings were regressions in this fix, not pre-existing holes.** That is the part
worth writing down:

1. **The migration instructions disarmed the only hard gate.** `BuildValidator` failed a release build on
   `password == "gema"`. My own instructions said to blank `password` and set `passwordHash` - so hashing
   `"gema"` passed every check while the panel still accepted it, and 10k PBKDF2 over a four-character
   dictionary word falls offline in seconds. `security-reviewer` found it. The gate now also fails when
   `passwordHash` verifies the default.
2. **`lockoutSeconds: 0` made the lockout a no-op that reported success.** `Mathf.Max(0, ...)` set the
   deadline to *now*; `_failedTries` had just been reset; the next click went straight through while the
   label read "Locked for 0s." and the log announced a lockout. A control that claims success and does
   nothing is this register's single most common defect shape, and I wrote a fresh one into the fix for it.
   `code-reviewer` found it. A 0 is now honoured as "rate limiting off" and *said*, not performed.
3. **A malformed `passwordHash` was invisible at build time.** The no-credential warning stayed quiet
   because the field was non-empty, and the panel refused every entry at runtime. `LooksLikeHash` now
   gates a warning - which also gave that method the production caller it was missing.

**Plaintext still works, deliberately.** Updating the framework must not lock a live site out of its own
diagnostics panel. Every plaintext comparison logs an error, `BuildValidator` warns on every build, and a
release build fails.

**The migration step that is easy to miss and defeats all of it:** `Core` prefers a
`PlayerPrefs["Settings"]` snapshot over settings.json, and an old snapshot has no `passwordHash` key - so
on any machine that ever saved from the panel, the old plaintext password keeps working. On Android and
iOS that snapshot is the only save target. This is now a `CLAUDE.md` convention, because it applies to
every config-format change, not just this one.

**Ceiling, stated plainly.** This stops the password being readable at rest, which is what H14 actually
logged. It does not stop anyone who can *write* `settings.json` from replacing the hash, and
`MainController`'s Ctrl+Alt+R clears the lockout for anyone with a keyboard. It is a real rate limit
against a visitor with a touchscreen - the threat a kiosk panel has.

**Found, not fixed:** M59. The panel is shielded from a pre-boot NRE by accident - `CoreSystemUI.Awake`

### M60 - tested, and not a defect

Logged during H18 as a suspicion: 18 nested-settings-class fields have no initializer, so each would be
null when its block is absent from settings.json, and `MainController.Init` dereferences all ten top-level
blocks in one method - a boot NRE with nothing surfaced, C3's shape. I deliberately did not fix it on

**The premise was false, both halves.** `JsonUtility.FromJson` constructs an absent nested
`[Serializable]` class field rather than leaving it null: the `Phidgets` block was deleted from a copy of
the shipped config and the editor booted clean through to `Core :: Boot complete.`, having dereferenced
`Core.settings.Phidgets.isActive`. And the two arrays that genuinely have no initializer are both guarded

change would have been a no-op.

the pass criterion was an absence (no NRE), and nothing in the log showed the swapped config had been

names, for the second time in two days.

stopped being "no crash happened" and became "this specific content was imported, and then boot completed".

cites it as evidence of a risk.

### C6 + M17 - the socket layer rewritten (v0.20.0)

The register's last Critical, folded together with M17 as its sequencing note always said to.

**I argued for deferring this, and Tiago was right to override it.** My reasoning was that both `isActive`
flags ship `false`, so the code is dormant and a threading rewrite could not be tested here. His answer:
this is a base project, every client project branches from it, and "not active in the base config" says
nothing about what child projects need - a defect left here ships to all of them and comes back as his
support call. Dormant-here makes testing harder; it does not make broken code acceptable. My "cannot be
tested" was also simply wrong: I had written the echo-server harness in the same message I used to argue it.

**The old design was four interlocking defects, not four independent ones.** A throwaway thread that
connected and then invoked a `UnityEvent` from itself; per-frame `DataAvailable` polling on the main
thread; three unsynchronised `bool`s shared between the two; `SendTimeout = 3` **milliseconds**. Now one
worker owns the socket - `BeginConnect` with a 5&#160;s timeout, then a blocking read loop framing on `'|'`
into a `ConcurrentQueue<string>` - and it touches no Unity API at all. One `volatile bool` replaces the
three flags; `TryGetMessage` replaces `ReadSocket`.

**`OneCoreSocketConnection` is deleted.** It was a copy of the same socket layer that had already diverged -
keeping four of C6's five defects while losing the fifth - which is the clearest demonstration available
that the duplicate *was* the bug. `OneCoreClient.Settings` derives from `SocketsSettings`, so one class
always served both.

**Three of the four review findings were regressions in my rewrite, and one was worse than what it
replaced:**

1. **A compounding leak.** The reconnect branch did not tear down first, so a half-open socket - pulled
   cable, powered-off host, no FIN or RST - left the worker blocked in `Read` forever. `JoinWorker` then
   froze the **main thread** for its full 6&#160;s timeout, gave up, and left a live thread holding a
   socket; when the OS eventually killed that read, the abandoned worker reported the by-then *healthy*
   connection as dead and the cycle repeated. One leaked thread per network blip. Found independently by
   both reviewers, which is the strongest signal I have had all session.
2. **An observability regression.** `_reportedState` started at `-1`, so the first `Update` spent the only
   transition slot on a failure that had not happened: an error notification on the kiosk at boot,
   `onDisconnectedEvent` raised to child-project code, and then every real connect failure reported to
   nobody. The old code logged every attempt. A kiosk whose server had moved would log one bogus line and
   go mute for months - and two minutes of that looks identical to six.
3. **A silent drop.** Queue overflow was reported through `_lastError`, which is only read on a disconnect -
   so losing messages while connected said nothing, and the warning later resurfaced pretending to be the
   reason the connection died.

**A fourth regression, found by running it rather than reading it.** Stopping play in the editor
logged `Failed connecting to OneCore Server: 127.0.0.1:6501` as an **error**, every single time:
`OnApplicationQuit` closed the socket, `CloseSocket` raised its transition, and `OneCore`'s handler reports
any disconnection as a failed connection. Two things wrong at once - a deliberate shutdown reported as a
failure, and reported as an error. The transition is now suppressed while quitting, since nothing
subscribing to it can usefully run then.

The instructive part is that `code-reviewer` **examined this exact path and cleared it**. Its question (f)
asked whether the synchronous fire in `CloseSocket` was safe during `OnDestroy`, and it correctly showed
that the *second* `CloseSocket` fires nothing because `_reportedState` is already 0. It never asked whether
the *first* one should fire at all. A review can only falsify the question it is given, and I gave it the
wrong one - "is the second call safe" instead of "should this event exist here". Running the thing found it
in one keystroke.

Corrected while there: `OneCore.OnConnectionChanged` called every disconnection "Failed connecting", which
sends whoever reads it to check a server address that had been fine for hours. It now distinguishes a lost
connection from a failed connect. Still imperfect - an explicit `StopOneCore()` reports "Lost connection"
as an error, because OneCore's own state machine does not tell its handler that the stop was deliberate.
Left alone rather than expanded into.

**A fifth regression, spotted on screen rather than in a log.** Starting OneCore produced three
notifications: "Trying to connect to **Socket** Server", "Connected to **Socket** Server", then "Success
connecting to **OneCore** Server". Two problems in one picture. The deleted `OneCoreSocketConnection` had
said "OneCore Server" in its own text, so merging the classes lost the name - one shared class cannot know
which server it is talking to. And the merge added a success notification the OneCore path never had, on
top of `OneCore`'s own.

`SocketConnection` now takes a `connectionName` from its owner, and `OneCore`'s duplicate toasts are gone
rather than the shared ones, because `SocketConnection`'s carry the reason and `OneCore`'s never did. The
events stay: `onConnectedEvent`/`onDisconnectedEvent` are what child projects build on, the toasts are not.

The pattern across regressions 4 and 5 is worth naming: **both were about what the change looks like from
outside, and neither review asked that.** I briefed both agents on threading, lifetime and correctness, and
they found the compounding leak and the observability regression - genuinely hard things. Nobody, me
included, asked "what does a person see when this runs". Two minutes of running it produced two findings
that four review passes did not.

**Two caller defects the old buffer had been hiding.** `OneCore.HandleTimeout` had never once run
(`response == "timeout"` cannot match a NUL-padded 8&#160;KB buffer) and `ProcessResponse` discarded every
message after the first newline. Both are live now - which is why the timeout branch became **M61**: it only
logs and carries on, so framing turned an unreachable undefined behaviour into the default one. That is a
Gema Core protocol decision, not a code one.

**`keepAliveTime` and `reconnectTime` are now capped at 300&#160;s.** Both were clamped at the low end only,
and the keep-alive ping is the *only* detector of a half-open socket, because a blocking read on one never
returns. Either value set large silently disabled recovery while still reading as connected.

## Verified

**Framing, out-of-tree against `csc.exe`** - the .NET Framework profile Unity targets - 13 cases, all
passing: several messages in one read; a message split across two reads; a split completed by a later read;
a trailing partial withheld until its delimiter arrives; a UTF-8 character straddling a read boundary (the
reason the decoder is stateful); CRLF stripped; empty frames and a leading delimiter dropped; a zero-byte
read; and honouring the read count. For contrast the harness prints what the old code did: **8,192
characters decoded for a four-character message, 8,187 of them NUL.**

**Not verified: anything against a real server.** There is no Gema Core host here and both flags ship

1. **Start a listener:**
   `python -c "import socket;s=socket.socket();s.setsockopt(socket.SOL_SOCKET,socket.SO_REUSEADDR,1);s.bind(('127.0.0.1',9000));s.listen(1);c,a=s.accept();[c.sendall(c.recv(4096)) for _ in iter(int,1)]"`

3. **Framing end to end:** have the listener send `hello|world|` in a single write. Two separate

### M61 - the timeout branch, closed by not inventing a protocol (v0.20.3)

C6's framing made this branch reachable for the first time, which is how it was found: `SocketResponse`
compared a message against `"timeout"` and called `HandleTimeout()`, which logged and carried on. When I
logged it I wrote that it "most likely" meant drop the connection and let the reconnect loop run.

**The evidence argued against my own suggestion.** `TIMEOUT`'s sibling constants `OK` and `ERROR` survive
only inside **commented-out** code referring to `MossCommand` and `_webSocket.Close()` - a WebSocket client
this one replaced. Nothing in the project sends or produces the token. And a bare `timeout` does not match
the protocol's own message shape, `^%(.+)%(.+)?%([0-1])?%(.+)$`, which is how every real message is
dispatched. Acting on it would have handed an unexplained server token the power to kill a connection, on
a guess - worse than the defect.

**What was actually wrong is narrower and provable: the branch swallowed the message.** It reported and
`continue`d, so `onDataReceivedEvent` never fired and a project that *does* know the protocol could not act
on it either. It now falls through to `OnMessage` like any other unrecognised message. The report is once
per connection, since this is a per-message path, and the comparison is case-insensitive because `OK` and
`ERROR` are upper case while `TIMEOUT`'s value is lower - the constant's casing is not evidence of
anything.

The log line now says the client does not act on it and why, instead of `"Timeout!"`. That is the whole of
what can be said honestly until someone documents the server side.

## Verified

1. **It compiles** - the only new symbol is `StringComparison`, and `System` was already imported.
2. **`grep -n "continue;" OneCore.cs`** shows none in `SocketResponse`: the message is no longer swallowed.
3. **With the echo listener from the C6 steps**, send `timeout|`. The Console must show the
   `OneCore sent "timeout"...` error **once**, and `onDataReceivedEvent` must fire for it - the second is
   the point, since that is what the old branch prevented.
4. **Send `timeout|` again on the same connection.** No second log line. Drop and restore the connection,
   send it once more: the log returns, because the flag resets on connect.
5. **Send `TIMEOUT|`** (upper case). Same path - that is the case-insensitivity.
6. **Counter-test:** send a real `%`-shaped message and confirm it still dispatches normally and does not
   trip the timeout branch.

Untestable here in the way that matters: what a real Gema Core server means by the token. The code now
states that rather than assuming it.

### H11 - a Dictionary that never used its own hash table (v0.21.0)

`TranslatableField<T> : Dictionary<string, T>`, and every lookup ran a `foreach` comparing keys with
`EqualsIgnoreCase`. Since that extension is exactly
`string.Equals(a, b, StringComparison.OrdinalIgnoreCase)`, the entire fix is to move the same rule into the
dictionary's comparer: identical matches, identical misses, only the cost changes.

**Both of this entry's own claims were wrong, and both overstated it.**

1. *"enumerator alloc"* - the scan allocated **nothing**. `foreach` over `this` binds to the inherited
   `Dictionary<K,V>.GetEnumerator()`, which returns a **struct**. But `performance-reviewer` found a real
   boxed enumerator one level up that nobody had noticed: `Translations.IsNullOrEmpty` resolved to the
   `IEnumerable<T>` overload of `IsNullOrEmpty`, whose `Any()` takes the enumerator through the interface -
   one heap allocation on **every** `GetTranslation` call, since it is the first thing evaluated. Fixed
   with a `Count` test. So the register's claim was wrong about the line it cited and right about the path.
2. *"O(keys x languages)"* - **additive**, O(keys + languages). The outer lookup finds one entry and the
   inner scan runs once over that entry. The only multiplier in the whole path was the `.ToLower()` bug,
   and it was x2.

**The 153x figure is algorithmic, not an improvement to anything shipped.** 247 ms to 2 ms for 50,000
lookups over 500 keys, measured out-of-tree. This repo cannot exhibit the defect: `appData.json` has
**one** translation key and `MultiLangText` appears in **no** scene or prefab. Labelled as such in the
register, because a number like that reads as a measured app win to whoever finds it next.

**The review caught a regression I had introduced, and it was the worst kind.** Making the dictionary
case-insensitive makes `"EN"` and `"en"` one key - so `Helper.ParseTranslations`'s `Add` **throws** on a
server that sends both, and `AppDataController` catches that exception and leaves `_translations` null. One
duplicated key in CMS data would have cost the app **every string it has**, silently, on any OneCore
branch. It is an indexer assignment now, which also makes the two parsers agree: the Newtonsoft path
already overwrote last-wins while `Add` threw.

**And the review deleted my own safety net with a better argument than I had for it.** I had kept the
linear scan as a fallback for "if the comparer did not apply", with a report. `performance-reviewer`
pointed out that **C# does not inherit constructors**: this type declares exactly one, it always passes the
comparer, and no reachable path produces an instance without it - Newtonsoft included, which I had already
measured. So the fallback was dead code charging a `Comparer` read and a `ReferenceEquals` on every
*miss*, and misses are ordinary here. It also leaned on `Dictionary.Comparer` returning the instance it was
given, which is the `ConcurrentQueue<T>.Count` shape from `CLAUDE.md` - true as far as anyone traced it,
and not worth depending on when the type system already guarantees the thing. Deleted; the null guard
stayed, because that one is load-bearing.

## Verified

Out-of-tree against **Unity's own Newtonsoft DLL** (`Library/PackageCache/com.unity.nuget.newtonsoft-json`)
with the .NET Framework compiler - 21 cases, all passing:

- **`ToObject<TranslatableField<TranslatableField<string>>>()` preserves the comparer**, on the outer *and*
  the nested inner dictionaries. That is the assumption the whole fix rests on, and it is now measured
  rather than reasoned.
- The old scan and the new hash lookup **agree on every probe** - exact, lower, upper, mixed, absent,
  empty, and both whitespace variants.
- `base.TryGetValue(null, ...)` **throws**, where the old scan returned false. That is why the null guard
  exists.
- `ContainsKey` is now case-insensitive, which is why `caseSensitive: true` needed its own ordinal scan
  rather than the old `ContainsKey`.
- A plain `Dictionary` without the comparer **misses** on case - the failure the deleted fallback was
  guarding, demonstrated to be unreachable rather than assumed away.

A second harness for the regression, all passing: `Add` **throws** on a case-duplicate; the indexer does
not; it keeps one entry, last-wins; the Newtonsoft path behaves identically; and the two parsers now agree.

In the editor: nothing to see. There is one translation key and no `MultiLangText` in any scene, so a Play
run exercises none of this. The honest test is the harness, and for a branched project the marker is a
`GC.Alloc` spike on the frame that raises `Core.LanguageChangedEvent` - which should now be absent.
